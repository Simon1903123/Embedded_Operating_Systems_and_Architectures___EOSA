In the first two weeks, the focus was entirely on very low-level management: configuring the bare CPU so that it could start executing code[cite: 91]. We successfully built a freestanding C program (with no \texttt{libc} and no underlying OS) that could boot the CPU and print a message to the screen[cite: 91]. The ultimate goal of this course is to write a small operating system. Having started from the bottom by configuring the CPU, the next logical step is to learn how to use the other devices present on our board. This introduces three major additions to our codebase[cite: 91]:
\begin{itemize}
    \item A driver for the board's UART, allowing us to implement a real \texttt{printf} function[cite: 91].
    \item Hardware interrupts, a timer tick, and an interrupt-driven transmit path[cite: 91].
    \item System calls, allowing a user application to securely ask the kernel for services instead of touching the hardware directly[cite: 91].
\end{itemize}

\subsection{Organizing Code for an Operating System}
While controlling a hardware device could technically be written in just a few lines of code, building a real operating system requires a robust software architecture. Starting this week, we will begin spreading our code across different files based on their logical roles in the OS. The codebase will become more complex not because the operations are inherently difficult, but because the code must be structured professionally to ensure maintainability and separation of concerns.

We will tackle device communication in stages:
\begin{enumerate}

    \item Next, we will introduce \textbf{interrupts} to manage devices more efficiently.
    \item Finally, we will integrate these mechanisms into a proper operating system structure using system calls.
\end{enumerate}

\section{CMSDK and CMSIS: ARM's Hardware and Software Standards}
To understand how we communicate with devices, it is essential to understand ARM's business model. ARM is not a chip manufacturer (like Samsung or Intel); instead, ARM designs the CPU architecture and the Instruction Set Architecture (ISA), and then sells licenses for these designs to manufacturers. 

Some companies (like Samsung) may buy the entire CPU design and simply manufacture it. Other companies (like Apple) pay for a license to use the ARM instruction set, but design the internal CPU hardware themselves.

Because every manufacturer could theoretically design their custom I/O devices completely differently, writing portable operating systems would be a nightmare. To solve this, ARM introduced standards to influence producers to build I/O devices that are software-compatible across different boards. These two standards sound similar but mean very different things[cite: 93]:

\begin{table}[h!]
\centering
\begin{tabular}{|p{0.15\linewidth}|p{0.4\linewidth}|p{0.4\linewidth}|}
\hline
 & \textbf{CMSDK (Cortex-M System Design Kit)} & \textbf{CMSIS (Cortex Microcontroller Software Interface Standard)} \\ \hline
\textbf{What it is} & \textbf{Hardware:} Ready-made peripheral designs that chip designers can physically place next to the CPU[cite: 93]. & \textbf{Software:} A standard for the C headers and functions used to describe a chip[cite: 93]. \\ \hline
\textbf{Examples} & APB UART, APB timer, dual timer, watchdog, AHB GPIO[cite: 93]. & \texttt{NVIC\_EnableIRQ()}, names like \texttt{UART0->DATA}, \texttt{UART0TX\_IRQn}, \texttt{core\_cm3.h}[cite: 93]. \\ \hline
\end{tabular}
\end{table}

\subsection{How the Standards Work}
The \textbf{CMSDK} standard tells hardware designers exactly how a device (like a UART) must be structured from a programmer's perspective. It dictates exactly how many registers the device must have, what each bit inside those registers means, and the addresses where those registers must be mapped. How the hardware actually works internally does not matter, as long as it respects these specifications.

Because the hardware interface is standardized, ARM can also provide the \textbf{CMSIS} standard---a set of ready-to-use C headers and software drivers. If you buy a board with CMSDK-compatible hardware in the industry, you can usually just include the CMSIS headers and everything works out of the box.

\subsection{Our Approach in This Course}
Our emulated board's peripherals are standard CMSDK blocks[cite: 93]. However, to truly understand how an OS interacts with hardware, \textbf{we will not use any vendor CMSIS files or libraries}[cite: 93]. Instead, we will rewrite the entire framework manually from scratch. Our hand-written register header (\texttt{cmsdk.h}) is designed in a CMSIS style (so its variable names match standard documentation), but the underlying implementation will be entirely our own work[cite: 93].

\section{The Emulated Board and the I/O Landscape}
To write our own low-level OS layers from scratch, we must understand the specific hardware we are working with. We are using QEMU to emulate the \textbf{MPS2} ARM development board, specifically loaded with the \textbf{AN385} FPGA image[cite: 94]. This configuration features a Cortex-M3 CPU and several standard CMSDK peripherals, all driven by a 25 MHz system clock[cite: 94].

Our emulated board provides a specific set of hardware devices[cite: 94]:
\begin{itemize}
    \item \textbf{Timers:} Simple hardware devices comprising registers connected directly to the system clock[cite: 94]. You can program them with a specific value to count down to zero, or start from zero and count up. Because they are driven by a known clock frequency (25 MHz), they measure real time with extreme precision. Whenever software needs to perform activities with strict timing, timers are the mandatory hardware choice. The board features three of them: \texttt{TIMER0}, \texttt{TIMER1}, and a dual timer[cite: 94].
    \item \textbf{UART (Universal Asynchronous Receiver-Transmitter):} A legacy but incredibly common interface used to send serial bits over a line[cite: 94]. It is typically used to connect keyboards or terminals to a device. Its greatest advantage is being \texttt{asynchronous}, meaning the communicating devices do not need to share a common clock signal. The board provides three UARTs (\texttt{UART0}, \texttt{UART1}, \texttt{UART2})[cite: 94].
    \item \textbf{GPIO (General-Purpose Input/Output) and FPGAIO:} Simple hardware lines that can be programmed to output a 1 or a 0, or read incoming binary states[cite: 94]. If you need to connect a simple sensor or an actuator (like an LED or a button), you plug it into a GPIO line. On our emulated board, these are represented by \texttt{GPIO0} and the \texttt{FPGAIO} block[cite: 94].
\end{itemize}

\subsection{Memory-Mapped I/O}
How is each device physically accessible to the software? Every device consists of a set of hardware registers, and in the ARM Cortex-M architecture, these registers are \textbf{mapped directly into memory}. 

As seen in the Cortex-M memory map from Week 2, there is a specific range of addresses strictly reserved for peripherals (\texttt{0x4000\_0000} to \texttt{0x5FFF\_FFFF})[cite: 94]. Every single device is assigned to one or more memory addresses within this region[cite: 94]. Software interacts with the device simply by writing to or reading from these exact memory locations:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{Address} & \textbf{Device} \\ \hline
\texttt{0x4000\_0000} & \texttt{TIMER0} / \texttt{TIMER1} / dual timer \\ \hline
\texttt{0x4000\_4000} & \texttt{UART0} / \texttt{UART1} / \texttt{UART2} \\ \hline
\texttt{0x4000\_8000} & watchdog \\ \hline
\texttt{0x4001\_0000} & \texttt{GPIO0} (general-purpose pins) \\ \hline
\texttt{0x4002\_8000} & \texttt{FPGAIO}: board LEDs and buttons \\ \hline
\end{tabular}
\end{table}

\section{Hardware Architecture: AHB vs. APB Buses}
When devices are physically connected to the CPU, they sit on hardware buses. A bus is the physical set of wires (address, data, control) that carries every load and store operation from the CPU to a memory module or a peripheral[cite: 95]. 

In the ARM architecture, there are two distinct types of buses[cite: 95]:
\begin{enumerate}
    \item \textbf{AHB (Advanced High-performance Bus):} This is the main, ultra-fast, pipelined bus, capable of executing one transfer per clock cycle[cite: 95]. When you design a board, devices that require high-speed, high-frequency access are connected here. This includes RAM, flash code memory, and the GPIO controller[cite: 95].
    \item \textbf{APB (Advanced Peripheral Bus):} This is a slower, simpler, and lower-power bus[cite: 95]. It is designed for peripheral registers that are touched rarely (e.g., configuring a timer's duration or sending a single byte over the UART). Devices like the UARTs, Timers, and the Watchdog reside here[cite: 95].
\end{enumerate}

\subsubsection{The AHB-to-APB Bridge and Performance}
To allow the CPU to communicate with devices on the slower bus, the board utilizes a small electronic circuit called the \textbf{AHB-to-APB bridge}[cite: 95]. This bridge acts like a network router: it takes transactions arriving from the high-speed AHB and, if they are directed to an APB device, forwards them to the low-speed bus[cite: 95].

From a software programming perspective, this complex hardware routing is totally transparent[cite: 95]. When you write software, you simply read or write instructions in memory[cite: 95]. However, from a performance perspective, it has a tangible impact: a single store operation targeting a device on the low-speed APB will take several more clock cycles to complete than a store operation targeting the high-speed AHB[cite: 95]. If you are designing a real-time system where performance is highly critical, you must be aware of the latency introduced by the peripheral's bus placement.

Finally, while these devices execute their operations on the bus, many of them are also capable of generating \textbf{interrupts} to proactively notify the CPU that an operation is complete[cite: 96].

\section{The Board's Interrupt Lines}
Devices communicate with the CPU by raising physical hardware signals called Interrupt Request (IRQ) lines[cite: 96]. These physical lines are limited, and in a standardized architecture like the Cortex-M, devices are hardwired to specific, predefined lines[cite: 96]. When designing a board around a standard architecture, hardware designers are not free to connect devices to any arbitrary interrupt line[cite: 96]. 

The architecture strictly dictates which device must be connected to which line. For example, device IRQ line $N$ is served by vector-table slot $16 + N$, which sits right after the 16 core slots you configured during the boot process[cite: 96].

The AN385 board provides the following specific IRQ mapping for our devices[cite: 96]:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|l|l|}
\hline
\textbf{IRQ} & \textbf{Device} & \textbf{IRQ} & \textbf{Device} \\ \hline
0 & \texttt{UART0} receive (RX) & 8 & \texttt{TIMER0} \\ \hline
1 & \texttt{UART0} transmit (TX) & 9 & \texttt{TIMER1} \\ \hline
2/3 & \texttt{UART1} RX / TX & 10 & dual timer \\ \hline
4/5 & \texttt{UART2} RX / TX & 12 & UART overflow (all UARTs combined) \\ \hline
\end{tabular}
\end{table}

While you do not need to memorize all these lines, when you write software, you absolutely need to know where your hardware is connected. If we want to implement an interrupt-driven UART driver, we must use the exact slot in the vector table (e.g., IRQ 0 and 1 for UART0) to set the interrupt handler[cite: 96]. 

\texttt{Hardware Notes:}
\begin{itemize}
    \item High-end embedded boards often feature many UARTs and timers; they are extremely important for system design, and having more of them generally makes a board more capable. Our board features three UARTs (\texttt{UART0}, \texttt{UART1}, \texttt{UART2}).
    \item The watchdog timer has no standard IRQ line; instead, it raises the NMI (Non-Maskable Interrupt, slot 2) exception, which cannot be masked or ignored[cite: 96].
    \item QEMU raises every line in the table except IRQ 12, because its UART model never reports an overflow condition[cite: 96].
\end{itemize}

In the initial part of this unit, the CPU will simply poll the devices (asking them in a loop), meaning we will not use these interrupts just yet[cite: 96].

\section{Software Organization: \texttt{include/cmsdk.h}}
From the hardware standpoint, we know that every I/O device is associated with a specific range of memory addresses, and the specifications dictate the meaning of each address. From a software perspective, things start to become more complex. 

If you wanted to write software in a completely unstructured way, you could simply keep your CPU in privileged mode and directly read or write to raw hexadecimal memory addresses to control everything. However, to organize the software professionally—like a real operating system—it is best practice to define data types that group the information and registers of a device into a \texttt{struct}[cite: 97].

\subsection{Registers as a Struct}
The CMSDK specification dictates exactly how many registers a device has[cite: 97]. For instance, a CMSDK-compliant UART features exactly five registers, and every register is 32 bits wide[cite: 97]. We define a data structure with five elements, each being an unsigned 32-bit integer[cite: 97].

This layout is completely provided in the \texttt{include/cmsdk.h} file:

\begin{lstlisting}
typedef struct
{
    volatile uint32_t DATA;      /* 0x00: read = received byte, write = byte to send */
    volatile uint32_t STATE;     /* 0x04: status flags */
    volatile uint32_t CTRL;      /* 0x08: control flags */
    volatile uint32_t INTSTATUS; /* 0x0C: interrupt status; write 1 to clear a bit */
    volatile uint32_t BAUDDIV;   /* 0x10: baud-rate divider */
} CMSDK_UART_TypeDef;

#define CMSDK_UART0 ((CMSDK_UART_TypeDef *) 0x40004000UL)
\end{lstlisting}

\subsection{Why Use Structures?}
In C, the elements of a \texttt{struct} are allocated in continuous memory addresses. If you know the \textbf{base address} of a device by checking the board manual (e.g., \texttt{0x40004000} for \texttt{UART0}), you can instantiate the design by casting that initial address to a pointer of your struct type[cite: 97]. 

Because the structure exactly mirrors the hardware, addressing the members of the data structure actually accesses the correct, continuous hardware memory addresses[cite: 97]. For example, \texttt{CMSDK\_UART0->STATE} translates to a 32-bit load from \texttt{0x40004004}[cite: 97]. 

While you could manually declare every single register as a separate pointer, using a \texttt{struct} is a highly recommended best practice resulting from years of software maintenance and bug-fixing experience. The SDK design is incredibly general: because our board has three UARTs, we define the \texttt{struct} layout only once, and then simply write three \texttt{\#define} macros specifying the three different base addresses. The more you structure the software like this, the easier it is to maintain.

\subsection{Bitmasks and Hardware Control}
Because every device is ultimately controlled by manipulating specific bits within its registers, relying on raw hexadecimal values for every configuration is incredibly difficult and error-prone. To solve this, another standard good practice is creating \textbf{bitmasks}. This allows you to associate a human-readable mnemonic with a specific bit position.

In our \texttt{cmsdk.h} file, alongside the data structures, you will find a large number of bitmask definitions. These are typically defined using the left-shift bitwise operator (\texttt{<<})[cite: 108]:
\begin{itemize}
    \item \texttt{1 << 0}: Takes a 1 and shifts it 0 places to the left. This creates a mask where exactly bit 0 is equal to 1.
    \item \texttt{1 << 1}: Shifts the 1 one place to the left, meaning exactly bit 1 is equal to 1.
    \item \texttt{1 << 2}: Shifts the 1 two places to the left, meaning exactly bit 2 is equal to 1.
\end{itemize}

This notation is highly compact. While you could write out the full 32-bit hexadecimal masks (e.g., \texttt{0x00000004} for bit 2), reading strings of zeros becomes visually confusing. The compiler generates the exact same optimized machine code either way, but the shift notation allows a human reader to immediately know exactly which bit number is being targeted.

As an operating system designer, this is the very first stage of abstracting your hardware. You define data structures to give names to your memory addresses, and you define bitmasks to control the registers. This ensures your low-level code remains readable and maintainable.

\section{Try It: The Board's Memory Map from QEMU}
How can we verify that these devices and memory addresses actually exist? Because we are using the QEMU emulator, we can directly ask it to print the list of devices it is actively modeling[cite: 98].

QEMU features a \textbf{monitor}, which is a command console used to control the emulator itself[cite: 98]. You can start QEMU with no program loaded, paused (\texttt{-S}), with the monitor attached to your terminal, and with standard UART output discarded[cite: 98]:

\begin{lstlisting}
qemu-system-arm -M mps2-an385 -display none -S -monitor stdio -serial null
\end{lstlisting}

Once inside the QEMU monitor, typing \texttt{info mtree -f} prints every single memory address range and specifies what hardware component answers at that address[cite: 98]. 

Because the raw output is massive (it prints every address range available in QEMU), we can use a compact one-liner to filter the output, keeping only the peripheral addresses (\texttt{0x400xxxxx})[cite: 98]:

\begin{lstlisting}
printf 'info mtree -f\nquit\n' | qemu-system-arm -M mps2-an385 \
-display none -S -monitor stdio -serial null | grep 00000000400 | sort -u
\end{lstlisting}

Running this command explicitly prints the addresses of the devices that are actually implemented and working in QEMU[cite: 98]. You will clearly see the UART mapped at \texttt{0x40004000}, as well as the timers (\texttt{cmsdk-apb-timer}), the watchdog (\texttt{cmsdk-apb-watchdog}), and the FPGA I/O (\texttt{mps2-fpgaio}) mapped to their respective addresses[cite: 99].

\subsubsection{Interpreting the QEMU Memory Map Output}
When you analyze the output of the \texttt{info mtree -f} command, you will notice differences in how the devices are labeled. Specifically, you will see a priority value (\texttt{prio}) assigned to each memory region[cite: 99].

\begin{itemize}
    \item \textbf{\texttt{prio 0} + Device Name:} If a line shows \texttt{prio 0} followed by a specific device name (like \texttt{cmsdk-apb-timer} or \texttt{uart}), it means QEMU provides a \textbf{real, working model} of that device[cite: 99]. If your software performs operations at that memory address, QEMU will fully emulate the hardware's behavior.
    \item \textbf{\texttt{prio -1000}:} If a line shows \texttt{prio -1000} (such as the \texttt{cmsdk-ahb-gpio}), this indicates a \textbf{placeholder} (an "unimplemented device")[cite: 99]. Your software can still legally read or write to that memory location without crashing, but QEMU is not actually emulating the underlying hardware logic[cite: 99]. 
\end{itemize}

This distinction is crucial for emulator-based development. Placeholders are beneficial because they allow your software to execute without throwing hardware faults, but they have no functional behavior: writes are silently ignored, and reads typically just return 0[cite: 99]. 

For example, the GPIO (General-Purpose Input/Output) controller—which is a highly important I/O device on a real board—is merely a placeholder in our QEMU model[cite: 99]. You can write a 1 to a GPIO line to "turn on an LED", but nothing will visually happen in the emulator[cite: 99]. This limitation highlights why, to test complex hardware interactions, developers eventually need to deploy code onto physical hardware.

\texttt{Other noted devices:} You might also see \texttt{pl022} and \texttt{arm\_sbcon\_i2c} in the list[cite: 99]. These are an SPI controller and an I2C controller, respectively[cite: 99]. They are additional serial interfaces, but they are not fully emulated or used in this specific project[cite: 99].

\section{The General I/O Landscape}
To contextualize the devices we are working with, it is helpful to summarize the major categories of I/O interfaces found on modern embedded boards[cite: 102]. You rarely connect a complex peripheral (like a camera) directly to the CPU; instead, you plug it into one of these standardized I/O controllers[cite: 102].

\begin{table}[h!]
\centering
\begin{tabular}{|p{0.15\linewidth}|p{0.8\linewidth}|}
\hline
\textbf{Interface} & \textbf{Typical Use and Mechanics} \\ \hline
\textbf{GPIO} & \textbf{General-Purpose Input/Output.} These are simple, single-bit physical wires. You can program each line as an \texttt{input} (to read the 1/0 state of a sensor or button) or as an \texttt{output} (to drive a 1/0 voltage to an actuator, like turning an LED on or off)[cite: 102]. \\ \hline
\textbf{UART} & \textbf{Universal Asynchronous Receiver-Transmitter.} A serial connection using two distinct wires (TX and RX)[cite: 102]. It is strictly \texttt{asynchronous}, meaning there is no shared clock line between the devices; both sides must agree on a transmission speed (baud rate) beforehand[cite: 102]. Typically used for console output or PC communication[cite: 102]. \\ \hline
\textbf{SPI} & \textbf{Serial Peripheral Interface.} A fast, synchronous serial bus. The controller acts as the \texttt{master} and actively drives a shared clock wire[cite: 102]. It uses a chip-select wire to pick which \texttt{slave} device on the bus to talk to[cite: 102]. Often used for external flash memory or displays[cite: 102]. \\ \hline
\textbf{I2C} & \textbf{Inter-Integrated Circuit.} A synchronous serial bus that uses only two wires (clock and data) shared among multiple devices[cite: 102]. It supports multiple masters and multiple slaves, using 7-bit addresses to route data[cite: 102]. Often used for simple sensors[cite: 102]. \\ \hline
\textbf{ADC / DAC} & \textbf{Analog-to-Digital / Digital-to-Analog Converters.} Interfaces that translate an analog voltage level into a digital number (ADC, e.g., reading a temperature sensor) or convert a digital number into a physical voltage (DAC, e.g., outputting audio)[cite: 102]. \\ \hline
\end{tabular}
\end{table}

In this course, we will focus primarily on driving the UART, with timers acting as an exception since they are internal core devices that do not route through external interfaces.

\subsection{DMA: Moving Data Without the CPU}
Currently, our CPU must manually move every single byte of data: reading a register, storing it to memory, and repeating. For large data transfers (like reading a massive flash sector or an audio buffer), this forces the CPU to be 100\% busy for the duration of the transfer[cite: 103].

Modern microcontrollers solve this using a \textbf{DMA (Direct Memory Access)} controller[cite: 103]. The DMA is an independent hardware device that copies data by itself[cite: 103]. The software simply programs the DMA with a source address, a destination address, and a byte count, and then starts it[cite: 103]. The DMA uses the bus to move the data while the CPU is free to run other code[cite: 103]. Once finished, the DMA typically signals the CPU via a hardware interrupt[cite: 103].

While incredibly powerful, utilizing DMA comes with costs: the CPU and DMA must share the hardware bus, and the software must be carefully designed to never touch a memory buffer while the DMA is actively filling it[cite: 103]. Because QEMU's AN385 board does not feature a DMA controller, our OS will rely on the CPU to manually move every byte[cite: 103].

\section{Memory-Mapped I/O: Loads and Stores with Side Effects}
Different microprocessor architectures employ different programming styles to control I/O devices. For example, the x86 architecture features specific I/O instructions integrated directly into its assembly instruction set. 

The ARM architecture uses a different, more modern approach known as \textbf{Memory-Mapped I/O (MMIO)}. The instruction set has no specific I/O commands; instead, peripheral registers are assigned fixed memory addresses[cite: 104]. Talking to a device is achieved using standard \texttt{load} and \texttt{store} operations[cite: 104]. 

In C, this looks exactly like a standard variable pointer assignment[cite: 104]:
\begin{lstlisting}
#define UART0_DATA (*(volatile uint32_t *)0x40004000u)
UART0_DATA = 'A'; /* A store to 0x40004000: the UART sends 'A' */
\end{lstlisting}

\subsection{Hardware Side Effects}
While it looks like a variable assignment in C, a hardware register is fundamentally \textbf{not RAM}[cite: 104]. Operations on these memory addresses have immediate physical consequences in the real world (e.g., writing to a register might physically move a robot arm)[cite: 104].

Because of this, MMIO introduces several behaviors that seem counterintuitive when writing standard C code[cite: 104]:
\begin{itemize}
    \item \textbf{Reads have side effects:} Reading a memory location might alter the device's state (e.g., reading the UART data register extracts the byte and clears the "byte waiting" flag)[cite: 104].
    \item \textbf{Writes initiate actions:} Writing a value triggers a hardware action, which may asynchronously change other bits in the register to report the outcome[cite: 104].
    \item \textbf{Values change spontaneously:} If you read the exact same memory address twice in consecutive lines without writing anything, you may get two completely different values (e.g., a hardware timer actively counting down)[cite: 104].
    \item \textbf{Read-back differs from written value:} If you write a value to a register and immediately read it back, you might get a different result because some bits are read-only or hardware-controlled[cite: 104].
\end{itemize}

\section{The \texttt{volatile} Keyword}
These hardware side effects directly conflict with how standard C compilers optimize code[cite: 105]. A modern compiler assumes it is dealing with ordinary RAM, where a value only changes if the software explicitly writes to it[cite: 105].

Consider a loop waiting for a transmission buffer to empty:
\begin{lstlisting}
while (UART0_STATE & UART_STATE_TXBF) 
{
    /* wait until TXBF is 0 */
}
\end{lstlisting}

Without intervention, the compiler's optimizer analyzes this snippet and notices that \texttt{UART0\_STATE} is never modified inside the loop body[cite: 105]. It concludes the value "cannot change"[cite: 105]. The compiler will read the value exactly once before the loop; if the condition is true, it optimizes the code into an infinite spin loop, completely removing all subsequent hardware reads[cite: 105]. If the condition is false, it might remove the snippet entirely[cite: 105].

To prevent this catastrophic optimization, the \texttt{volatile} keyword is absolutely mandatory when accessing device registers[cite: 105]. It explicitly tells the compiler that the value at this memory address can change without any software action[cite: 105]. It forces the compiler to ensure that \textbf{every read and every write in the source code must really happen}, exactly in the order written, and must never be cached or optimized away[cite: 105].

\subsection{Try It: \texttt{volatile} at \texttt{-O2}}
To truly see how the compiler can delete hardware reads, you can examine the generated assembly code[cite: 106]. Consider a C file (\texttt{poll.c}) with the following polling loop:

\begin{lstlisting}
#include <stdint.h>
#ifndef QUAL
#define QUAL /* empty: a plain pointer */
#endif

/* UART0_STATE, bit 0 = TXBF (Transmit Buffer Full) */
#define UART0_STATE (*(QUAL uint32_t *)0x40004004u)

void wait_tx_room(void)
{
    while (UART0_STATE & 1) 
    {
        /* wait until TXBF is 0 */
    }
}
\end{lstlisting}

If you compile this twice with optimization level \texttt{-O2} (once normally, and once with \texttt{-DQUAL=volatile}) and inspect the output using \texttt{objdump -d}, you will see a drastic difference[cite: 106, 107]:

\begin{itemize}
    \item \textbf{Without \texttt{volatile} (\texttt{plain.o}):} The compiler emits a single \texttt{ldr} instruction to read the state register \texttt{before} the loop[cite: 107]. Inside the loop body, it simply branches back to itself (\texttt{b.n}) infinitely without ever issuing another \texttt{ldr}[cite: 107]. If the hardware buffer was full on that first read, the program hangs forever[cite: 107].
    \item \textbf{With \texttt{volatile} (\texttt{vol.o}):} The branch at the bottom of the loop explicitly jumps back to the \texttt{ldr} instruction[cite: 107]. The CPU physically reads the hardware register \texttt{UART0\_STATE} on every single iteration of the loop[cite: 107].
\end{itemize}

Warning: At optimization level \texttt{-O0} (which our Makefile currently uses), the plain version happens to re-read the register anyway[cite: 107]. This means a missing \texttt{volatile} bug will hide perfectly until you turn on optimizations for a release build, at which point the system will catastrophically freeze[cite: 107]. Always use \texttt{volatile} for hardware registers[cite: 107].

\section{Read-Modify-Write Needs Care}
When configuring a device, you often need to change a single bit while leaving the rest of the register intact. In C, this is commonly written using combined assignment operators, like the bitwise OR assignment:

\begin{lstlisting}
CMSDK_GPIO0->DATAOUT |= (1 << 3); /* set pin 3 */
\end{lstlisting}

While this looks like a single line of C code, at the hardware level, it compiles into three distinct operations[cite: 108]:
\begin{enumerate}
    \item \textbf{Read:} Load the current value of the register from memory into a CPU register.
    \item \textbf{Modify:} Perform the bitwise OR operation.
    \item \textbf{Write:} Store the modified value back to the hardware memory address.
\end{enumerate}

These three operations are \textbf{not atomic}[cite: 108]. This introduces several dangerous hardware pitfalls[cite: 108]:
\begin{itemize}
    \item \textbf{Concurrency conflicts:} If an interrupt fires or the hardware autonomously changes a different bit in the register between your read and your write, your subsequent write will forcefully overwrite the hardware's changes with outdated data[cite: 108].
    \item \textbf{Write-1-to-clear (W1C) bits:} Certain status registers clear their flags when you write a 1 to them, leaving them alone if you write a 0[cite: 108]. Using a read-modify-write pattern on a W1C register is disastrous: it reads back all currently set flags (as 1s) and writes them straight back, accidentally clearing every pending interrupt flag[cite: 108].
    \item \textbf{Read $\neq$ Written:} Some registers return different values when read compared to what was written[cite: 108]. Reading and writing back such a register can unintentionally scramble bits you did not mean to touch[cite: 108].
\end{itemize}

\subsection{Safer Hardware Patterns}
To avoid these pitfalls[cite: 108]:
\begin{itemize}
    \item \textbf{Set / Clear Registers:} Many modern peripherals provide dedicated registers strictly for setting or clearing bits (e.g., \texttt{OUTENABLESET})[cite: 108]. Writing \texttt{CMSDK\_GPIO0->OUTENABLESET = 1u << 3;} is a single write operation; the hardware ensures that only the bits set to 1 are modified[cite: 108].
    \item \textbf{W1C Registers:} Always use a plain assignment (\texttt{=}) containing only the specific bit you want to clear[cite: 108]. Never use \texttt{|=}[cite: 108].
    \item \textbf{Unavoidable Read-Modify-Write:} If a read-modify-write is strictly required, ensure that no other code or interrupts can touch the register during the operation (which we will learn to handle gracefully later in the course)[cite: 108].
\end{itemize}

\section{The Device Protocol and the Driver Concept}
Interacting with a hardware device is not just about flipping bits randomly; it requires following a strict state machine protocol dictated by the device's manual[cite: 109]. 

The lifecycle typically follows these steps[cite: 109]:
\begin{enumerate}
    \item \textbf{Configure:} Set up operational parameters (e.g., setting the UART baud rate). Hardware designers usually ensure that devices boot in a disabled, uninitialized state to prevent unpredictable behavior at power-on[cite: 109].
    \item \textbf{Enable:} Switch on the necessary circuits (e.g., turning on the transmitter)[cite: 109].
    \item \textbf{Check Status:} Verify the device is ready (e.g., checking if the transmit buffer has room)[cite: 109].
    \item \textbf{Move Data:} Send or receive the actual payload data[cite: 109].
    \item \textbf{Acknowledge:} Clear any relevant event flags so the hardware can report the next event[cite: 109].
\end{enumerate}

\subsection{What is a Device Driver?}
As operating system designers, our role is to absorb this hardware complexity. The software layers above us (like user applications) should not need to know memory addresses, bitmasks, or hardware protocols.

A \textbf{device driver} is the specialized code that intimately knows a specific device's registers and protocol[cite: 111]. It acts as an API boundary, offering the rest of the system simple functions with clear meanings (e.g., "send this byte")[cite: 111]. Callers include the driver's header file (\texttt{drivers/uart.h}), but they never directly include \texttt{cmsdk.h}[cite: 111]. Only the driver touches the raw hardware registers[cite: 111].

\section{Writing the UART Driver}
We will build a UART driver because the emulated UART is physically connected to the QEMU terminal. By driving this hardware properly, we can implement a real \texttt{printf} function, replacing the artificial semihosting debug trick from Week 2.

The driver API will start small and simple[cite: 111]:
\begin{lstlisting}
void uart_init(void);               /* Set up UART0; called once at boot */
void uart_putc_polled(char c);      /* Send one byte; waits if buffer is full */
int uart_getc_polled(void);         /* Get a byte, or -1 if none is waiting */
\end{lstlisting}

This initial driver will be \textbf{polled}, meaning it reads the hardware status register in a loop to determine if it can send or receive data, without using interrupts[cite: 111].

\subsection{The CMSDK UART Registers}
To control the UART and implement our driver, we must intimately understand the meaning of its hardware registers as defined by its specifications[cite: 110]. 

The CMSDK UART features the following primary registers[cite: 110]:
\begin{itemize}
    \item \textbf{\texttt{0x00 DATA} (R/W):} This is the data register. Writing a byte to this address physically instructs the UART to transmit it[cite: 110]. Reading from it extracts the received byte[cite: 110].
    \item \textbf{\texttt{0x04 STATE} (R, W1C):} This register reports the current status of the device[cite: 110]. It contains critical bits such as:
    \begin{itemize}
        \item \textbf{Bit 0 (\texttt{TXBF}):} Transmit Buffer Full. If this is 1, the device is still sending the last byte; any new write to \texttt{DATA} will be lost[cite: 110].
        \item \textbf{Bit 1 (\texttt{RXBF}):} Receive Buffer Full. If this is 1, a byte is waiting to be read[cite: 110].
    \end{itemize}
    Because QEMU pulls characters from the UART and prints them to our terminal much slower than our CPU executes instructions, our software must actively check these bits and wait before pushing new data.
    \item \textbf{\texttt{0x08 CTRL} (R/W):} The control register. This allows us to enable or disable the transmitter (\texttt{TXEN}) and receiver (\texttt{RXEN}), and configure interrupts[cite: 110]. For the first part of this week, we will leave interrupts disabled.
    \item \textbf{\texttt{0x10 BAUDDIV} (R/W):} The transmission rate divider[cite: 110].
\end{itemize}

\subsubsection{Configuring the Baud Rate}
Because UART is asynchronous (there is no shared clock), both devices must agree on a specific transmission speed, known as the \textbf{baud rate} (bits per second)[cite: 102]. If you have ever connected an Arduino to a PC using a program like PuTTY, you had to manually set the baud rate so the two independent devices could understand each other.

To configure this in hardware, you must divide your CPU's clock frequency by your target baud rate. For example, if our board's CPU runs at 25 MHz and we want to transmit at 115,200 baud, we compute[cite: 110]:
\[ \text{BAUDDIV} = \frac{25,000,000}{115,200} \approx 217 \]

Writing 217 into the \texttt{BAUDDIV} register configures the UART correctly[cite: 110]. However, because we are using QEMU, the emulator ignores the baud rate and prints instantly[cite: 110]. Therefore, our driver simply writes \texttt{16} (the smallest legal value permitted by the architecture) into this register[cite: 110].

\section{Implementing the Device Driver}
A device driver is essentially a set of high-level functions that implement low-level hardware operations. While complex operating systems like Linux enforce strict standards on how a driver must be written, we are building our own OS and have the freedom to design it ourselves[cite: 112].

Our initial polled driver requires three simple C functions[cite: 111]:
\begin{enumerate}
    \item An \texttt{init} function to initialize the UART[cite: 111].
    \item A \texttt{write} function to send a character[cite: 111].
    \item A \texttt{read} function to receive a character[cite: 111].
\end{enumerate}

\subsection{How Bigger OSes Generalize a Driver}
If you want to design an elegant OS architecture, defining plain functions is often not enough. If a system has many different devices of the same category (e.g., character devices like UARTs and keyboards), the OS needs a generic way to talk to them without caring about the underlying hardware[cite: 112].

Operating systems solve this by defining a \texttt{struct} composed entirely of function pointers[cite: 112]. 

\begin{lstlisting}
struct char_driver 
{
    void (*init)(void);          /* bring the device up */
    int  (*read)(void);          /* read one byte, or -1 if none */
    void (*write)(char c);       /* send one byte */
};
\end{lstlisting}

To write a new device driver, the developer implements the low-level functions and then populates an instance of this structure[cite: 112]:

\begin{lstlisting}
static const struct char_driver uart0_driver = { 
    uart_init, 
    uart_getc_polled, 
    uart_putc_polled 
};
\end{lstlisting}

This allows the higher-level kernel code to interact generically with any device[cite: 112]:
\begin{lstlisting}
void say_hi(const struct char_driver *dev) 
{ 
    dev->write('h'); 
    dev->write('i'); 
}
\end{lstlisting}

This is exactly how Linux manages drivers (using \texttt{struct file\_operations}). For our minimal OS, we will call our UART functions directly, but understanding this architectural pattern is crucial for OS design[cite: 112].

\subsection{Try It: The First UART Byte}
We will now implement the polled driver in \texttt{drivers/uart.c}. 

First, we implement the initialization function[cite: 113]. Following the hardware protocol, we must configure the speed and explicitly enable the transmitter and receiver circuits[cite: 113]. If we attempt to write data while the UART is disabled (because \texttt{CTRL} defaults to 0 at reset), the UART will completely drop the byte, and QEMU will report a guest error[cite: 115].

\begin{lstlisting}
#include "drivers/uart.h"
#include "cmsdk.h"

void uart_init(void)
{
    /* configure: speed (QEMU ignores it, but 16 is the minimum) */
    CMSDK_UART0->BAUDDIV = 16;
    
    /* enable: transmitter and receiver */
    CMSDK_UART0->CTRL = UART_CTRL_TXEN | UART_CTRL_RXEN;
}
\end{lstlisting}

Next, we implement the polled transmission function[cite: 113]. Before moving data, we must actively check the hardware status. The function reads the \texttt{STATE} register in a \texttt{while} loop until the \texttt{TXBF} (Transmit Buffer Full) bit clears. Once there is room, it moves the data by writing to the \texttt{DATA} register[cite: 113].

\begin{lstlisting}
void uart_putc_polled(char c)
{
    /* check status: wait for room */
    while (CMSDK_UART0->STATE & UART_STATE_TXBF) 
    { 
        /* spin */ 
    }

    /* move data: send the byte */
    CMSDK_UART0->DATA = (uint32_t)(unsigned char)c;
}
\end{lstlisting}

By calling \texttt{uart\_init()} and \texttt{uart\_putc\_polled()} from \texttt{main.c}, we can establish the first real hardware output of our operating system[cite: 114].

\subsection{Structuring the Driver Files}
To properly organize our operating system, every device driver is typically separated into its own header (\texttt{.h}) and implementation (\texttt{.c}) file.

\begin{itemize}
\item \textbf{\texttt{drivers/uart.h}:} This header file defines the API boundary. It contains only the prototypes of the functions we want to expose to the rest of the OS (e.g., \texttt{uart\_init}, \texttt{uart\_putc\_polled}, and \texttt{uart\_getc\_polled}).
\item \textbf{\texttt{drivers/uart.c}:} This file contains the actual C implementation. Crucially, it must include both its own header (\texttt{uart.h}) and the hardware definitions (\texttt{cmsdk.h}).
\end{itemize}

By including \texttt{cmsdk.h} strictly inside the \texttt{.c} file, we abstract the hardware addresses away from the rest of the system. If the underlying hardware changes, we only need to update the CMSDK layer and the driver's \texttt{.c} file; every higher-level application built on top of this driver will continue to compile and work perfectly without modification.

\subsection{Step-by-Step Implementation}
Let us break down the exact C implementation of these operations.

\subsubsection{1. Initialization}
The first function we implement is \texttt{uart\_init}. Based on the hardware protocol, we must configure the speed and explicitly enable the device.

\begin{lstlisting}
void uart_init(void)
{
/* Configure the transmission speed (baud rate divider) */
CMSDK_UART0->BAUDDIV = 16;

/* Enable both transmitter and receiver using a bitwise OR */
CMSDK_UART0->CTRL = UART_CTRL_TXEN | UART_CTRL_RXEN;

}
\end{lstlisting}

We use a logical bitwise OR (\texttt{|}) to combine two bitmasks: one that sets the transmission bit to 1, and one that sets the receiving bit to 1. This single assignment enables both data directions simultaneously.

\subsubsection{2. Polled Transmission}
Next, we implement \texttt{uart\_putc\_polled} to write a character to the UART line. Because we are using polling, we rely on a busy-waiting loop.

\begin{lstlisting}
void uart_putc_polled(char c)
{
/* Check status: Wait until the transmission buffer has an empty slot */
while (CMSDK_UART0->STATE & UART_STATE_TXBF)
{
/* Busy waiting */
}

/* Move data: Write the character to the data register */
CMSDK_UART0->DATA = (uint32_t)(unsigned char)c;

}
\end{lstlisting}

If the \texttt{TXBF} (Transmit Buffer Full) bit is 1, the UART is not ready to receive new data, so the CPU loops infinitely, waiting. Once the buffer is free, the loop exits, and we perform a store operation. We copy the character into the \texttt{DATA} memory address. At this point, the character is handed off to the UART hardware, and the CPU does not care about it anymore.

\subsection{Using the Driver as an Application Designer}
Now that the low-level device driver is written, we can switch roles to become an application software designer. We go into our \texttt{src/main.c} program and include the device driver by including \texttt{uart.h}. \textit{Notice that \texttt{main.c} does not include \texttt{cmsdk.h}; it only uses the high-level API.}

\begin{lstlisting}
#include "drivers/uart.h"

int main(void)
{
/* 1. Initialize the driver */
uart_init();

/* 2. Print characters using the hardware */
uart_putc_polled('O');
uart_putc_polled('K');
uart_putc_polled('\n');

for (;;) { }

}
\end{lstlisting}

When we execute these functions, we are sending characters to an external physical device (the UART). The UART transmits them through a serial line to the receiving device. In our emulation environment, QEMU acts as the receiving computer, capturing whatever is transmitted on that serial line and physically printing it to your screen.

\texttt{Troubleshooting Note:} What happens if you comment out the \texttt{uart\_init()} call in \texttt{main}? Because the \texttt{CTRL} register defaults to \texttt{0} at hardware reset, the transmitter remains strictly off. The UART will drop every byte written to the \texttt{DATA} register. Running QEMU with the \texttt{-d guest\_errors} flag will explicitly report: \texttt{CMSDK APB UART: transmit data write with Tx disabled}.

\subsection{The Reality of Hardware Printing}
When you run the code and see \texttt{OK} printed on the screen, it is crucial to understand that this is \textbf{not} the same mechanism we used last week. Last week, we used a semihosting debug trick that halted the CPU and asked the QEMU emulator to print on our behalf. Now, we are performing real hardware communication: the CPU is writing data bits directly into a hardware register, and the UART peripheral is transmitting those bits over a serial line to QEMU's terminal.

\texttt{Architectural note on initialization:} A common question is how many times the UART must be initialized if the project grows to multiple C files. Because the UART is an external physical device, you only initialize it \texttt{once} at boot (typically in \texttt{main}). Since our operating system currently only has a single process, that single initialization serves the entire system. If we eventually add multiple processes or need to dynamically change the baud rate, we might reinitialize it, but normally, hardware initialization is a one-time setup.

\subsection{Try It: A Polled Echo}
We have implemented transmission, but the UART is a bidirectional interface. We need the opposite operation: receiving data. In the QEMU environment, the UART's output is connected to your terminal screen, and its input is physically connected to your keyboard.

We add a reading function to our device driver (\texttt{drivers/uart.c}). Because this is a polled driver, if there is no character waiting, the function must not freeze; it should simply return \texttt{-1} immediately:

\begin{lstlisting}
int uart_getc_polled(void)
{
/* Check status: if the Receive Buffer is empty, return -1 */
if ((CMSDK_UART0->STATE & UART_STATE_RXBF) == 0)
{
return -1;
}

/* Move data: reading DATA automatically extracts the byte */
return (int)(CMSDK_UART0->DATA & 0xFF);

}
\end{lstlisting}

Now, we can update our \texttt{main.c} to utilize this new capability. We replace the empty infinite loop with an echo loop:

\begin{lstlisting}
for (;;)
{
int c = uart_getc_polled();
if (c >= 0)
{
uart_putc_polled((char)c);
}
}
\end{lstlisting}

When you run \texttt{make run} and type on your keyboard, you will see the \texttt{OK} banner, followed by whatever you type. (With the \texttt{-nographic} flag, the terminal itself does not show your keystrokes; every letter you see on the screen was explicitly sent back by your hardware echo loop).

This loop highlights the massive performance penalty of \textbf{polling}. The CPU spins in this infinite loop, executing millions of useless checks per second even when you are not pressing any keys. We will solve this inefficiency using interrupts later in this unit.

\section{Variadic Functions and \texttt{<stdarg.h>}}
Currently, our driver can only print single characters. To build a true operating system, we need a \texttt{printf}-like function capable of formatting complex strings and numbers (e.g., \texttt{\%d}, \texttt{\%s}, \texttt{\%x}). We will call our kernel-level version \texttt{kprintf}.

To build \texttt{kprintf}, we face two tasks:
\begin{enumerate}
\item String formatting (parsing the \texttt{\%d} markers and converting integers to ASCII characters).
\item Sending the resulting characters to the UART.
\end{enumerate}

In C, a function that accepts an arbitrary number of arguments (like \texttt{printf}) is called a \textbf{variadic function}. It is declared using an ellipsis (\texttt{...}):

\begin{lstlisting}
void kprintf(const char *fmt, ...);
\end{lstlisting}

Because we are compiling in a freestanding environment without the standard library (\texttt{<stdio.h>}), we must format the string ourselves. Fortunately, the C compiler still provides the \texttt{<stdarg.h>} header. This header contains no library executable code; it only provides the compiler built-in macros (\texttt{va\_list}, \texttt{va\_start}, \texttt{va\_arg}, \texttt{va\_end}) required to iterate sequentially through the unknown extra arguments.

\begin{lstlisting}
#include <stdarg.h>

void kprintf(const char *fmt, ...)
{
va_list ap;              /* a cursor over the extra arguments */
va_start(ap, fmt);       /* start the cursor right after 'fmt' */

/* Formatting logic goes here using va_arg(ap, type) */

va_end(ap);              /* done */

}
\end{lstlisting}

\texttt{Warning:} Variadic functions inherently lack type safety. The function cannot automatically detect how many arguments were passed or what type they are. It strictly trusts the format string; if you specify \texttt{\%d} but pass a string pointer, the compiler cannot catch the error, resulting in undefined behavior.

\subsection{Separating Formatting from Output (\texttt{vformat})}
The logic required to parse a format string (like converting the integer \texttt{42} into the ASCII characters \texttt{'4'} and \texttt{'2'}) is pure C programming[cite: 118]. This formatting logic is completely independent of where the characters are physically sent[cite: 118]. 

To maintain a clean operating system architecture, we separate the formatting engine from the hardware driver using a function called \texttt{vformat} (implemented in \texttt{lib/format.c})[cite: 118]. 

\begin{lstlisting}
void vformat(void (*out)(char c, void *ctx), void *ctx, const char *fmt, va_list ap);
\end{lstlisting}

Instead of calling the UART directly, \texttt{vformat} accepts a function pointer named \texttt{out}[cite: 118]. It parses the string and calls \texttt{out(c, ctx)} exactly once for every character generated[cite: 118]. This means the exact same formatting code can be reused whether the OS is printing to a serial port, drawing to a screen, or simply writing to a memory buffer[cite: 118]. 

\section{The Kernel Print Function (\texttt{kprintf})}
With the formatting engine and the UART driver both ready, we can combine them to create a real print function. We name it \textbf{\texttt{kprintf}} (where the "k" stands for kernel)[cite: 118]. 

\subsection{Kernel Mode vs. User Mode Printing}
Naming this function \texttt{kprintf} highlights a fundamental operating system concept. In a real OS (like Linux), there is a strict separation between how the kernel prints messages and how a user application prints messages:
\begin{itemize}
    \item \textbf{User-Level \texttt{printf}:} A user application runs in a restricted user mode. It does not know that a UART even exists, nor does it have the hardware privileges to touch it. When a user program calls \texttt{printf}, it triggers a \texttt{system call}, asking the OS to print on its behalf. The OS then securely routes that request to the appropriate device driver.
    \item \textbf{Kernel-Level \texttt{kprintf}:} The OS kernel itself runs in privileged (supervisor) mode. It inherently knows about the hardware and the I/O devices. Therefore, \texttt{kprintf} bypasses system calls entirely and talks directly to the hardware driver.
\end{itemize}

Any operating system that implements hardware protection features both a user-side print function and a kernel-side print function. We are currently inside the operating system layer, so we implement \texttt{kprintf} first. (The more complex user-level system call mechanism will be implemented later).

\subsection{Implementing \texttt{kprintf}}
In \texttt{kernel/kprintf.c}, we write a small wrapper function that connects \texttt{vformat} to our polled UART driver[cite: 122].

First, we define the callback function that \texttt{vformat} expects. This simply takes a character and hands it to the driver[cite: 122]:

\begin{lstlisting}
#include "kernel/kprintf.h"
#include "lib/format.h"
#include "drivers/uart.h"

/* vformat's output callback: sends one char to the UART */
static void kprintf_out(char c, void *ctx)
{
    (void)ctx; /* Context is unused here */
    uart_putc_polled(c);
}
\end{lstlisting}

Then, we implement the variadic \texttt{kprintf} function itself. It initializes the argument list using the \texttt{<stdarg.h>} macros, passes our \texttt{kprintf\_out} callback to \texttt{vformat}, and cleans up when finished[cite: 122]:

\begin{lstlisting}
void kprintf(const char *fmt, ...)
{
    va_list ap;
    va_start(ap, fmt);
    
    /* Pass the formatting work to vformat, targeting the UART */
    vformat(kprintf_out, 0, fmt, ap);
    
    va_end(ap);
}
\end{lstlisting}

Because \texttt{kprintf} relies on our polled UART driver, it operates entirely without hardware interrupts[cite: 118]. This is a massive architectural advantage: it means \texttt{kprintf} can be safely executed anywhere in the kernel, even inside a catastrophic \texttt{HardFault} handler where interrupts are strictly disabled[cite: 118].

\textit{Implementation note: To follow along with the codebase, you can copy the fully implemented \texttt{lib/format.c} and \texttt{kernel/kprintf.c} files directly from the solution folder into your working directory.}

\section{Upgrading the Kernel: Fault Handlers That Print}
Now that we have successfully built a working device driver and a robust \texttt{kprintf} function, we can put them to use inside the kernel. 

Recall from Week 2 that we configured the CPU's vector table with specific exception handlers (like \texttt{HardFault\_Handler} and \texttt{UsageFault\_Handler}). In that initial implementation, these handlers were completely silent: they consisted of nothing more than an infinite \texttt{while(1)} loop. If a hardware fault occurred, the system simply locked up, leaving the developer completely blind to the cause.

Because our new \texttt{kprintf} function relies strictly on a polled driver, it does not require interrupts to function[cite: 118]. This means it can safely execute even inside a catastrophic hardware fault handler where normal system interrupts are masked[cite: 125]. We can now replace the silent loops with handlers that actively print the exact reason for the crash[cite: 123].

\subsection{The Status Registers (\texttt{HFSR} and \texttt{CFSR})}
When an exception arises, the Cortex-M hardware automatically records the specific reason for the crash into dedicated system registers[cite: 124]. You do not need to memorize these addresses by heart; instead, we access them cleanly through the data structures we mapped earlier (via the \texttt{SCB} pointer in our CMSDK headers).

The two critical registers we want to read are[cite: 124]:
\begin{itemize}
    \item \textbf{\texttt{CFSR} (Configurable Fault Status Register):} Located at \texttt{0xE000ED28}, this register contains one bit for every specific cause of a MemManage, BusFault, or UsageFault[cite: 124].
    \item \textbf{\texttt{HFSR} (Hard Fault Status Register):} Located at \texttt{0xE000ED2C}, this indicates exactly why a HardFault was escalated[cite: 124].
\end{itemize}

\subsection{Implementing the New Handlers}
In \texttt{kernel/faults.c}, we first define a generic \texttt{halt} helper function that implements the infinite loop[cite: 123]. Then, we override the weak default handlers by defining strong C functions that print the contents of these status registers before halting the CPU[cite: 123]:

\begin{lstlisting}
#include "cmsdk.h"
#include "kernel/kprintf.h"

/* Stop here forever. */
static void halt(void)
{
    for (;;) { }
}

void HardFault_Handler(void)
{
    kprintf("HardFault: HFSR=0x%x\n", SCB->HFSR);
    halt();
}

void MemManage_Handler(void)
{
    kprintf("MemManage: CFSR=0x%x\n", SCB->CFSR);
    halt();
}

void BusFault_Handler(void)
{
    kprintf("BusFault: CFSR=0x%x\n", SCB->CFSR);
    halt();
}

void UsageFault_Handler(void)
{
    kprintf("UsageFault: CFSR=0x%x\n", SCB->CFSR);
    halt();
}
\end{lstlisting}

\subsection{Try It: Catching a Divide-By-Zero}
We can immediately test if our new fault handlers work by intentionally crashing the OS[cite: 124]. 

In Week 2 (\texttt{Step 7}), we configured the CPU's \texttt{CCR} (Configuration and Control Register) to actively trap division by zero by setting the \texttt{DIV\_0\_TRP} bit. To test this, add the following code into \texttt{main.c} right after your banner print[cite: 124]:

\begin{lstlisting}
volatile unsigned zero = 0;   /* Use volatile to force a runtime read */
kprintf("%u\n", 10u / zero);  /* This should trigger a hardware fault */
\end{lstlisting}

If you compile and run the project (\texttt{make run}), the program will halt and output the following to your terminal[cite: 125]:

\begin{lstlisting}
UsageFault: CFSR=0x2000000
\end{lstlisting}

This output perfectly validates our entire architecture. The value \texttt{0x2000000} indicates that bit 25 of the \texttt{CFSR} is set[cite: 125]. If you check the hardware manual (or the \texttt{SCB\_CFSR\_DIVBYZERO} macro in \texttt{cmsdk.h}), bit 25 explicitly means "Divide by Zero"[cite: 125]. 

The sequence of events was:
\begin{enumerate}
    \item The CPU detected the illegal division and instantly fired a \texttt{UsageFault}.
    \item The CPU jumped to our custom \texttt{UsageFault\_Handler}.
    \item The handler successfully used the polled \texttt{kprintf} to push the error string byte-by-byte through the UART hardware to QEMU's terminal.
    \item The handler called \texttt{halt()}, safely freezing the system.
\end{enumerate}

\subsection{The Limitations of Polling}
While polling is simple to implement and works perfectly in restricted environments (like inside a \texttt{HardFault} handler where interrupts are strictly disabled), it is highly inefficient for a general-purpose operating system[cite: 127].

\begin{itemize}
    \item \textbf{Wasted CPU Cycles:} A UART transmitting at 115,200 baud requires about 87 microseconds to send a single byte[cite: 127].     \item \textbf{Latency:} The system's response time to a hardware event (like a key press) is limited by how often the CPU explicitly decides to check the register, which can cause lag or dropped inputs[cite: 127].
\end{itemize}

The CPU instantly pauses its current task, jumps to a specific Exception Handler to service the device, and then seamlessly resumes its previous task[cite: 127].

While interrupts solve the CPU waste problem entirely, they introduce significant software complexity[cite: 127]. \section{Polling vs. Interrupts: A Conceptual Overview}
To fully appreciate why we must transition our architecture away from polling, we can use a real-world analogy. 

Consider the interaction between a student and a professor regarding the start date of a university project:
\begin{itemize}
    \item \textbf{The Polling Approach:} The student sends the professor an email every single day asking, "When can we start the project?" The professor continuously replies, "You need to wait." The student spends all their time and energy repeatedly asking the same question until, finally, the professor says, "You can start tomorrow." This is exactly how our current UART driver works: the CPU constantly asks the \texttt{STATE} register if it is ready, wasting millions of cycles doing nothing else.
    \item \textbf{The Interrupt Approach:} The student asks the professor once: "Can you let us know when the project starts?" The student then relaxes, goes out with friends, and enjoys their life. They do absolutely no waiting. One day, the student receives an email notification (the hardware interrupt) stating the project has started. The student immediately pauses their social life, handles the new task, and gets to work.
\end{itemize}

For a microprocessor, the interrupt approach means that while a very slow I/O device (like the UART) is transmitting data over a serial line, the CPU is completely free to run other application code or perform background tasks. It is the hardware's responsibility to notify the CPU the exact moment it needs attention.

Interrupt capabilities must be physically designed into the silicon of the peripheral device. Fortunately, standard CMSDK devices—including our UARTs and Timers—are explicitly designed with interrupt lines physically connected to the Cortex-M processor.

\section{Function Calls and the ARM Calling Convention}
Before we can write the software to handle these interrupts, we must deeply understand how the C compiler translates function calls into assembly language. 

When an interrupt fires, the CPU abruptly pauses the currently executing code to jump to an Exception Handler. To ensure that the interrupted code can resume later exactly as if nothing happened, we must guarantee that its working memory (specifically, the CPU registers) is not corrupted by the interrupt handler. 

To manage this, ARM defines a strict set of rules known as the \textbf{AAPCS (ARM Architecture Procedure Call Standard)}. Every compiler (like GCC) strictly follows this standard to ensure that C functions can safely call each other without destroying data.

\subsection{Register Roles in AAPCS}
The AAPCS dictates exactly how the 16 core CPU registers must be used during a function call:

\begin{table}[h!]
\centering
\begin{tabular}{|l|p{0.75\linewidth}|}
\hline
\textbf{Registers} & \textbf{Role defined by AAPCS} \\ \hline
\textbf{R0 - R3} & \textbf{Arguments and Return Values.} When calling a function, the first four arguments are placed in these registers. If the function returns a value, it is placed in \texttt{R0} (or \texttt{R0} and \texttt{R1} for 64-bit values). Crucially, these are \textbf{Caller-Saved} registers. A function is completely free to overwrite them without restoring their original values. \\ \hline
\textbf{R4 - R11} & \textbf{Local Variables (Callee-Saved).} These registers are used for long-term local variable storage inside a function. If a function wants to use them, it \texttt{must} save their original values to the stack at the beginning of the function and restore them before returning. The caller expects these to be exactly the same before and after the call. \\ \hline
\textbf{R12} & \textbf{Intra-Procedure Call Scratch Register.} Used primarily by the linker for complex subroutine branching. It is \textbf{Caller-Saved}. \\ \hline
\textbf{R13 (SP)} & \textbf{Stack Pointer.} Points to the top of the current stack. \\ \hline
\textbf{R14 (LR)} & \textbf{Link Register.} Contains the return address. It is \textbf{Caller-Saved}. \\ \hline
\textbf{R15 (PC)} & \textbf{Program Counter.} Points to the currently executing instruction. \\ \hline
\end{tabular}
\end{table}

Understanding the distinction between \texttt{Caller-Saved} (\texttt{R0-R3}, \texttt{R12}, \texttt{LR}) and \texttt{Callee-Saved} (\texttt{R4-R11}) registers is the fundamental key to understanding how Cortex-M processors handle interrupts seamlessly.

\section{Writing Assembly Callable from C}
Why do we need to study the AAPCS calling convention? In an operating system, there are moments when you must go lower than C and write direct assembly instructions. 

If you write a function in pure assembly language and want to call it from your C code, you must manually implement it using the exact same standard the C compiler expects. If you break these rules, your system will crash.

\subsection{Applying the Convention}
Let us analyze how you must prepare an assembly function if you want to call it from C:
\begin{enumerate}
    \item \textbf{Receiving Arguments:} If your C prototype defines arguments (e.g., \texttt{void my\_func(int a, int b);}), you know automatically that \texttt{a} will be sitting in \texttt{R0} and \texttt{b} will be sitting in \texttt{R1} the moment your assembly code begins.
    \item \textbf{Returning Values:} If your function returns an integer, you must physically copy that result into \texttt{R0} before executing the return branch (\texttt{bx lr}).
    \item \textbf{Preserving Variables (Callee-Saved):} If your assembly code is complex and needs to use registers \texttt{R4} through \texttt{R11} to calculate things, you are the "Callee." The standard dictates that you must save these registers to the stack (using \texttt{push}) at the very start of your function, and restore them (using \texttt{pop}) immediately before returning. The C code that called you expects \texttt{R4-R11} to be completely untouched.
    \item \textbf{Scratch Registers (Caller-Saved):} You are completely free to overwrite \texttt{R0-R3} and \texttt{R12} inside your assembly function without restoring them. The C compiler (the "Caller") knows these registers might get destroyed, so it saved anything important before calling you.
    \item \textbf{Stack Alignment:} The AAPCS requires the Stack Pointer (\texttt{SP}) to be 8-byte aligned at all public interfaces. If your stack is misaligned when you call another function, you will trigger hardware faults.
\end{enumerate}

To call a C function \texttt{from} assembly, the logic is reversed: you must put your arguments into \texttt{R0-R3}, save any of your own data that is in \texttt{R0-R3/R12} to the stack, and then use the \texttt{bl} (Branch with Link) instruction to jump to the C function. 

\section{Managing the CPU's Interrupt State}
Before we can use specific hardware interrupts (like the UART), we must write low-level code to manage the CPU's global ability to listen to interrupts.

The Cortex-M CPU has a special hardware register called \textbf{\texttt{PRIMASK}}. This is a 1-bit register. When \texttt{PRIMASK} is set to 1, all configurable interrupts are globally masked (disabled), meaning the CPU will completely ignore them and continue executing its current code. When \texttt{PRIMASK} is set to 0, the CPU will listen to the interrupt lines.

Because \texttt{PRIMASK} is a special CPU core register (not a standard memory-mapped peripheral), it cannot be accessed using standard C variable assignments. It must be accessed using two specific assembly instructions:
\begin{itemize}
    \item \textbf{\texttt{mrs}} (Move to Register from Special register): To read \texttt{PRIMASK}.
    \item \textbf{\texttt{msr}} (Move to Special register from Register): To write to \texttt{PRIMASK}.
\end{itemize}

\subsection{Designing the OS Interrupt API}
As operating system designers, we need to create high-level C functions that wrap these assembly instructions. We could simply write two functions: \texttt{enable\_interrupts()} and \texttt{disable\_interrupts()}. However, this is dangerous in a complex OS.

Imagine a piece of kernel code that needs to briefly disable interrupts to safely update a shared variable, and then re-enable them. If it blindly calls \texttt{disable} and then \texttt{enable}, it assumes interrupts were enabled when it started. But what if this code was called from somewhere where interrupts were \texttt{already} disabled? By blindly calling \texttt{enable} at the end, it breaks the system's expected state.

To solve this, we design a smart API using two functions:
\begin{enumerate}
    \item \texttt{uint32\_t irq\_save(void);}\\
    This function reads the current state of \texttt{PRIMASK}, globally disables interrupts, and returns the old state.
    \item \texttt{void irq\_restore(uint32\_t state);}\\
    This function takes the state we saved earlier and writes it back to \texttt{PRIMASK}, restoring the CPU exactly to whatever state it was in before.
\end{enumerate}

This allows kernel code to safely say: \texttt{"I don't know if interrupts are currently enabled or not, but I want to be completely sure they are disabled right now to do my job safely. When I am done, put the system back exactly how it was."}

\begin{lstlisting}
uint32_t state = irq_save(); /* disable interrupts, save old state */
/* safely modify shared variables here */
irq_restore(state);          /* restore old state */
\end{lstlisting}

\section{Implementing \texttt{irq\_save} and \texttt{irq\_restore} in Assembly}
To practice applying the AAPCS calling convention, we will implement these two functions directly in assembly language. We place this code in a file named \texttt{arch/irq.s}.

\subsection{Implementing \texttt{irq\_save}}
The goal of \texttt{irq\_save} is to read the current \texttt{PRIMASK} state, return it to the caller, and disable interrupts. 

According to the AAPCS, because this C function (\texttt{uint32\_t irq\_save(void);}) takes no arguments but returns a 32-bit integer, we must leave the resulting \texttt{PRIMASK} state strictly inside register \texttt{R0} before we branch back to the caller.

\begin{lstlisting}
    .syntax unified
    .thumb
    .text

    .global irq_save
    .type irq_save, %function
irq_save:
    /* Read PRIMASK into R0 (this is our return value) */
    mrs r0, PRIMASK
    
    /* Disable interrupts (Change Processor State, Interrupt Disable) */
    cpsid i
    
    /* Return to caller. The return value is safely in R0. */
    bx lr
\end{lstlisting}

\texttt{Code Breakdown:}
\begin{itemize}
    \item \texttt{.global irq\_save}: Tells the linker that this symbol should be visible to C code.
    \item \texttt{.type irq\_save, \%function}: Declares this symbol as executable code.
    \item \texttt{mrs r0, PRIMASK}: The \texttt{mrs} instruction copies the special \texttt{PRIMASK} register into a standard register (\texttt{R0}).
    \item \texttt{cpsid i}: This dedicated instruction explicitly sets \texttt{PRIMASK} to 1, immediately masking all configurable interrupts. 
    \item \texttt{bx lr}: Branches back to the address stored in the Link Register, returning execution to C.
\end{itemize}

\subsection{Implementing \texttt{irq\_restore}}
The goal of \texttt{irq\_restore} is to take a previously saved state and write it back to \texttt{PRIMASK}.

According to the AAPCS, because this C function (\texttt{void irq\_restore(uint32\_t state);}) accepts one argument, the compiler will pass that argument to our assembly code strictly in register \texttt{R0}.

\begin{lstlisting}
    .global irq_restore
    .type irq_restore, %function
irq_restore:
    /* Write R0 (our first argument) into PRIMASK */
    msr PRIMASK, r0
    
    /* Return to caller */
    bx lr
\end{lstlisting}

\texttt{Code Breakdown:}
\begin{itemize}
    \item \texttt{msr PRIMASK, r0}: The \texttt{msr} instruction moves the value from \texttt{R0} (the saved state) directly into the special \texttt{PRIMASK} register. If the saved state was 0, interrupts turn back on; if it was 1, they remain disabled.
\end{itemize}

While these could technically be implemented using inline assembly inside a C function, putting them in a dedicated \texttt{.s} file acts as an excellent exercise to prove that C and Assembly can interface perfectly as long as you respect the AAPCS rules.

\subsection{Try It: Testing the API in C}
To use these newly crafted assembly functions, we define their prototypes in \texttt{kernel/irq.h}:

\begin{lstlisting}
#ifndef IRQ_H
#define IRQ_H
#include <stdint.h>

uint32_t irq_save(void);
void irq_restore(uint32_t state);

#endif
\end{lstlisting}

Now we can navigate to our \texttt{main.c} application code, include \texttt{kernel/irq.h}, and test if our assembly functions successfully manipulate the hardware state.

\begin{lstlisting}
#include "drivers/uart.h"
#include "kernel/kprintf.h"
#include "kernel/irq.h"

int main(void)
{
    uart_init();
    
    /* Save current state and disable interrupts */
    uint32_t old_state = irq_save();
    
    /* Right here, we are absolutely sure interrupts are masked. */
    
    /* Restore the state back to what it was */
    irq_restore(old_state);
    
    /* Print the old state to see what it was initially */
    kprintf("PRIMASK before irq_save was: %d\n", old_state);
    
    for (;;) { }
}
\end{lstlisting}

When you compile and execute this, the UART should print: \texttt{PRIMASK before irq\_save was: 0}. This confirms that our boot process successfully started the CPU with interrupts enabled (\texttt{PRIMASK = 0}), and that our custom assembly layer accurately captured and restored that state.

\subsection{The Philosophy of OS Design}
When we ran our test in the previous section, the terminal outputted \texttt{PRIMASK before irq\_save was: 0}. This confirms that the initial state of the interrupt mask was indeed 0 (enabled), our assembly function safely disabled it, and then cleanly restored it.

This pattern reveals the core philosophy of operating system design. We take a complex, highly architecture-specific concept (like manipulating the CPU's \texttt{PRIMASK} using inline assembly), wrap it inside a robust, well-tested C function (\texttt{irq\_save}), and then use that simple wrapper everywhere else. The more you organize your wrappers hierarchically, the easier your job becomes: once the low-level core functions work flawlessly, you build the next layers entirely on top of them without worrying about the underlying hardware mechanics.

\section{ARM Exception Entry and Return Mechanics}
While we can wrap many features in simple C functions, handling exceptions (interrupts) requires a deep understanding of what the Cortex-M hardware does autonomously behind the scenes. 

When a hardware interrupt fires and the CPU pauses the current execution to jump to an Exception Handler, it performs several complex operations automatically:

\subsection{The Automatic Hardware State Save (Stacking)}
To respect the AAPCS calling convention and ensure the interrupted code can resume later seamlessly, the CPU hardware automatically pushes \textbf{eight words} (32 bytes) onto the current stack before executing the very first instruction of your C handler. 
    
These eight words consist of the Caller-Saved registers: \texttt{R0}, \texttt{R1}, \texttt{R2}, \texttt{R3}, \texttt{R12}, the Link Register (\texttt{LR}), the Program Counter (\texttt{PC}), and the Program Status Register (\texttt{xPSR}). If you ever write a low-level exception handler in pure assembly, you must account for the fact that the Stack Pointer (\texttt{SP}) has already been modified by the hardware by the time your code begins.

\subsection{The \texttt{EXC\_RETURN} Value}
In standard C functions, the Link Register (\texttt{LR}) holds the exact memory address to return to when the function finishes. However, when entering an Exception Handler, the CPU hardware overwrites the \texttt{LR} with a special 32-bit code called the \textbf{\texttt{EXC\_RETURN}} value (which always starts with \texttt{0xFFFFFF...}).

This special code is crucial because exceptions can interrupt different execution contexts. For example, an interrupt might happen while the CPU is in User Mode running an application, or it might happen while the CPU is already in Supervisor Mode handling a different, lower-priority exception. 

When the handler finishes and executes a return instruction, the CPU catches this \texttt{0xFFFFFF...} code. Instead of trying to jump to a literal memory address, the CPU decodes it to determine exactly how to return:
\begin{itemize}
    \item Which execution mode to return to (Handler mode vs. Thread mode).
    \item Which stack pointer to restore the eight words from (Main Stack Pointer vs. Process Stack Pointer).
\end{itemize}

While we will rely on the C compiler to generate the correct return instructions for our basic handlers, you must be aware of this mechanism when debugging or writing advanced context-switching code.

\section{The Heartbeat of the OS: The SysTick Timer}
We are now ready to start using hardware interrupts, and we will begin with the most critical device for any operating system: the \textbf{SysTick} timer. 

Unlike external peripherals (like the UART or GPIO), the SysTick timer is built directly into the Cortex-M core itself. Every modern operating system—from our minimal OS up to Linux—relies on this specific hardware timer to give a sense of time to the system.

\subsection{The Necessity of the System Tick}
The OS configures the SysTick timer to generate a hardware interrupt at a fixed, strictly periodic frequency (for example, every 30 milliseconds). But why is this so fundamental?

Imagine running a user application that contains an infinite loop:
\begin{lstlisting}
while(1) 
{ 
    /* do nothing forever */ 
}
\end{lstlisting}
    
If an OS relies entirely on cooperative software (where applications voluntarily yield the CPU back to the kernel), this infinite loop would permanently hijack the CPU. The computer would become completely unresponsive, and the OS would be deadlocked.

The SysTick timer solves this through \textbf{hardware preemption}. Because the timer is a hardware device wired directly to the CPU's interrupt lines, its periodic interrupt will physically force the CPU to pause the infinite loop and jump into the kernel's SysTick Exception Handler. This guarantees that no matter what user applications do, the operating system kernel is physically guaranteed to regain control of the CPU at a fixed interval to perform scheduling and manage the system.

\section{Hardware Preemption and the System Tick}
If a computer's operating system relied entirely on cooperative software—where applications voluntarily yield the CPU back to the kernel—an infinite loop in a user program would permanently hijack the CPU. The computer would become completely unresponsive, and the OS would be deadlocked.

The SysTick timer solves this through \textbf{hardware preemption}. By programming the timer to fire an interrupt periodically (e.g., every 30 milliseconds), the OS ensures that whatever code is currently running on the CPU is forcefully paused. The CPU is then physically forced to jump into the kernel's Exception Handler. 

This guarantees that the operating system kernel regains control of the CPU at fixed intervals. Once inside the kernel, the OS can:
\begin{itemize}
    \item Perform \textbf{scheduling}: give control to different programs fairly so they appear to run in parallel.
    \item Detect if a program has been running for too long and forcefully terminate it.
    \item Maintain the system clock by tracking how many ticks have occurred since boot.
\end{itemize}

A hardware interrupt is the \texttt{only} mechanism powerful enough to definitively stop the CPU and guarantee that the operating system can perform its tasks.

\subsection{The SysTick Hardware Registers}
The SysTick timer is a small piece of hardware mapped into memory. Like the UART, its registers are already mapped into a C data structure in our CMSDK headers (\texttt{SysTick\_Type}).

The primary registers are:
\begin{itemize}
    \item \textbf{\texttt{0x10 SYST\_CSR}:} Control and Status Register. Used to enable the timer and its interrupt.
    \item \textbf{\texttt{0x14 SYST\_RVR}:} Reload Value Register. This dictates the frequency of the tick.
    \item \textbf{\texttt{0x18 SYST\_CVR}:} Current Value Register. The actual counting mechanism.
\end{itemize}

To configure the timer to fire exactly every $T$ milliseconds, you must consult the manual and calculate the reload value based on your CPU's clock frequency. For our board running at 25 MHz, firing an interrupt every 10 milliseconds requires programming \texttt{SYST\_RVR} with the value \texttt{249,999}. While the exact calculation changes depending on the specific board, the architectural concept remains identical across all Cortex-M devices.

\section{Building the SysTick Driver}
To integrate this hardware into our OS, we write a device driver just like we did for the UART. 

\subsection{The API Definition (\texttt{systick.h})}
The driver API exposes initialization and time-tracking functions, as well as the prototype for the hardware interrupt handler itself:

\begin{lstlisting}
void systick_init(unsigned int period_ms);
unsigned int systick_get(void);
void SysTick_Handler(void); /* The actual interrupt handler */
\end{lstlisting}

\subsection{The Implementation (\texttt{systick.c})}
Inside the C file, we need a global variable to track the number of ticks that have occurred since the system booted.

\begin{lstlisting}
#include "drivers/systick.h"
#include "cmsdk.h"

#define SYSTEM_CORE_CLOCK 25000000

/* Global counter to track ticks since boot */
static volatile unsigned int systick_counter = 0;
\end{lstlisting}

The initialization function computes the correct reload value mathematically and configures the hardware:

\begin{lstlisting}
void systick_init(unsigned int period_ms)
{
    /* Compute reload value based on CPU clock speed */
    unsigned int reload = (SYSTEM_CORE_CLOCK / 1000) * period_ms - 1;
    
    SysTick->LOAD = reload;
    SysTick->VAL  = 0;
    
    /* Enable the timer and its interrupt line */
    SysTick->CTRL = SysTick_CTRL_CLKSOURCE_Msk | 
                    SysTick_CTRL_TICKINT_Msk | 
                    SysTick_CTRL_ENABLE_Msk;
}
\end{lstlisting}

We then provide a simple getter function so the rest of the kernel can ask what time it is (in ticks):

\begin{lstlisting}
unsigned int systick_get(void)
{
    return systick_counter;
}
\end{lstlisting}

\subsection{The Exception Handler}
Finally, we must implement the code that actually runs when the hardware interrupt fires. The \texttt{SysTick\_Handler} function increments our global counter. Because this is a hardware exception, it also serves as an excellent place to prove the system is working by printing a message:

\begin{lstlisting}
#include "kernel/kprintf.h"

void SysTick_Handler(void)
{
    /* Increment the global tracker */
    systick_counter++;
    
    /* Print a heartbeat message to the terminal */
    kprintf("Tick: %u\n", systick_counter);
}
\end{lstlisting}

\texttt{Crucial Step:} Defining this function is not enough. For the CPU to actually jump to this code, the address of \texttt{SysTick\_Handler} must be correctly placed into the 15th slot of the CPU's Vector Table in our \texttt{boot.s} startup code. If the table is missing this entry, the CPU will jump to the default \texttt{while(1)} loop and the system will freeze on the very first tick.

\subsection{The \texttt{volatile} Variable and the Uptime Calculation}
In our implementation, the variable tracking the number of ticks must absolutely be declared as \texttt{volatile}. 

Because the main CPU thread never writes to this variable (it only reads it via the getter function), the C compiler's optimizer will assume its value never changes. Without \texttt{volatile}, a loop waiting for the time to reach a certain value would be optimized into an infinite spin lock. The \texttt{volatile} keyword informs the compiler that this variable can be modified at any time by the hardware interrupt handler.

Additionally, in our final implementation, we will track the system \texttt{uptime} in milliseconds rather than raw ticks.

\begin{lstlisting}
static volatile unsigned int systick_uptime_ms = 0;
static unsigned int systick_period_ms = 0;

void systick_init(unsigned int period_ms)
{
    systick_period_ms = period_ms;
    
    unsigned int reload = (SYSTEM_CORE_CLOCK / 1000) * period_ms - 1;
    SysTick->LOAD = reload;
    SysTick->VAL  = 0;
    SysTick->CTRL = SysTick_CTRL_CLKSOURCE_Msk | 
                    SysTick_CTRL_TICKINT_Msk | 
                    SysTick_CTRL_ENABLE_Msk;
}

unsigned int systick_get_ms(void)
{
    return systick_uptime_ms;
}

void SysTick_Handler(void)
{
    systick_uptime_ms += systick_period_ms;
}
\end{lstlisting}

\texttt{Implementation Detail:} The hardware manual specifies a skew of one clock cycle when configuring the reload register. Therefore, the mathematical formula strictly requires subtracting 1 after multiplying by the frequency. Furthermore, the \texttt{SysTick\_CTRL\_CLKSOURCE\_Msk} flag explicitly tells the timer to use the internal CPU clock as its timing source, rather than an external crystal oscillator.

\subsection{Try It: Proving the Hardware Interrupt Works}
To prove that our SysTick timer is functioning and successfully firing interrupts in the background, we can test it in our \texttt{main} application loop.

First, we must include the proper driver headers (\texttt{drivers/systick.h} and \texttt{drivers/uart.h}). Then, we initialize the UART and initialize the SysTick timer to fire an interrupt every 10 milliseconds.

We then enter an infinite loop that simply reads the current uptime and prints it via \texttt{kprintf}.

\begin{lstlisting}
#include "drivers/uart.h"
#include "drivers/systick.h"
#include "kernel/kprintf.h"

int main(void)
{
    uart_init();
    systick_init(10); /* Fire interrupt every 10 ms */
    
    for (;;) 
    {
        kprintf("Uptime: %u ms\n", systick_get_ms());
    }
}
\end{lstlisting}

When you compile and run this code (\texttt{make run}), your terminal will output the uptime value repeatedly. Because \texttt{kprintf} relies on our polled UART driver—which is incredibly slow at transmitting characters over the serial line—the CPU will spend a significant amount of time trapped inside the \texttt{kprintf} logic. 

Despite the CPU being stuck inside an infinite loop continuously running \texttt{kprintf}, the numbers printed on the screen will actively increment (e.g., \texttt{Uptime: 0 ms}, \ldots, \texttt{Uptime: 10 ms}, \ldots, \texttt{Uptime: 20 ms}). 

This proves that every 10 milliseconds, the hardware SysTick timer is forcefully pre-empting the CPU, pausing the \texttt{kprintf} execution, jumping to \texttt{SysTick\_Handler} to increment the \texttt{systick\_uptime\_ms} variable, and then smoothly returning the CPU to exactly where it left off inside \texttt{kprintf}. 

You have successfully built the fundamental hardware beating heart of an operating system. This periodic interrupt will become the foundation of our multitasking scheduler in the upcoming units.

\subsection{A Remark on Emulated Time vs. Real Time}
Before moving on, it is important to note a caveat about running an operating system inside an emulator like QEMU. 

When you run the SysTick test on physical hardware, setting the timer to 10 milliseconds guarantees a hardware interrupt exactly every 10 milliseconds of real-world wall-clock time. In QEMU, the execution is functionally and architecturally perfect: the emulator strictly counts the exact number of Cortex-M3 clock cycles. 

However, QEMU is just a software application running on a host operating system (like Linux or Windows). If your host CPU temporarily pauses QEMU to refresh a web browser or update a presentation, the emulator loses real-world time. Therefore, while the internal logic and register states are perfectly accurate, you cannot rely on QEMU to measure precise real-time hardware performance.

\section{The Nested Vectored Interrupt Controller (NVIC)}
Until now, we have handled the SysTick timer, which is an internal core exception. But what about external peripheral interrupts, like the UART or the timers on the APB bus?

All external hardware interrupts in an ARM Cortex-M processor are centrally managed by a dedicated, memory-mapped I/O device called the \textbf{NVIC (Nested Vectored Interrupt Controller)}.

The NVIC sits between the peripheral devices and the CPU core. It acts as a gatekeeper and priority manager. You control the NVIC by reading and writing to its specific memory-mapped registers:

\begin{itemize}
    \item \textbf{\texttt{ISER} (Interrupt Set-Enable Register):} Used to enable specific interrupt lines. Writing a 1 to bit $N$ enables IRQ line $N$.
    \item \textbf{\texttt{ICER} (Interrupt Clear-Enable Register):} Used to disable specific interrupt lines.
    \item \textbf{\texttt{IPR} (Interrupt Priority Registers):} Used to assign a priority level to each interrupt. If two interrupts fire simultaneously, or if an interrupt fires while the CPU is already handling another one, the NVIC uses these registers to determine which one preempts the other (hence "Nested").
\end{itemize}

\subsection{The Golden Rule of Interrupt Handlers}
When a hardware device requires attention, it asserts its interrupt line. The NVIC detects this, records that the interrupt is \texttt{pending}, and forces the CPU to jump to your handler.

This introduces a critical complexity: \textbf{your software must acknowledge and clear the interrupt reason before returning}. Usually, this means reading the device's data register or writing a 1 to a specific "Interrupt Clear" bit in the device's status register. 

If your handler finishes and executes its return instruction \texttt{without} clearing the hardware flag, the NVIC will see that the line is still asserted. The very microsecond your CPU attempts to return to the main program, the NVIC will instantly fire the interrupt again. Your system will become permanently trapped in an infinite loop of re-entering the exact same interrupt handler, completely starving the rest of the OS.

\section{The Three Gates of Interrupts}
To successfully transition a device like our UART from polling to interrupts, we must coordinate multiple layers of the architecture. An external device's interrupt will only execute its handler if a strict set of conditions—the three gates—are all simultaneously true:

\begin{enumerate}
    \item \textbf{The Device Gate:} The peripheral itself must be configured to generate interrupts. For example, in the UART's \texttt{CTRL} register, you must explicitly set the \texttt{TXINTEN} (Transmit Interrupt Enable) or \texttt{RXINTEN} (Receive Interrupt Enable) bits.
    \item \textbf{The NVIC Gate:} The specific IRQ line connecting that device to the CPU must be unmasked in the NVIC. For UART0 (which lives on IRQ 0 and 1), you must write the corresponding bits in the NVIC's \texttt{ISER} register.
    \item \textbf{The CPU Gate:} The CPU's global interrupt mask (\texttt{PRIMASK}) must be set to 0 (enabled), meaning the core is actively listening to the NVIC.
\end{enumerate}

By mastering these three layers, we unlock the ability to write highly efficient, asynchronous device drivers that let the CPU sleep or run applications while the hardware does the heavy lifting in the background.

\subsection{Shared Interrupt Lines (Q\&A)}
During the lecture, a common question arises: \texttt{Is there strictly one device per interrupt line?}

From the CPU's perspective, an interrupt line is just a single physical wire (a bit). In most commercial Cortex-M boards, hardware designers map exactly one device to one line to keep software simple. However, if a complex board has more peripherals than available NVIC lines, hardware designers might physically wire multiple devices to the same IRQ line. 

If this happens, the CPU hardware has no way of knowing which specific device triggered the line. The software interrupt handler must act as a dispatcher: it must manually read the status registers (poll) of every device sharing that line to figure out who raised the flag, service the correct one, and clear it. While perfectly legal, it reintroduces a layer of polling inside the handler, so it is usually avoided unless hardware pin constraints demand it.

\section{Expanding the Vector Table for External Devices}
To finally make our UART interrupts work, we must connect the hardware signals to our software functions. This requires expanding the CPU's Interrupt Vector Table that we initially created in Week 2.

Recall that the first 16 slots (indices 0 to 15) of the vector table are strictly reserved for the ARM core's internal exceptions (e.g., Initial SP, Reset, HardFault, SysTick). External peripheral interrupts, which are managed by the NVIC, begin immediately after this reserved block. 

Therefore, a device connected to NVIC IRQ line $N$ must have its handler address placed at slot $16 + N$ in the vector table.

\begin{table}[h!]
    \centering
    \begin{tabular}{|l|l|l|}
        \hline
        \textbf{Vector Slot} & \textbf{IRQ Number} & \textbf{Handler / Device} \\ \hline
        15 & -1 & \texttt{SysTick\_Handler} (Core Exception) \\ \hline
        16 & IRQ 0 & \texttt{UART0\_RX\_Handler} (External) \\ \hline
        17 & IRQ 1 & \texttt{UART0\_TX\_Handler} (External) \\ \hline
        18 & IRQ 2 & \texttt{UART1\_RX\_Handler} (External) \\ \hline
    \end{tabular}
\end{table}

To support our UART, we must update our startup code (whether in \texttt{boot.s} or a C-based vector table array) to include the specific addresses of our new handlers:

\begin{lstlisting}
    /* Declare the handler prototypes */
    void SysTick_Handler(void);
    void UART0_RX_Handler(void);
    void UART0_TX_Handler(void);

    /* Inside the vector table array structure: */
    (void *)SysTick_Handler,    /* Slot 15: Core Timer */
    (void *)UART0_RX_Handler,   /* Slot 16: IRQ 0 */
    (void *)UART0_TX_Handler,   /* Slot 17: IRQ 1 */
\end{lstlisting}

With the vector table fully populated, the NVIC configured, the device interrupts enabled, and the CPU's \texttt{PRIMASK} cleared, the hardware is fully armed. The moment a character arrives over the serial line, the CPU will autonomously pause its current task and jump directly to \texttt{UART0\_RX\_Handler}.

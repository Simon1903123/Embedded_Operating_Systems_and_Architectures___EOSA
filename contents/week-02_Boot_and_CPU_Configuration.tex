\section{Introduction to Low-Level CPU Control}
In the previous week, we built a tiny program for a Cortex-M3, ran it in QEMU, and saw it print one line[cite: 101]. Several pieces of that program were handed to us as-is: the linker script that decided where everything goes in memory, and the startup code that ran before \texttt{main()}. We were asked to trust them. This phase is about stopping that trust and building those components from scratch.
By the end of this phase, developers will understand, and will have written, every instruction that the CPU executes between power-on and the first line of \texttt{main()}[cite: 101]. The development process covers knowing where each piece of a C program lives in the chip's memory and why, how the CPU finds its first instruction, how to watch the CPU one instruction at a time with a debugger, how to configure the CPU so that errors are reported clearly instead of silently, and what it means to run C with nothing underneath it (no C library, no operating system)[cite: 101]. Finally, the program will be split into a privileged and an unprivileged part, building the smallest possible version of a system call (\texttt{svc})[cite: 101].

The process is organized into three core units[cite: 101]:
\begin{enumerate}
    \item \textbf{Where code and data live:} The kinds of memory a microcontroller has, the Cortex-M memory map, how the linker script turns that map into decisions, and what the CPU does at reset[cite: 101].
    \item \textbf{Taking control of the CPU:} The debugger, the CPU registers, just enough ARM assembly to read and write boot code, and writing the reset handler step by step (stack, \texttt{.data}, \texttt{.bss}, vector table, fault configuration, priorities)[cite: 101].
    \item \textbf{Life without an OS underneath:} What ``freestanding'' C means, how the program prints without a C library, privileged and unprivileged code, and the \texttt{svc} instruction as a system call[cite: 101].
\end{enumerate}

\subsection{Where You Start and Where You End}
All the in-class work happens on top of a starting skeleton, specifically the folder \texttt{week-02/base/}[cite: 101]. It is derived from the previous week with one major difference: the original C startup code, which did all the setup work, has been thrown away[cite: 101].

The program in \texttt{base/src/main.c} attempts to print two lines[cite: 101]:

    \item \texttt{data\_message}, a global character array initialized with the text \texttt{"main: this text lives in .data\textbackslash{}n"}[cite: 101].

\begin{lstlisting}[language=bash]

By the end of the week, the fully implemented program will print four distinct lines, each serving as evidence that a specific piece of the low-level architecture is in place[cite: 102]:

\section{Memory Technologies in Embedded Systems}
When writing a C program on a standard laptop, developers rarely think about \textit{which} memory their variables reside in. On a microcontroller, this is a critical consideration because the chip contains two very different kinds of memory, and each piece of the program can live in only one of them[cite: 102].

\subsection{SRAM (Static RAM): The Working Memory}
The first kind of memory is \textbf{SRAM} (Static RAM)[cite: 102]. 
\begin{itemize}
    \item \textbf{Direct Bus Connection:} SRAM is connected directly to the CPU's memory bus[cite: 102]. Every byte in it has a specific address, and the CPU reads or writes any byte using ordinary load or store instructions (the same instructions the compiler uses for \texttt{x = y;})[cite: 102].
    \item \textbf{Speed:} It is extremely fast; on a microcontroller, one access typically takes about one clock cycle[cite: 102].
    \item \textbf{Writeability:} You can write to a single byte at any time, as often as you like[cite: 102].
    \item \textbf{Volatility:} Its primary weakness is that it is \textbf{volatile}: when power goes off, its content is completely lost[cite: 102]. Furthermore, when power comes back on, the content is not zero; it is \textbf{undefined}, consisting of a random pattern of bits left by the physical state of the memory cells[cite: 102].
\end{itemize}
Because of these characteristics, SRAM is the designated location for everything that \textit{changes} while the program runs, specifically your variables and the stack[cite: 102].
\subsection{NOR Flash: Execute-in-Place Memory}
The second kind of memory is \textbf{NOR flash}. NOR flash sits on the memory bus, similar to a ROM: every word has a specific address, allowing the CPU to read any of them quickly and in any order. Because of this, the CPU can fetch instructions directly from the flash and execute them right where they are stored, without needing to copy the program into RAM first. This capability is known as \textbf{execute-in-place} (XIP). 

NOR flash is \textbf{non-volatile}, meaning your program remains intact even after the board is unplugged or powered off. The price for these features is paid when writing data. Writing to flash is not a simple store instruction. It requires a two-step process: 

\begin{enumerate}
    \item An entire \textbf{sector} (a block of a few kilobytes) must be \textbf{erased}, setting every bit within it to 1. 
    \item An individual words can be \textbf{programmed}, which only turns bits from 1 to 0.
\end{enumerate}

Both operations take microseconds to milliseconds and require a special command sequence sent to the flash controller. Consequently, for a running program, NOR flash is effectively \textbf{read-only}.

\subsection{Contrasting with NAND Flash and Block Devices}
It is worth contrasting this with the storage technologies commonly found in standard laptops, such as \textbf{NAND flash} (used in SD cards and SSDs) and hard disks. 

These storage devices are \textbf{not} on the memory bus. They are accessed through a controller, one \textbf{block} (or page) at a time (typically 512 bytes to 4 KB). A block has no CPU address. The CPU cannot fetch an instruction from it, nor can it read a single variable directly: the contents must first be copied into RAM and then used from there. 

This is exactly what a desktop operating system does when you start a program: the OS \textbf{loader} copies the executable from the SSD into RAM before running it. A microcontroller, however, has no loader. Its program already sits in NOR flash, at the exact address it runs from.

\subsection{Applying Constraints to C Code}
Put these facts side by side, and you get the rules for a C program on a microcontroller:

\begin{table}[h!]
    \centering
    \begin{tabular}{|l|l|l|l|l|}
        \hline
        \textbf{Technology} & \textbf{On the bus?} & \textbf{Execute from it?} & \textbf{Write at run time?} & \textbf{Keeps data at power-off?} \\ \hline
        SRAM & yes & yes & yes, bytes & no \\ \hline
        NOR flash & yes & yes (XIP) & no (erase/program) & yes \\ \hline
        NAND / disk & no (blocks) & no & through a driver & yes \\ \hline
    \end{tabular}
\end{table}

Based on these constraints:
\begin{itemize}
    \item \textbf{Code and Constants:} Code stays in flash and runs directly from there. Constants (anything declared \texttt{const}, and string literals such as \texttt{"hello"}) also stay in flash and are read in place.
    \item \textbf{Uninitialized Variables:} Variables must live in RAM because they change.
    \item \textbf{Initialized Variables:} The interesting case is an \textbf{initialized} variable such as \texttt{int x = 5;}. The variable lives in RAM, but RAM is random at power-on. Therefore, the value \texttt{5} has to come from somewhere that survives power-off (flash). So the \texttt{5} is \textbf{stored in flash}, and something must \textbf{copy it into RAM at boot}, before \texttt{main()} runs and reads \texttt{x}. This missing copy mechanism is the whole reason the base program prints only one line.
\end{itemize}

\subsection{The Linker Script and the Memory Map}
The CPU physically sees a single address space of 4 GB (using 32-bit addresses)[cite: 8]. On every Cortex-M chip, this space is rigidly divided into regions whose purpose is fixed by the ARM architecture[cite: 8]. Our emulated board provides specific hardware at specific addresses: 4 MB of executable memory (FLASH) starting at address \texttt{0x0}, and 4 MB of working memory (RAM) starting at \texttt{0x20000000}[cite: 8].

The \textbf{Linker Script} (\texttt{.ld} file) is the architectural blueprint that tells the compiler tools exactly where these physical regions are and how to place the C program into them. Let us analyze the complete script provided for our board:

\begin{lstlisting}
MEMORY
{
    FLASH (rx)  : ORIGIN = 0x00000000, LENGTH = 4M  /* code + read-only data */
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 4M  /* data, bss, stack */
}

ENTRY(Reset_Handler)

_estack = ORIGIN(RAM) + LENGTH(RAM);   /* initial SP = top of RAM */
_Min_Stack_Size = 0x1000;              /* 4 KB reserved for stack */
_Min_Heap_Size = 0x1000;               /* 4 KB reserved for heap */
\end{lstlisting}

\subsubsection{MEMORY: Defining the Regions}
In the \texttt{MEMORY} block, each line explicitly describes one physical region[cite: 9]: a name you choose (\texttt{FLASH}, \texttt{RAM}), a start address (\texttt{ORIGIN}), a size (\texttt{LENGTH}), and access attributes (like \texttt{r} for read, \texttt{x} for execute)[cite: 9]. 

The linker actively uses the \texttt{LENGTH} values to protect your program: if you ask it to place more code than the flash memory can hold, the link intentionally fails at build time with an overflow error rather than producing a broken image that crashes at runtime[cite: 9, 15].

Immediately following the regions, the script calculates the \texttt{\_estack} symbol[cite: 9]. This value (\texttt{0x20400000}) represents exactly one byte past the last available address in the RAM[cite: 9]. Because the Cortex-M stack physically grows downwards (toward lower memory addresses), initializing the stack pointer at the absolute top of the RAM gives it the maximum possible room to grow[cite: 9].

\subsection{SECTIONS: Building the Executable Image}

\subsection{Reading the Result: The \texttt{nm} and \texttt{objdump} Utilities}
The process of linking object files (\texttt{.o}) is not magic; you can actively inspect exactly what the compiler produced before the linker even starts[cite: 12]. The ARM GCC toolchain provides standard utilities to peek inside these files and verify how the compiler tagged your C code.

\subsubsection{Analyzing Symbols with \texttt{nm}}
The \texttt{arm-none-eabi-nm} command lists all the symbols (functions and variables) inside an object file (\texttt{.o}) or the final executable (\texttt{.axf})[cite: 12]. It assigns a specific letter to each symbol, indicating exactly which input section the compiler prepared it for[cite: 12]:

\begin{itemize}
    \item \textbf{\texttt{T / t} (\texttt{.text}):} Executable code. A capital 'T' means a globally visible function (like \texttt{main}), while a lowercase 't' indicates a local (static) function.
    \item \textbf{\texttt{R} (\texttt{.rodata}):} Read-only data, such as string literals (e.g., \texttt{"hello"}) or \texttt{const} variables.
    \item \textbf{\texttt{D / d} (\texttt{.data}):} Initialized global or static variables destined for RAM (e.g., \texttt{int x = 5;}).
    \item \textbf{\texttt{B / b} (\texttt{.bss}):} Uninitialized global or static variables, which strictly default to zero (e.g., \texttt{int total;}).
    \item \textbf{\texttt{U} (Undefined):} An external reference waiting for the linker to resolve it. For example, the compiler marks \texttt{main} as 'U' inside \texttt{startup.o} because it knows the function exists elsewhere, but relies entirely on the linker to determine its final physical address[cite: 13, 15].
\end{itemize}

When you write commands like \texttt{*(.text*)} or \texttt{*(.data*)} in your Linker Script, you are explicitly ordering the Linker to gather all the symbols marked with these specific letters and pack them sequentially[cite: 15].

\subsubsection{Inspecting Section Sizes with \texttt{objdump}}
While \texttt{nm} shows individual variables, the \texttt{arm-none-eabi-objdump -h} utility reveals the structure of the "boxes" themselves. 

When run on an object file or the final executable, it prints one line per output section (e.g., \texttt{.text}, \texttt{.data}, \texttt{.bss}), revealing its exact size in bytes, its VMA (run address), and its LMA (load address). This is the ultimate tool to verify that the Linker Script successfully placed your variables into the correct memory regions according to your mathematical boundaries.

\subsubsection{The .isr\_vector}
The \texttt{SECTIONS} block dictates exactly how the raw code and variables from your C files (the input sections) are packed into the final executable image (the output sections)[cite: 9].

\begin{lstlisting}
SECTIONS
{
    /* 1. Vector table first, at address 0 */
    .isr_vector :
    {
        . = ALIGN(4);            /* word-align */
        KEEP(*(.isr_vector))     /* never garbage-collect it */
        . = ALIGN(4);
    } > FLASH

\end{lstlisting}

The rules are strictly applied in top-to-bottom order. The single dot (\texttt{.}) is the \textbf{Location Counter}: it represents the address the linker is currently at while placing bytes. 

This cursor manages the population of the \texttt{FLASH} memory step by step:

\begin{itemize}
    \item \textbf{Mathematical Alignment (\texttt{ALIGN}):} Before each block, the instruction \texttt{. = ALIGN(4)} ensures that the cursor is on an address that is a multiple of $4$ bytes. It is crucial to understand that this is not a physical block of data: if the cursor is already on a valid address (like the initial zero or \texttt{0x8}), the command does not add any empty space (padding).
    \item \textbf{Anchoring the Vector Table (\texttt{.isr\_vector}):} Because it is the very first section declared within the \texttt{FLASH} region, the linker places it exactly at address \texttt{0x00000000}. This anchoring is vital, because \texttt{0x0} is the exact point where the hardware will blindly read the first instructions upon power-on (reset).
    \item \textbf{Cursor Advancement:} Once the Vector Table is inserted, the Location Counter moves forward by an amount exactly equal to the size of the inserted table. If the base skeleton with only $2$ words ($8$ bytes) is used, the cursor advances to address \texttt{0x00000008}. If the complete $16$-exception table ($64$ bytes) is used, the cursor moves to address \texttt{0x00000040}.
    \item \textbf{Final Alignment and Assignment (\texttt{> FLASH}):} The section closes with another \texttt{ALIGN(4)}, ensuring the cursor is ready on a $4$-byte multiple for whatever comes next (in this case, \texttt{0x8} is already aligned). Finally, the \texttt{> FLASH} directive assigns this entire packaged block into the physical \texttt{FLASH} memory region\end{itemize}

\begin{lstlisting}
    /* 2. Executable code and read-only data */
    .text :
    {
        . = ALIGN(4);
        *(.text*)                /* all executable code */
        *(.rodata*)              /* string literals, const variables */
        . = ALIGN(4);
    } > FLASH
\end{lstlisting}

Continuing the top-to-bottom execution, the Location Counter now processes the second section, \texttt{.text}:

\begin{itemize}
    \item \textbf{Executable Code (\texttt{*(.text*)}):} The linker gathers all the compiled machine instructions (Thumb code) from your object files (such as \texttt{main.o} and \texttt{startup.o}) and places them here.
    \item \textbf{Read-Only Data (\texttt{*(.rodata*)}):} Immediately after the executable code, the linker packs all the constant variables and string literals (e.g., \texttt{"main: hello..."}). These are read-only values that never change during execution, so they stay permanently in Flash.
    \item \textbf{Sequential Placement (No Overwriting Risk):} There is absolutely no risk of overwriting the previous section. The Location Counter (\texttt{.}) acts as a continuous cursor. Having naturally advanced by the exact size of the \texttt{.isr\_vector}, it automatically resumes at the very next available byte (e.g., \texttt{0x00000008} or \texttt{0x00000040}). The \texttt{.text} section is safely and perfectly appended right below the Vector Table.
    \item \textbf{Region Assignment (\texttt{> FLASH}):} The \texttt{> FLASH} directive at the end commands the linker to physically store this newly merged block (\texttt{.text} + \texttt{.rodata}) into the \texttt{FLASH} memory region, continuously building the final \texttt{.axf} firmware image.
\end{itemize}

\subsubsection{The \texttt{.data} Section, VMA and VLA}
The \texttt{.data} section, which holds initialized global variables (like our \texttt{data\_message} string), introduces a critical architectural challenge:

\begin{lstlisting}
    _sidata = LOADADDR(.data);  /* FLASH address of the 
                                   stored initial values */
\end{lstlisting}

\begin{itemize}
    \item \textbf{Extracting the LMA (\texttt{LOADADDR}):} The instruction \texttt{\_sidata = LOADADDR(.data);} dynamically extracts the physical Load Memory Address (LMA) in \texttt{FLASH} where the linker actually stored the initial values of the \texttt{.data} section. 
    \item \textbf{Creating the Source Pointer:} It assigns this address to the symbol \texttt{\_sidata}. During the boot process, our assembly code will use \texttt{\_sidata} as the exact source pointer (\texttt{src}) to read the bytes from \texttt{FLASH} before copying them into \texttt{RAM}[cite: 40, 41].
\end{itemize}

\begin{lstlisting}
    /* 3. Initialized variables */
    .data :
    {
        . = ALIGN(4);
        _sdata = .;             /* start of .data in RAM */
        *(.data*)               /* initialized variables */
        . = ALIGN(4);
        _edata = .;             /* end of .data in RAM */
    } > RAM AT > FLASH          /* run address in RAM, 
                                   load address in FLASH */
\end{lstlisting}

\begin{figure}[h]
    \centering
    \includegraphics[width=0.5\textwidth]{contents/images/sidata.png}
    \caption{Schema concettuale: \_sidata -> .data}
\end{figure}

This code block introduces a fundamental distinction in how embedded systems manage memory for variables that need an initial value but must also change during execution. Every output section possesses two distinct memory addresses:
\begin{itemize}
    \item \textbf{VMA (Virtual/Run Memory Address):} Where the program expects the section to be when it runs. This is the address the CPU uses to access the variable.
    \item \textbf{LMA (Load Memory Address):} Where the section's raw bytes are actually stored in the physical flash image. This is where the initial values are permanently kept.
\end{itemize}

For code (\texttt{.text}), the VMA and LMA are identical because the CPU executes code directly from flash. However, for variables (\texttt{.data}), they \textit{must} differ: variables must physically live in RAM so they can be written to, but their initial values must be permanently stored in FLASH so they survive power-off.

The directive \texttt{> RAM AT > FLASH} enforces exactly this split: it sets the run address (VMA) in RAM and the load address (LMA) in FLASH. The script also defines specific symbols to record the exact boundary addresses, creating a bridge for the boot sequence:
\begin{itemize}
    \item \texttt{\_sidata}: The starting physical address in \texttt{FLASH} where the initial values are stored (the LMA).
    \item \texttt{\_sdata}: The target starting address in \texttt{RAM} where the variables will reside during execution (the VMA).
    \item \texttt{\_edata}: The end address in \texttt{RAM} of the \texttt{.data} section.
\end{itemize}
These symbols act as precise mathematical boundaries, allowing our assembly boot code to know exactly where to copy the bytes from (\texttt{\_sidata}) and where to place them (\texttt{\_sdata} to \texttt{\_edata})[cite: 40, 41].

Further notes:
\begin{itemize}
    \item \textbf{The Input Sections Wildcard (\texttt{*(.data*)}):} This instruction is a powerful gathering command for the linker. The first asterisk (\texttt{*}) acts as a wildcard meaning "from ALL object files" (e.g., \texttt{main.o}, \texttt{startup.o}). The content in parentheses, \texttt{(.data*)}, means "any input section starting with the name \texttt{.data}".
    \item \textbf{How it works:} When you declare an initialized global variable in C, the compiler automatically tags it as \texttt{.data} inside the \texttt{.o} file[cite: 41, 46]. When the linker encounters \texttt{*(.data*)}, it searches through all \texttt{.o} files, extracts every piece of tagged data, and systematically merges and packs them right here into the final output section[cite: 40, 46].
\end{itemize}

\subsubsection{The \texttt{.bss} Section: Zero-Initialized Variables}
The \texttt{.bss} section is responsible for holding uninitialized global and static variables (e.g., \texttt{int total;})[cite: 11, 46]. According to the C standard, these variables are strictly promised to start at zero when the program begins execution.

\begin{lstlisting}
    /* 4. Zero-initialized variables */
    .bss :
    {
        . = ALIGN(4);
        _sbss = .;              /* start of .bss */
        *(.bss*)                /* zero-initialized variables */
        *(COMMON)
        . = ALIGN(4);
        _ebss = .;              /* end of .bss */
    } > RAM
\end{lstlisting}

This section is fundamentally different from \texttt{.data} because it requires absolutely no physical storage space in the final executable (\texttt{.axf}) image[cite: 11]. There is no point in storing thousands of zero bytes in the \texttt{FLASH} memory[cite: 11]. 

Therefore, the \texttt{.bss} section only has a VMA (run address) in \texttt{RAM} and completely lacks a \texttt{LOADADDR} (LMA) in \texttt{FLASH}[cite: 11]. The directive \texttt{> RAM} exclusively assigns it to the working memory[cite: 11].

\begin{itemize}
    \item \textbf{Gathering the Variables (\texttt{*(.bss*)} and \texttt{*(COMMON)}):} The \texttt{*(.bss*)} wildcard extracts all standard zero-initialized variables from the object files[cite: 11]. The \texttt{*(COMMON)} directive handles a specific C language mechanism: in older C standards (or when compiling with the \texttt{-fcommon} flag), uninitialized global variables defined in multiple files without the \texttt{extern} keyword were tagged by the compiler as "common symbols" rather than strictly \texttt{.bss}. The linker merges all these shared symbols together and places them here, ensuring they are also zeroed out during the boot process[cite: 11].
    \item \textbf{The Boot Responsibility:} Because there are no zeros physically stored in \texttt{FLASH}, the \texttt{RAM} is filled with random garbage at power-on[cite: 8]. It is entirely the responsibility of our assembly boot code (inside \texttt{startup.s}) to actively loop from \texttt{\_sbss} to \texttt{\_ebss} and physically write zeros into those memory addresses before calling \texttt{main()}[cite: 11, 46].
\end{itemize}

\subsubsection{The \texttt{.heap} Section: Dynamic Memory}
The \texttt{.heap} region is an area of RAM strictly reserved for dynamic memory allocation (e.g., using \texttt{malloc()} in a hosted C environment). 

\begin{lstlisting}
    /* 5. Heap region */
    .heap :
    {
        . = ALIGN(8);
        _heap_bottom = .;
        . = . + _Min_Heap_Size; /* advance location counter by 4 KB */
        _heap_top = .;
    } > RAM
\end{lstlisting}

Unlike the \texttt{.text} or \texttt{.data} sections, the heap is not a standard input section[cite: 11]. The compiler does not generate \texttt{.heap} tags in the object files because the heap is not made of pre-defined variables; it is simply an empty space set aside for the program to use at runtime. Consequently, this region requires zero physical storage space in the executable flash image[cite: 11].

\begin{itemize}
    \item \textbf{Architectural Alignment (\texttt{ALIGN(8)}):} The cursor is aligned to an $8$-byte boundary. This is a strict architectural requirement on ARM processors to ensure that dynamically allocated $64$-bit data types (like \texttt{double} or \texttt{uint64\_t}) are safely aligned in memory without triggering hardware alignment faults.
    \item \textbf{Carving Out Space (\texttt{. = . + \_Min\_Heap\_Size;}):} Because there are no input variables to pack (no \texttt{*(.heap*)} instruction), the linker simply advances the Location Counter mathematically[cite: 11]. By adding \texttt{\_Min\_Heap\_Size} (previously defined as \texttt{0x1000}, or $4$ KB) to the current cursor position, the linker effectively carves out a contiguous $4$ KB chunk of empty RAM[cite: 11].
    \item \textbf{Boundary Symbols:} The Location Counter records the start and end of this reserved block into \texttt{\_heap\_bottom} and \texttt{\_heap\_top}. If a standard C library (like \texttt{libc} or \texttt{newlib}) were linked, its dynamic memory manager (\texttt{sbrk}) would use these precise symbols to safely hand out memory chunks when \texttt{malloc()} is called.
    \item \textbf{Region Assignment (\texttt{> RAM}):} Just like \texttt{.bss}, this section exists purely in the working memory and has no Load Memory Address (LMA) in \texttt{FLASH}[cite: 11].
\end{itemize}

\subsubsection{Link-Time Guard: Stack Reservation and \texttt{ASSERT}}
The final lines of the linker script do not allocate new memory sections, but rather implement a critical mathematical safety net to prevent memory collisions.

\begin{lstlisting}
    /* 6. Link-time guard */
    __StackLimit = _estack - _Min_Stack_Size;
    ASSERT(__StackLimit >= _heap_top, "region RAM overflowed...")
\end{lstlisting}

To understand this guard, we must consider how the Cortex-M architecture utilizes the physical memory map. An $8$-digit hexadecimal address represents $32$ bits, giving the processor a theoretical $4$ GB address space ($2^{32}$ bytes). However, the physical hardware is much smaller. In our ARM Cortex-M3 system, a $4$ MB physical RAM chip is placed starting at address \texttt{0x20000000}. Therefore, the absolute top of the RAM (\texttt{\_estack}) is located at \texttt{0x20400000}.

Within this physical $4$ MB space, the dynamic memory regions operate with:
\begin{itemize}
    \item \textbf{Opposing Growth Directions:} The heap grows upwards (towards higher memory addresses) starting from the bottom of available RAM (right after the \texttt{.bss} section). Conversely, the Cortex-M stack physically grows downwards, starting strictly from the absolute top of the RAM (\texttt{\_estack} at \texttt{0x20400000}). When data is pushed to the stack, the Stack Pointer decreases (e.g., \texttt{0x203FFFFC}, \texttt{0x203FFFF8}). If these two regions ever cross paths in the middle, they will silently overwrite each other's data, causing catastrophic system crashes.
    \item \textbf{Calculating the Stack Boundary (\texttt{\_\_StackLimit}):} The script mathematically subtracts the reserved minimum stack size (e.g., \texttt{0x1000}, or $4$ KB) from the top of the RAM (\texttt{\_estack}). This calculates the \texttt{\_\_StackLimit} symbol (e.g., \texttt{0x203FF000}), representing the absolute lowest memory address the stack is safely permitted to reach without colliding with the heap below it.
    \item \textbf{The Build-Time Safety Net (\texttt{ASSERT}):} The \texttt{ASSERT} directive is a logic check evaluated strictly by the linker during the build process, not by the CPU at runtime. It actively verifies that the highest address of the heap (\texttt{\_heap\_top}) has not encroached upon the reserved stack space boundary (\texttt{\_\_StackLimit}).
    \item \textbf{Intentional Build Failure:} If the condition (\texttt{\_\_StackLimit >= \_heap\_top}) evaluates to false, it mathematically proves that the physical $4$ MB \texttt{RAM} is too small to hold the requested layout. Instead of generating a broken executable image that will crash unpredictably at runtime, the linker intentionally aborts the compilation process entirely and prints the custom error message: \texttt{"region RAM overflowed..."}.
\end{itemize}

\subsection{Inspecting the Build Artifacts}
\subsubsection{Linker-Defined Symbols Are Addresses, Not Variables}
Symbols defined in the linker script such as \texttt{\_sdata}, \texttt{\_edata}, and \texttt{\_estack} are unique: \textbf{they have no physical storage}[cite: 11]. 

There is no physical memory cell called \texttt{\_sdata} holding a value[cite: 11]. The linker simply assigns each symbol an address, and that address \textit{itself} is the information[cite: 11]. This distinction is critical when referencing them from C:
\begin{lstlisting}[language=c]
extern uint32_t _sdata;
uint32_t start = (uint32_t)&_sdata; /* OK: gets the actual address */
uint32_t oops = _sdata;              /* WRONG: reads garbage from RAM */
\end{lstlisting}

In assembly, the boot code utilizes these symbols strictly as mathematical boundaries (e.g., looping from \texttt{\_sidata} to \texttt{\_sdata}) to initialize the C runtime[cite: 11].

\subsubsection{Analyzing the Map File (\texttt{.map})}
When the linker successfully finishes linking the object files, it produces an \texttt{output.map} file. This file is the absolute source of truth for understanding exactly where every single byte of your program physically landed in memory.

Looking at the generated \texttt{output.map} for our actual build, we can observe the Linker strictly enforcing our rules:

\begin{lstlisting}[language=bash]
Memory Configuration
Name             Origin             Length             Attributes
FLASH            0x00000000         0x00400000         xr
RAM              0x20000000         0x00400000         xrw
\end{lstlisting}
The \texttt{Memory Configuration} block confirms that the physical hardware map was understood exactly as we defined it.

As we scroll down into the \texttt{Linker script and memory map} section, we see the calculation of our top-level boundaries:
\begin{lstlisting}[language=bash]
                0x20400000                _estack = (ORIGIN (RAM) + LENGTH (RAM))
                0x00001000                _Min_Stack_Size = 0x1000
                0x00001000                _Min_Heap_Size = 0x1000
\end{lstlisting}

Then, we can observe the individual output sections being populated and "folded" together:

\begin{lstlisting}[language=bash]
.isr_vector     0x00000000       0x40
                0x00000000                . = ALIGN (0x4)
 *(.isr_vector)
 .isr_vector    0x00000000       0x40 build/boot/startup.o
                0x00000000                isr_vector

.text           0x00000040       0xc0
                0x00000040                . = ALIGN (0x4)
 *(.text*)
 .text          0x00000040       0x70 build/boot/startup.o
                0x00000040                Reset_Handler
                0x000000ac                DebugMon_Handler
                ... (other handlers)
 .text          0x000000b0       0x34 build/src/main.o
                0x000000c8                main
\end{lstlisting}
This section clearly demonstrates the sequential packing behavior: 
\begin{itemize}
    \item The vector table (\texttt{.isr\_vector}) was correctly placed at address \texttt{0x00000000} and took up \texttt{0x40} bytes.
    \item Immediately after it, at address \texttt{0x00000040}, the linker began packing the executable code (\texttt{.text}). 
    \item It first placed \texttt{Reset\_Handler} and the other handlers from \texttt{startup.o}, and then placed the \texttt{main} function from \texttt{main.o} starting at \texttt{0x000000c8}.
\end{itemize}

Finally, analyzing the \texttt{.data} section reveals the LMA/VMA split perfectly:
\begin{lstlisting}[language=bash]
                0x00000100                _etext = .
                0x00000100                _sidata = LOADADDR (.data)
...
.data           0x20000000       0x20 load address 0x00000100
                0x20000000                _sdata = .
 *(.data*)
 .data          0x20000000       0x20 build/src/main.o
                0x20000000                data_message
                0x20000020                _edata = .
\end{lstlisting}
Here, the linker explicitly proves our memory architecture: our initialized array \texttt{data\_message} is mapped to run from RAM at address \texttt{0x20000000} (its VMA), but its physical load address (LMA) in the image is \texttt{0x00000100}. The map file also confirms that \texttt{\_sidata} and \texttt{\_etext} share this exact same physical address in FLASH.

Once the linker has stitched all the object files together using the rules defined in the Linker Script, we can inspect the final executable image (\texttt{scratch-os.axf}) using \texttt{nm}. By passing the \texttt{-n} flag, we force the output to be strictly sorted by physical memory address rather than alphabetically:

\begin{lstlisting}

This final, ordered output perfectly visualizes our memory layout architecture from top to bottom:
\begin{itemize}
    \item \textbf{Vector Table in FLASH:} \texttt{isr\_vector} is perfectly anchored at \texttt{0x00000000} (\textbf{R} for read-only).
    \item \textbf{Code Placement:} The previously undefined (\textbf{U}) symbols from the object files have been assigned exact physical addresses in FLASH. \texttt{Reset\_Handler} starts at \texttt{0x00000040}, immediately followed by our internal boot loop labels (\texttt{zero\_bss}), the \texttt{Default\_Handler} (and its Weak aliases, marked \textbf{W}), and eventually \texttt{main} at \texttt{0x000000c8}.
    \item \textbf{The Boot Copy Bridge:} Notice how \texttt{\_etext} and \texttt{\_sidata} both share the exact same address (\texttt{0x00000100}). This visually proves that the initial values for the \texttt{.data} section physically reside in FLASH immediately after the executable code ends.
    \item \textbf{Variables in RAM:} Our writable global array, \texttt{data\_message}, sits precisely at \texttt{0x20000000} (\textbf{D} for initialized data), which perfectly matches the linker-defined target symbol \texttt{\_sdata}.
    \item \textbf{Absolute Linker Symbols:} Symbols defined purely by math in the linker script (like \texttt{\_Min\_Stack\_Size} or \texttt{\_\_StackLimit}) are tagged as \textbf{A} (Absolute). They do not belong to any specific code section; they are simply hardcoded constant addresses calculated during the build process.
\end{itemize}

\subsubsection{Analyzing the Object Files (\texttt{.o})}
Before the linker merges everything into the final image, we can inspect the raw object files generated by the compiler and assembler using \texttt{nm}. 

If we inspect the compiled assembly boot code (\texttt{startup.o}) using the \texttt{-n} flag, we see:
\begin{lstlisting}
$ arm-none-eabi-nm -n startup.o
         U _ebss
         U _estack
         U _sbss
         U main
00000000 T Reset_Handler
00000000 R isr_vector
0000000c t zero_bss
00000016 t zero_bss_done
0000004a t hang
0000006c W BusFault_Handler
0000006c W DebugMon_Handler
0000006c T Default_Handler
0000006c W HardFault_Handler
0000006c W MemManage_Handler
0000006c W NMI_Handler
0000006c W PendSV_Handler
0000006c W SVC_Handler
0000006c W SysTick_Handler
0000006c W UsageFault_Handler
\end{lstlisting}
This output perfectly validates our code:
\begin{itemize}
    \item \textbf{Global vs. Local Code:} \texttt{Reset\_Handler} and \texttt{Default\_Handler} are global code (\textbf{T}), while internal assembly loops like \texttt{zero\_bss} and \texttt{hang} are strictly local labels (\textbf{t}).
    \item \textbf{Read-Only Data:} \texttt{isr\_vector} is treated as read-only data (\textbf{R}) destined for FLASH.
    \item \textbf{Weak Symbols:} The \textbf{W} tag indicates a "Weak" symbol. All these specific fault handlers are temporarily pointing to the exact same address as \texttt{Default\_Handler} (\texttt{0x0000006c}). The linker allows us to override them later in C without throwing duplicate symbol errors.
    \item \textbf{Undefined Dependencies:} \texttt{\_estack}, \texttt{\_sbss}, \texttt{\_ebss}, and \texttt{main} are marked as \textbf{U} (Undefined). The assembler encountered these names but did not find them in \texttt{startup.s}. It leaves them blank, trusting the Linker Script (for the memory boundaries) and \texttt{main.o} (for the function) to provide their actual addresses later.
\end{itemize}

Similarly, if we inspect our C program (\texttt{main.o}):
\begin{lstlisting}
$ arm-none-eabi-nm -n main.o
00000000 D data_message
00000000 t semihost_write0
00000000 n wm4.0.ad0b2718a3b78dc336646f204185dd21
00000000 n wm4.stdintgcc.h.29.6d480f4ba0f60596e88234283d42444f
00000018 T main
\end{lstlisting}
Here, the C compiler correctly categorized our components:
\begin{itemize}
    \item \textbf{Functions:} \texttt{main} is a globally visible C function (\textbf{T}), while \texttt{semihost\_write0} is a \texttt{static} C function, making it strictly local to this file (\textbf{t}).
    \item \textbf{Data Mapping:} \texttt{data\_message} is an initialized global array, so the compiler explicitly tagged it for the \texttt{.data} section (\textbf{D}).
    \item \textbf{Debug Metadata:} The symbols marked with \textbf{n} are internal GCC debug/informational notes. They are harmless metadata and will not consume physical memory on the microcontroller.
\end{itemize}
When the linker runs, it will stitch \texttt{startup.o} and \texttt{main.o} together, replacing the \textbf{U} symbols with the real addresses assigned during the layout phase.

\subsection{Memory Mapping of C Variables}
\subsubsection{Pointers, Local, and Static Variables}
Pointers deserve a moment of care, because a pointer is itself a variable. In the declaration \texttt{const char *p = "hi";}, the characters \texttt{"hi"} are a string literal and go to \texttt{.rodata}; however, \texttt{p}, the variable holding their address, is an initialized writable variable and goes to \texttt{.data}.

This table of section rules only applies to declarations made \textbf{outside any function}. A local variable inside a function has no section at all: it lives on the stack while the function runs, and it is gone as soon as the function returns.

\subsubsection{Try It: Testing Global Declarations}
You can test these placement rules by adding the following \textbf{global} variables to \texttt{src/main.c}, right after the line that defines \texttt{data\_message} (before \texttt{main}), so outside any function:

\begin{lstlisting}[language=c]
const int limit = 100;
int counter = 5;
int total;
int zero = 0;
const char *greeting = "hi";
char buffer[64];
\end{lstlisting}

Write down your prediction for each one, then compile and check the raw object file:
\begin{lstlisting}[language=bash]
$ arm-none-eabi-nm -n build/src/main.o
00000000 D data_message
00000000 R limit
00000000 B total
00000004 B zero
00000008 B buffer
00000018 T main
00000020 D counter
00000024 D greeting
\end{lstlisting}

In the object file (\texttt{.o}), the addresses are mostly \texttt{00000000} because they are merely offsets within their respective sections. The compiler has brilliantly sorted our variables:
\begin{itemize}
    \item \textbf{\texttt{total} and \texttt{buffer} (\texttt{B}):} Uninitialized global variables go straight to \texttt{.bss}.
    \item \textbf{The \texttt{zero} trick (\texttt{B}):} We wrote \texttt{int zero = 0;}. Technically, it is initialized, but the compiler knows our \texttt{.bss} initialization loop will overwrite this area with zeros anyway. To save precious FLASH memory, it optimizes \texttt{zero} by moving it from \texttt{.data} to \texttt{.bss}.
    \item \textbf{\texttt{counter} (\texttt{D}):} Initialized with \texttt{5}, it correctly goes to \texttt{.data}.
    \item \textbf{The \texttt{greeting} pointer (\texttt{D}):} We wrote \texttt{const char *greeting = "hi";}. The string \texttt{"hi"} is constant, but the pointer variable \texttt{greeting} (which holds the address of the string) is writable! You could later write \texttt{greeting = "hello";}. Therefore, the pointer itself belongs in \texttt{.data}.
    \item \textbf{\texttt{limit} (\texttt{R}):} A strictly read-only integer constant goes to \texttt{.rodata}.
\end{itemize}

Now, check the final linked executable:
\begin{lstlisting}[language=bash]
$ arm-none-eabi-nm -n build/scratch-os.axf
...
000000e4 T limit
00000108 T _etext
00000108 A _sidata
20000000 D _sdata
20000000 D data_message
20000020 D counter
20000024 D greeting
20000028 D _edata
20000028 B _sbss
20000028 B total
2000002c B zero
20000030 B buffer
20000070 B _ebss
...
\end{lstlisting}

Notice the physical addresses: \texttt{buffer} starts at \texttt{0x20000030} and is $64$ bytes long (\texttt{0x40} in hex). Consequently, \texttt{\_ebss} correctly marks the end of the section at \texttt{0x20000070} (\texttt{0x20000030 + 0x40}).

More importantly, look at \texttt{limit}. In the final executable, it is marked \textbf{T} (Text), not \textbf{R}! This is because our Linker Script explicitly packaged the \texttt{*(.rodata*)} inputs inside the \texttt{.text} output section. \texttt{nm} classifies symbols in the \texttt{.axf} based on the final output section they reside in.

The string \texttt{"hy"} has no name, so \texttt{nm} does not show it directly, but the map file confirmed that the \texttt{.rodata} input sections of \texttt{main.o} are folded inside the \texttt{.text} output section. You can find its raw bytes by dumping the contents of the \texttt{.text} section from the final executable:

\begin{lstlisting}[language=bash]
$ arm-none-eabi-objdump -s -j .text scratch-os.axf

scratch-os.axf:     file format elf32-littlearm

Contents of section .text:
 ...
 00d0 efff0348 fff7ecff 00bffde7 ec000000  ...H............
 00e0 00000020 64000000 68790000 6d61696e  ... d...hy..main
 00f0 3a206865 6c6c6f20 66726f6d 20746865  : hello from the

\end{lstlisting}

Each line starts with the hexadecimal address of its first byte, followed by $16$ bytes of data, and repeats the same bytes translated as ASCII text on the far right. This dump perfectly corroborates our previous findings:
\begin{itemize}
    \item \textbf{The constant integer:} At address \texttt{0x00e4} (which exactly matches the \texttt{limit} symbol from our \texttt{nm} analysis), you find the bytes \texttt{64 00 00 00}. Because ARM Cortex-M uses Little-Endian architecture, this is the $32$-bit integer \texttt{0x00000064}, which is exactly $100$ in decimal.
    \item \textbf{The string literal:} At address \texttt{0x00e8}, you find \texttt{68 79 00 00}. In ASCII, \texttt{0x68} is 'h' and \texttt{0x79} is 'y', followed by the null-terminating byte (\texttt{0x00}) and a padding byte. This proves that the nameless string literal \texttt{"hy"} physically resides in FLASH memory.
    \item \textbf{Other constants:} Immediately following it at \texttt{0x00ec}, you can clearly see the bytes for \texttt{main: hello from the base\\n}, another read-only string literal used elsewhere in the \texttt{main.c} code.
\end{itemize}

\subsubsection{Pointers in RAM and Little-Endianness}
If the string literal \texttt{"hy"} is physically stored in FLASH, how does the C program actually find it? It finds it through the \texttt{greeting} variable, which is a pointer physically stored in RAM. 

We can verify this by dumping the runtime \texttt{.data} section from the final executable:
\begin{lstlisting}[language=bash]
$ arm-none-eabi-objdump -s -j .data scratch-os.axf

scratch-os.axf:     file format elf32-littlearm

Contents of section .data:
 20000000 6d61696e 3a207468 69732074 65787420  main: this text 
 20000010 6c697665 7320696e 202e6461 74610a00  lives in .data..
 20000020 05000000 e8000000                    ........
\end{lstlisting}

Because you defined the test variables in \texttt{src/main.c} immediately after \texttt{data\_message}, the linker placed them in that exact sequential order:
\begin{itemize}
    \item The first $32$ bytes (from \texttt{0x20000000} to \texttt{0x2000001F}) contain the initialized \texttt{data\_message} array (you can easily read its text string on the right side of the dump).
    \item Immediately following it, at address \texttt{0x20000020}, we find \texttt{counter}.
    \item At address \texttt{0x20000024}, we find the \texttt{greeting} pointer.
\end{itemize}

To correctly read these hexadecimal values, you must remember a fundamental architectural detail: the Cortex-M3 processor is strictly \textbf{little-endian}. This means that multi-byte integers are stored in memory with their least significant byte (LSB) at the lowest memory address.

\begin{itemize}
    \item \textbf{The integer \texttt{counter}:} At \texttt{0x20000020}, we see the four bytes \texttt{05 00 00 00}. Read in little-endian order, this is the $32$-bit integer \texttt{0x00000005}, which exactly matches the initialized value of \texttt{counter} (\texttt{5}).
    \item \textbf{The pointer \texttt{greeting}:} At \texttt{0x20000024}, we see the four bytes \texttt{e8 00 00 00}. Read in little-endian order, this is the $32$-bit integer \texttt{0x000000e8}. If you look back at our previous \texttt{.text} dump, \texttt{0x000000e8} is the exact FLASH address where the string literal \texttt{"hy"} physically resides!
\end{itemize}

This perfectly demonstrates what a pointer physically is at the hardware level: it is simply an integer variable (living in RAM) whose numeric value is the memory address of another piece of data (living in FLASH).

\subsubsection{Local vs. Static Local Variables}
You can see the local-vs-global contrast directly. Inside \texttt{main}, add \texttt{int local = 7;} and \texttt{static int s = 3;}, then check \texttt{nm} again.
\begin{itemize}
    \item \texttt{local} never appears at all: it is not a global, it has no fixed address, and it only exists on the stack while \texttt{main} is running.
    \item \texttt{s} does appear, as \texttt{d s.0}: lowercase \texttt{d} means it lives in \texttt{.data} but is visible only inside this file, and the compiler appends a \texttt{.0} (or \texttt{.N} suffix) to tell one function's static local apart from another's if they share a name. Unlike \texttt{local}, a \texttt{static} local keeps one fixed address for the whole run of the program, exactly like a global — it is only its \textit{name} that stays private to the function.
\end{itemize}

\subsection{Advanced Memory Layout: Custom Sections and Orphans}
You are not strictly limited to the default sections the compiler chooses. GCC provides compiler attributes that allow you to explicitly name the input section of a variable or a function:

\begin{lstlisting}[language=c]
int tagged __attribute__((section(".mysection"))) = 42;
\end{lstlisting}

Where that custom section physically ends up is entirely up to the linker script, \textbf{if the script names it}. A section that does not match any rule in the \texttt{SECTIONS} block is called an \textbf{orphan}. The linker does not reject an orphan section; instead, it places it by guessing based on its flags (e.g., whether it is writable or executable) and places it adjacent to sections with similar properties. 

While this guess usually allows the program to link successfully, the orphan section is placed completely outside your control and, critically, outside any predefined symbol ranges.

If you add the \texttt{tagged} variable to the base project and examine the output using \texttt{arm-none-eabi-nm -n}, you will see the linker symbols placed next to your variable:

\begin{lstlisting}[language=bash]
20000000 D _sdata
20000020 D _edata
20000020 D tagged
\end{lstlisting}

A new output section \texttt{.mysection} appears. The linker saw a writable, initialized section, so it placed it in RAM \textbf{right after \texttt{.data}}, and gave it its own load address in FLASH. 

Now compare its address with \texttt{\_edata}: \texttt{tagged} sits exactly at \texttt{\_edata}, that is, \textit{after} the end of the range \texttt{\_sdata}...\texttt{\_edata}. A boot loop that copies only \texttt{\_sdata}...\texttt{\_edata} will never copy it, so \texttt{tagged} will not hold 42 when \texttt{main()} runs. The program links without a single warning and is still wrong. That is the fundamental danger of orphans.

If you declare a \texttt{const int} in a section called \texttt{.myconst} instead, the linker sees a read-only section and places it safely in FLASH, between \texttt{.isr\_vector} and \texttt{.text}. 

\subsection{Overflowing a Region}
The \texttt{LENGTH} values in the \texttt{MEMORY} block are not decoration: the linker actively enforces them. First, measure how much flash the base image needs:

\begin{lstlisting}[language=bash]
arm-none-eabi-size build/scratch-os.axf
\end{lstlisting}

The FLASH region has to hold \texttt{text + data}: the code and constants, plus the stored copy of \texttt{.data}'s initial values. For the base skeleton, this is $96 + 32 = 128$ bytes. 

If you edit \texttt{scripts/mps2\_m3.ld} and set FLASH \texttt{LENGTH = 100}, you can test this enforcement. Rebuild with \texttt{make -B} (the \texttt{Makefile} does not automatically list the linker script as a prerequisite, so \texttt{-B} forces everything to be rebuilt). The link will intentionally fail with:

\begin{lstlisting}[language=bash]
region 'FLASH' overflowed by 28 bytes
\end{lstlisting}

$128 - 100$ is exactly 28. If you set \texttt{LENGTH = 128}, the link succeeds because the image fits exactly.

If you then restore FLASH and set RAM \texttt{LENGTH = 8K} instead, \texttt{\_estack} moves down to \texttt{0x20002000}. The 4 KB stack reservation starts 4 KB below it, meaning the 4 KB heap no longer fits between \texttt{.bss} and the stack. The build failure in this scenario comes directly from the script's own \texttt{ASSERT} line, printing its custom message about the heap colliding with the stack.

\section{Reset: The Hardware Contract and \texttt{boot.s}}
Once the memory layout is finalized in the linker script and loaded into memory, the machine can be powered on. The next question is how the CPU starts using it.

When the Cortex-M3 comes out of reset, before any of your code runs, there is absolutely no C runtime available. The `.data` section is not copied to RAM yet, and `.bss` is not zeroed. To boot the system, the hardware automatically executes a strictly predefined sequence. It does exactly two things:
\begin{enumerate}
    \item It reads the 32-bit word at address `0x0` and puts it directly into the Stack Pointer (`SP`).
    \item It reads the word at address `0x4` and puts it directly into the Program Counter (`PC`). Execution starts at that exact address.
\end{enumerate}

\textbf{Everything else (copying `.data`, zeroing `.bss`, configuring the CPU, calling `main()`) is entirely the responsibility of your bare-metal code}. This foundational runtime setup is written entirely in assembly in a file named \texttt{boot/startup.s}.

\subsection{The Assembly Environment}
Before writing the actual instructions, the assembly file configures the build tools using assembler directives:
\begin{itemize}
    \item \textbf{\texttt{.syntax unified}:} Instructs the assembler to use modern ARM syntax.
    \item \textbf{\texttt{.cpu cortex-m3}:} Ensures the assembler only accepts instructions physically present on the Cortex-M3, catching typos at compile-time.
    \item \textbf{\texttt{.thumb}:} Emits Thumb instructions. Cortex-M CPUs can \textit{only} execute Thumb code; they lack a standard 32-bit ARM mode.
\end{itemize}
Any symbol the assembler does not find defined locally (like \texttt{\_estack} from the linker script, or \texttt{main} from \texttt{main.c}) is automatically treated as an external reference, leaving it up to the linker to fill in the correct addresses.

\subsection{The Vector Table}
Those two initial words read at reset are the beginning of the \textbf{Vector Table}: an array of addresses at a fixed place in memory (address `0x00000000` at reset).

The table exists because of exceptions. An exception is an event that forces the CPU to stop its current task and run a specific piece of code called a handler. Slot $N$ of the table physically holds the memory address of the handler for exception $N$. Slot 0 is unique: it is not executable code, but purely the initial value of the Stack Pointer.

In \texttt{boot/startup.s}, we construct this table explicitly. Notice how the assembly mirrors standard C array initialization:

\begin{lstlisting}
    .section .isr_vector,"a",%progbits
    .global isr_vector
    .type isr_vector, %object

isr_vector:
    .word _estack               /* 0: initial SP = top of RAM */
    .word Reset_Handler         /* 1: reset: first code after power-on */
\end{lstlisting}

\textbf{C Equivalent:}
\begin{lstlisting}[language=c]
void (* const isr_vector[])(void) = {
    (void (*)(void)) &_estack,  /* Slot 0: Initial Stack Pointer */
    Reset_Handler,              /* Slot 1: Reset execution address */
};
\end{lstlisting}

\textit{Directive breakdown:} The \texttt{.section .isr\_vector,"a",\%progbits} directive explicitly tells the tools to place these words into a section named \texttt{.isr\_vector}. The linker script ensures this specific section is always physically placed first in the FLASH memory, guaranteeing it lands precisely at address `0x0`.

\subsubsection{The Thumb Bit Constraint}
One critical detail you will observe in a debugger: the value stored in word 1 is not exactly the raw address of 'Reset\_Handler', but that address with its lowest bit set to 1.

Instructions always sit at even addresses (2-byte or 4-byte aligned), so bit 0 of a code address is physically unused. ARM repurposes bit 0 as a flag to mean "this is Thumb code". Because the Cortex-M3 executes only the Thumb instruction set, the hardware strictly requires this bit to be 1.

\subsubsection{KEEP and Garbage Collection}
The linker possesses an optional optimization feature known as section garbage collection. It drops every section of code or data that no other software actively references. 

Because no software code actively calls or reads \texttt{isr\_vector} (only the hardware reads it at power-on), the garbage collector would consider the table useless and throw it away, causing an immediate hardware lockup at boot[cite: 16, 17]. The \texttt{KEEP (*(.isr\_vector))} directive in the linker script explicitly forces the linker to preserve the table regardless of software references[cite: 16, 17].

\subsection{The Reset Handler}
Once the vector table is read, execution officially begins at the 'Reset\_Handler'. This is standard executable code, placed into the \texttt{.text} section.

\begin{lstlisting}
    .section .text,"ax",%progbits
    .global Reset_Handler
    .type Reset_Handler, %function
    .thumb_func
Reset_Handler:
    /* Runtime setup steps (stack, data, bss) go here. */

    bl main                     /* Branch with Link to C code */
hang:
    b hang                      /* Infinite loop if main returns */

    .ltorg                      /* Literal pool placement */
\end{lstlisting}

\textbf{C Equivalent:}
\begin{lstlisting}[language=c]
void Reset_Handler(void) {
    /* Setup runtime... */
    main();
    for (;;) { }
}
\end{lstlisting}

\textit{Directive breakdown:} 
\begin{itemize}
    \item \textbf{.thumb\_func}: Instructs the tools that the immediately following label ('Reset\_Handler') is a Thumb function. When the assembler builds the vector table above, it sees this tag and automatically sets bit 0 to 1, fulfilling the hardware's Thumb bit constraint.
    \item \textbf{.ltorg}: Generates the \textbf{Literal Pool}. ARM instructions are only 16 or 32 bits wide, meaning they cannot physically contain a full 32-bit constant (like the memory address of \textit{\_estack}) inside the instruction itself. The assembler stores the actual 32-bit constant in a nearby table (the literal pool) and translates your instruction into a PC-relative load. \textit{.ltorg} guarantees this table of constants is placed safely after the last instruction, where the CPU will never accidentally attempt to execute it as code.
\end{itemize}

\subsection{Back to the Base: Why Only One Line Prints}
With the memory layout and hardware contract fully mapped, we can finally explain the behavior of the base skeleton observed at the beginning of the chapter.

If you run the base code (\texttt{make run}), the \texttt{main()} function attempts to print two lines:
\begin{enumerate}
    \item A standard string literal.
    \item \texttt{data\_message}, an initialized global array.
\end{enumerate}

Let us look closely at how these are defined in \texttt{src/main.c}, as it perfectly illustrates the memory concepts from Unit 1:

\begin{lstlisting}[language=c]
/* A global array with an initial value. 
 * Because it is writable data, it MUST live in RAM. */
char data_message[] = "main: this text lives in .data\n";

int main(void)
{
    /* 1. Printing a string literal */
    semihost_write0("main: hello from the base\n");

    /* 2. Printing the global array */
    semihost_write0(data_message);

    for (;;) { }
}
\end{lstlisting}

When \texttt{main()} executes, here is exactly what happens at the hardware level:
\begin{itemize}
    \item \textbf{The String Literal (Line 1):} A string literal like \texttt{"main: hello..."} is read-only \texttt{const} data. The compiler naturally places it in the \texttt{.rodata} section, which the linker script puts directly into FLASH memory alongside the executable code. It needs no copying to be read: it is already sitting at the physical address it will be read from, right from the very first instruction. Therefore, this line always prints correctly.
    \item \textbf{The Global Array (Line 2):} Unlike a string literal, a global array is \textit{writable} data, so it must physically live in RAM (since FLASH cannot be written to at runtime). As confirmed by the linker script, the \texttt{.data} section has its VMA (Run Address) at \texttt{0x20000000} in RAM, but its initial bytes are stored at a FLASH LMA (Load Address). 
\end{itemize}

Until something physically copies its initial value from FLASH to RAM, this array's content in RAM is whatever happened to already be there at power-on. In our base skeleton, \texttt{Reset\_Handler} contains no code to move the bytes from the LMA to the VMA. Consequently, the RAM at \texttt{0x20000000} in QEMU is filled with zeros, which C interprets as an empty string. Thus, the second call prints nothing.

Writing the assembly loop to perform this missing memory copy is the very first task in building our C runtime.


\section{Taking Control of the CPU}
In this unit, you rebuild \texttt{Reset\_Handler} in \texttt{boot/startup.s} yourself, in assembly, one step at a time. To do that, you need two things you have not used before: a debugger to \textit{see} what the CPU does, and enough ARM assembly to read and write the boot code.

\subsection{What is a Debugger?}
A \textbf{debugger} is a program that controls another program while it runs. It can \textbf{stop} the program at any instruction you choose (a \textbf{breakpoint}) or right at the start, before anything has run. It can \textbf{step} it forward one machine instruction, or one C line, at a time. While the program is stopped, it can \textbf{inspect} the CPU registers and any memory address, and even change them. And it can \textbf{continue} the program until the next breakpoint.

On a desktop, a crashing program at least prints an error message. On a microcontroller, there is often no console at all, and a crash simply looks like "nothing happens". A debugger is frequently the \textit{only} way to see what the CPU is really doing. The standard tool is \textbf{gdb}, the GNU debugger, part of the same toolchain family as gcc. The ARM version you use is \texttt{arm-none-eabi-gdb}; on Linux, the gdb that understands ARM is usually called \texttt{gdb-multiarch} instead.

\subsection{A Remote Debugger: Two Programs, Two Terminals}
In this setup, the program being debugged does not run on the same "machine" as gdb. It runs inside QEMU, which emulates the Cortex-M3 board on your laptop. gdb talks to QEMU over a network connection (a TCP socket on your own machine). So you use two terminals:

\begin{verbatim}
 Terminal 1: make debug               Terminal 2: arm-none-eabi-gdb build/scratch-os.axf
 +-------------------------+          +--------------------------+
 | QEMU: CPU + Flash + RAM |  TCP     | gdb: knows your symbols  |
 | halted at reset         |<-------->| (main, Reset_Handler...) |
 | gdb server on port 1234 |  :1234   | from the .axf file       |
 +-------------------------+          +--------------------------+
   program output shows here            you type commands here
\end{verbatim}

In terminal 1, you start QEMU with \texttt{make debug}. The \texttt{debug} target in the \texttt{Makefile} runs the same QEMU command as \texttt{make run}, plus two options: \texttt{-S}, which freezes the emulated CPU before its very first instruction, and \texttt{-gdb tcp::1234}, which starts a gdb server that waits for a connection on TCP port 1234. Anything the program prints still appears in this terminal.

\subsubsection{Reconstructing the Debug Target}
The \texttt{debug} target is therefore nothing more than a shorthand, and you can reconstruct it for any image. Take the QEMU command from the \texttt{run} target of the \texttt{Makefile} you are working with, and append \texttt{-S -gdb tcp::1234}:

\begin{lstlisting}[language=bash]
qemu-system-arm -machine mps2-an385 -monitor null -semihosting \
    -semihosting-config enable=on,target=native \
    -kernel build/scratch-os.axf -serial stdio -nographic \
    -S -gdb tcp::1234
\end{lstlisting}

This matters after this week: the later checkpoints' Makefiles have a \texttt{run} target but no \texttt{debug} target, and this command, run from the checkpoint's folder after \texttt{make}, is how you debug them.

In terminal 2, you start gdb and give it the ELF file, \texttt{arm-none-eabi-gdb build/scratch-os.axf}. gdb reads the ELF only for its \textbf{symbols} and debug information, so that it knows the addresses of \texttt{main}, \texttt{Reset\_Handler}, \texttt{data\_message}, and so on. It does not load the code: QEMU already holds the program. You then connect with \texttt{target remote :1234}.

\subsubsection{The GDB Commands You Need}
This small set of commands is enough for everything this week:

\begin{table}[h!]
    \centering
    \begin{tabular}{|l|l|}
        \hline
        \textbf{Command} & \textbf{What it does} \\ \hline
        \texttt{target remote :1234} & connect to the gdb server (QEMU) on this machine \\ \hline
        \texttt{info registers sp pc} & show some registers (\texttt{info registers} alone: all of them) \\ \hline
        \texttt{x/2wx 0} & e\textbf{x}amine memory: 2 \textbf{w}ords (32 bits each) in he\textbf{x}, at address 0 \\ \hline
        \texttt{x/s \&data\_message} & examine memory as a C \textbf{s}tring \\ \hline
        \texttt{p/x \$r1} & \textbf{p}rint one register (or a C expression) in hex \\ \hline
        \texttt{display/i \$pc} & after every step, show the next \textbf{i}nstruction \\ \hline

        \texttt{quit} (\texttt{q}) & leave gdb (QEMU keeps running: stop it with \texttt{Ctrl-C}) \\ \hline

\end{table}

\subsection{Attaching at Reset}
The first thing to do with the debugger is to catch the CPU \textit{before} its first instruction, and check the reset contract from Unit 1. In the base folder:

\begin{lstlisting}[language=bash]
make debug                                  # terminal 1: QEMU waits
arm-none-eabi-gdb build/scratch-os.axf      # terminal 2
\end{lstlisting}

and in gdb:

\begin{lstlisting}[language=bash]
(gdb) target remote :1234
(gdb) info registers sp pc
(gdb) x/2wx 0
\end{lstlisting}

You see \texttt{sp} equal to \texttt{0x20400000}, \texttt{pc} equal to \texttt{0x8 <Reset\_Handler>}, and at address 0 the two words \texttt{0x20400000 0x00000009}. \textbf{No instruction has run yet}, yet SP and PC already have values: the CPU itself copied vector word 0 into SP and vector word 1 into PC. 

Compare the two: word 1 is \texttt{0x9}, PC is \texttt{0x8}. This is the Thumb bit from Unit 1. The CPU uses bit 0 to check that the target is Thumb code and then clears it; the instruction really starts at \texttt{0x8}. And why \texttt{0x8} in the first place? The base's vector table has only two words (8 bytes), and the code is placed right after it in FLASH.

\subsection{Cortex-M3 Programmer's Model: The Registers}
To follow the CPU instruction by instruction, you need to know what it holds. The \textbf{programmer's model} is the set of registers your code, and gdb, can see. All of them are 32 bits wide.

\begin{table}[h!]
    \centering
    \begin{tabular}{|l|l|l|}
        \hline
        \textbf{Register} & \textbf{Name} & \textbf{Role} \\ \hline
        R0--R12 & general purpose & your values; a C function call passes its first arguments in R0--R3 \\ \hline
        R13 & \textbf{SP} & stack pointer: address of the top of the stack \\ \hline
        R14 & \textbf{LR} & link register: where to return after a function call \\ \hline
        R15 & \textbf{PC} & program counter: address of the next instruction \\ \hline
        --- & \textbf{xPSR} & status: flags, Thumb bit, current exception \\ \hline
    \end{tabular}
\end{table}

At this level, there are no variables: only these registers and memory. When your C code says \texttt{x = x + 1}, the compiler turns it into "load \texttt{x} from memory into a register, add 1 to the register, store the register back". The stack, as you know, grows \textbf{downwards}: pushing a value first does \texttt{SP = SP - 4}, then writes the value at the new SP.

\subsubsection{The Status Register (xPSR) and CPU Modes}
\textbf{xPSR} (program status register) packs three critical pieces of information into one register:
\begin{itemize}
    \item \textbf{Flags (Bits 31--28):} The \textbf{N Z C V} flags (negative, zero, carry, overflow), set by comparison instructions and used by conditional jumps.
    \item \textbf{Thumb Bit (Bit 24):} The \textbf{T} state bit, which must always be 1 on Cortex-M (this is where bit 0 of the vector entry ends up).
    \item \textbf{Exception Number (Bits 8--0):} Holds the number of the exception currently being handled, or 0 if none.
\end{itemize}

That last field dictates which of the two \textbf{modes} the CPU is in:
\begin{itemize}
    \item \textbf{Thread mode:} The CPU runs normal code (\texttt{Reset\_Handler}, \texttt{main()}, and the functions they call); the exception number is 0.
    \item \textbf{Handler mode:} The CPU runs an exception handler, and the field holds that exception's number.
\end{itemize}
\textit{Note:} Code in Thread mode can also be privileged or unprivileged; everything in this specific unit runs privileged, and Unit 3 explains the difference.

\subsection{ARM Assembly Basics: A Load/Store Architecture}
The boot code has to be written in assembly because, before it runs, there is no valid stack and no initialized data, so C code cannot yet be trusted. You need only a handful of instructions, and each has a direct C equivalent.

\textbf{A load/store machine:} ARM arithmetic works only on registers. Memory is touched only by \textbf{load} instructions (\texttt{ldr}, memory to register) and \textbf{store} instructions (\texttt{str}, register to memory).

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{Assembly} & \textbf{C equivalent} \\ \hline
\texttt{ldr r3, [r0]} & \texttt{r3 = *r0;} \\ \hline
\texttt{str r3, [r1]} & \texttt{*r1 = r3;} \\ \hline
\texttt{ldr r3, [r0], \#4} & \texttt{r3 = *r0; r0 += 4;} (that is, \texttt{r3 = *src++;}) \\ \hline
\texttt{str r3, [r1], \#4} & \texttt{*r1 = r3; r1 += 4;} (that is, \texttt{*dst++ = r3;}) \\ \hline
\texttt{strb r1, [r0, \#7]} & \texttt{((uint8\_t *)r0)[7] = r1;} (one \textbf{b}yte, at offset 7) \\ \hline
\end{tabular}
\end{table}

The square brackets mean "the memory at this address". The form \texttt{[r0], \#4} is called \textbf{post-increment}: the instruction first uses the address in \texttt{r0}, then adds 4 to \texttt{r0}. One word is 4 bytes, so a loop using this syntax walks through memory word by word, exactly like \texttt{*dst++} in C.

\subsubsection{Constants, Labels, and Jumps}
Moving data between registers and controlling program flow requires another set of basic instructions:

\begin{table}[h!]
    \centering
    \begin{tabular}{|l|l|}
        \hline
        \textbf{Assembly} & \textbf{C equivalent} \\ \hline
        \texttt{ldr r0, =\_estack} & \texttt{r0 = (uint32\_t)\&\_estack;} (any 32-bit value) \\ \hline
        \texttt{mov sp, r0} & \texttt{sp = r0;} (register to register) \\ \hline
        \texttt{movs r3, \#0} & \texttt{r3 = 0;} (small constants only) \\ \hline
        \texttt{copy\_data:} & a \textbf{label}: a name for this address, like a C \texttt{goto} label \\ \hline
        \texttt{b copy\_data} & \texttt{goto copy\_data;} \\ \hline
        \texttt{bl main} & \texttt{main();}: \textbf{b}ranch with \textbf{l}ink, saves the return address in LR \\ \hline
    \end{tabular}
\end{table}

\textbf{The 32-bit Instruction Encoding Constraint (Literal Pools):} 
The \texttt{ldr rX, =value} form needs a word of explanation because you will see it look different in gdb. An instruction is only 16 or 32 bits long, so it mathematically cannot contain an arbitrary 32-bit constant alongside its opcode. 

The assembler therefore stores the constant in a small table of constants near the code, called the \textbf{literal pool}, and turns your \texttt{ldr r0, =\_estack} into "load r0 from that table". In gdb, this appears as something like \texttt{ldr r0, [pc, \#92]} (an address relative to the PC). 

The \texttt{.ltorg} directive at the end of \texttt{Reset\_Handler} in \texttt{boot/startup.s} tells the assembler where to put this pool: typically after the last instruction, where the CPU will never try to execute it as code.

\subsubsection{Control Flow: Decisions, Bits, and Interrupts}
Branching and loops in assembly rely entirely on the \texttt{xPSR} status register. A decision is a two-step process: compare values to set condition flags, then jump based on those flags.

\begin{table}[h!]
    \centering
    \begin{tabular}{|l|l|}
        \hline
        \textbf{Assembly} & \textbf{C equivalent} \\ \hline
        \texttt{cmp r1, r2} & compute \texttt{r1 - r2}, keep only the flags N Z C V \\ \hline
        \texttt{bhs done} & \texttt{if (r1 >= r2) goto done;} (\textbf{h}igher or \textbf{s}ame, unsigned) \\ \hline
        \texttt{orr r1, r1, \#0x10} & \texttt{r1 |= 0x10;} \\ \hline
        \texttt{cpsid i} & stop accepting interrupts (\texttt{\_\_disable\_irq()} in vendor C code) \\ \hline
        \texttt{cpsie i} & accept interrupts again (\texttt{\_\_enable\_irq()}) \\ \hline
    \end{tabular}
\end{table}

With \texttt{cmp} and a conditional branch, you can build any loop. A C \texttt{while} loop becomes "test at the top, jump back at the bottom":
\begin{lstlisting}
loop:  cmp r1, r2        @ while (r1 < r2) {
       bhs done          @
       ...               @     body
       b   loop          @ }
done:
\end{lstlisting}
The loop continues while \texttt{r1 < r2}; as soon as \texttt{r1 >= r2}, \texttt{bhs} jumps out of the loop.

\subsubsection{Assembler Directives}
Lines that start with a dot (\texttt{.}) produce no instructions: they steer the assembler itself. The directives used in \texttt{boot/startup.s} are:

\begin{lstlisting}
    .section .isr_vector,"a",%progbits   @ put what follows in section .isr_vector
    .global isr_vector                   @ make the name visible to the linker
isr_vector:
    .word _estack                        @ one 32-bit value
    .word Reset_Handler

    .section .text,"ax",%progbits
    .global Reset_Handler
    .thumb_func                          @ next label is Thumb code: its address gets bit 0 = 1
Reset_Handler:
\end{lstlisting}

The vector table block translates to the following C equivalent:
\begin{lstlisting}
__attribute__((section(".isr_vector")))
const uint32_t isr_vector[] = { (uint32_t)&_estack, (uint32_t)Reset_Handler };
\end{lstlisting}

\begin{itemize}
    \item \texttt{.section}: Chooses the section, with flags. \texttt{"a"} means the section occupies space in the image; \texttt{"x"} means it is executable.
    \item \texttt{.global}: Makes a name visible to other files and to the linker. Without it, a label acts like a \texttt{static} name in C.
    \item \texttt{.word}: Allocates exactly one 32-bit word and stores the given value inside it.
    \item \texttt{.thumb\_func}: Dictates that the next label is Thumb code. This instructs the tools to store \texttt{Reset\_Handler} with bit 0 set to 1, which is where the \texttt{0x9} in the base (and \texttt{0x41} in the solution) comes from.
\end{itemize}
The file also uses \texttt{.type} and \texttt{.size} to tell \texttt{gdb} and \texttt{nm} whether a name is code or data and its total size.

\section{Writing the Startup Script (\texttt{Reset\_Handler})}
The \texttt{Reset\_Handler} in \texttt{boot/startup.s} has one critical job: to turn a bare CPU into an environment that can safely run C code.

Here is the complete sequence of operations, in the exact order the boot code executes them:
\begin{table}[h!]
    \centering
    \begin{tabular}{|l|l|}
        \hline
        \textbf{Step} & \textbf{Why} \\ \hline
        1. Mask interrupts & Nothing may interrupt a half-built system \\ \hline
        2. Set SP & C functions inherently need a stack \\ \hline
        3. Copy \texttt{.data} FLASH $\rightarrow$ RAM & Initialized global variables must get their values \\ \hline
        4. Zero \texttt{.bss} & C promises uninitialized global variables start at 0 \\ \hline
        5. Configure the CPU & Set up vector table address, fault handlers, traps, priorities \\ \hline
        6. Unmask interrupts, \texttt{bl main} & Hand execution over to C \\ \hline
        7. Loop forever & If \texttt{main} ever returns, there is nowhere to go \\ \hline
    \end{tabular}
\end{table}

In the base skeleton, \texttt{Reset\_Handler} has only steps 6 and 7 (and without the unmask). The following sections go through building the remaining steps in order.

\subsection{Steps 1 and 2: Mask Interrupts and Set the Stack}
An \textbf{interrupt} is an exception raised by hardware (e.g., a timer expiring or a device receiving data): the CPU drops what it is doing and runs that interrupt's handler. During setup, absolutely nothing is ready to handle one: a handler written in C could attempt to read a variable that has not been initialized yet.

Therefore, the very first instruction, \texttt{cpsid i}, tells the CPU to explicitly ignore interrupts for now. (While no device has been told to raise an interrupt yet, writing it makes the rule explicit instead of relying on luck).

Next, the stack pointer (\texttt{SP}) must be set:
\begin{lstlisting}
@ C equivalent: sp = &_estack;
ldr r0, =_estack    @ top of RAM, 0x20400000
mov sp, r0
\end{lstlisting}

Because C has no way to name SP directly, the C equivalent is pseudo-code. One might wonder why this step is strictly needed, since the hardware already loaded SP from word 0 of the vector table at reset. The answer is that \texttt{Reset\_Handler} is not \textit{always} reached through a real hardware reset: a custom bootloader or a debugger may jump to it directly, with SP holding an arbitrary or invalid value. 

Setting SP explicitly makes the code robust and correct in every case, and demonstrates that the stack is nothing more than an address in a register. Notice the two-step ARM pattern: because SP is a special register, the address is first loaded into an ordinary general-purpose register (\texttt{r0}), and then explicitly copied into SP using \texttt{mov}.

\subsection{Step 3: Copy \texttt{.data} from FLASH to RAM}
This is the critical step that fixes the base skeleton's missing print line. The linker script gives you three key addresses:

\begin{lstlisting}[language=make]
FLASH:  [ .text | .rodata | initial values of .data ]
                             ^ _sidata
RAM:    [ .data             | .bss | ...        stack ]
          ^ _sdata          ^ _edata                  ^ _estack
\end{lstlisting}

The copy operation is a simple loop, which you can write first in C and then translate line by line into assembly:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{C Equivalent} & \textbf{ARM Assembly} \\ \hline
\texttt{uint32\_t *src = \&\_sidata;} & \texttt{ldr r0, =\_sidata} \\
\texttt{uint32\_t *dst = \&\_sdata;} & \texttt{ldr r1, =\_sdata} \\
\texttt{                      } & \texttt{ldr r2, =\_edata} \\ \hline
\texttt{while (dst < \&\_edata)} & \texttt{copy\_data: cmp r1, r2} \\
\texttt{                      } & \texttt{            bhs copy\_data\_done} \\ \hline
\texttt{    *dst++ = *src++;  } & \texttt{            ldr r3, [r0], \#4} \\
\texttt{                      } & \texttt{            str r3, [r1], \#4} \\
\texttt{                      } & \texttt{            b   copy\_data} \\ \hline
\texttt{                      } & \texttt{copy\_data\_done:} \\ \hline
\end{tabular}
\end{table}

Register \texttt{r0} plays the role of \texttt{src}, \texttt{r1} of \texttt{dst}, and \texttt{r2} holds the end address. The loop is named \texttt{copy\_data} in \texttt{boot/startup.s}, and it exits to \texttt{copy\_data\_done}. It copies whole words, 4 bytes at a time; this is perfectly safe because the linker script intentionally aligns the start and end of \texttt{.data} to multiples of 4.

If you write steps 1--3 into the base skeleton (just before \texttt{bl main}) and run it, the missing line finally appears:
\begin{lstlisting}[language=bash]
make run
main: hello from the base
main: this text lives in .data
\end{lstlisting}
Before the copy, \texttt{data\_message} sat in RAM as all zeros and printed as an empty string; now it successfully holds its initial value.

\subsubsection{Watching the Copy Loop in GDB}
It is highly recommended to watch this loop run step-by-step in GDB. It takes the abstract linker concepts of LMA (Load Memory Address, in FLASH) and VMA (Virtual Memory Address, in RAM) and makes them concrete. 

Start \texttt{make debug} in terminal 1 and gdb in terminal 2, then execute the following session:

\begin{lstlisting}[language=bash]
(gdb) target remote :1234
(gdb) display/i $pc                  # Auto-print the next instruction
(gdb) stepi                          # Step through setup instructions...
(gdb) stepi                          # ...until you reach "cmp r2, r3"
...
=> 0x4c <Reset_Handler+12>:     cmp     r2, r3
(gdb) p/x $r0                        # Check _estack (Top of RAM)
$1 = 0x20400000
(gdb) p/x $r1                        # Check _sidata (LMA: Source in FLASH)
$2 = 0x120
(gdb) p/x $r2                        # Check _sdata  (VMA: Dest in RAM)
$3 = 0x20000000
(gdb) x/s &data_message              # Inspect RAM before the copy
0x20000000 <data_message>:      ""   # Nothing here yet!
(gdb) stepi 5                        # Execute one full 5-instruction loop
=> 0x4c <Reset_Handler+12>:     cmp     r2, r3
(gdb) p/x $r1                        # Check source pointer again
$4 = 0x124                           # Incremented by 4 bytes (1 word)
(gdb) break copy_var_done            # Set a breakpoint after the loop
(gdb) continue                       # Let the CPU finish the copying
Breakpoint 1, Reset_Handler () at boot/startup.s:244
(gdb) x/s &data_message              # Inspect RAM again
0x20000000 <data_message>:      "main: this text lives in .data\n"
\end{lstlisting}

\paragraph{Understanding the Output}
As you step through the initialization, you can observe exactly how the Cortex-M3 translates our assembly:
\begin{itemize}
    \item \textbf{Pseudo-instructions revealed:} When stepping over \texttt{ldr r0, =\_estack}, GDB shows the actual machine instruction being executed: \texttt{ldr r0, [pc, \#92]}. This proves that the CPU cannot load a 32-bit address directly; it must read it from the literal pool located 92 bytes ahead of the current Program Counter.
    \item \textbf{LMA vs VMA:} When the code reaches \texttt{cmp r2, r3}, checking the registers perfectly illustrates the linker script mapping. Register \texttt{r1} points to \texttt{0x120}, a small address in the FLASH memory where the initial values are stored permanently (LMA). Register \texttt{r2} points to \texttt{0x20000000}, the beginning of the volatile SRAM (VMA).
    \item \textbf{The Copy Action:} The command \texttt{x/s \&data\_message} asks GDB to read the memory at that RAM address and interpret it as a string. Initially, it is completely empty (\texttt{""}). By typing \texttt{stepi 5}, we force the CPU to execute exactly one iteration of the loop (\texttt{cmp}, \texttt{bhs}, \texttt{ldr}, \texttt{str}, \texttt{b}). Register \texttt{r1} climbs from \texttt{0x120} to \texttt{0x124}, proving one 32-bit word was moved. 
    \item \textbf{The Result:} Instead of manually stepping hundreds of times, we place a breakpoint at the end of the loop and continue. Once the loop finishes, reading the RAM address again reveals that the string has been successfully transferred from FLASH to SRAM, ready for C code to use it.
\end{itemize}

\subsubsection{Try It: Breaking the Stack on Purpose}
Seeing a wrong SP fail is the best way to believe that SP matters. In \texttt{boot/startup.s}, inside \texttt{Reset\_Handler}, find the line you wrote in Step 2 (\texttt{ldr r0, =\_estack}) and intentionally replace \texttt{\_estack} with a bad address. (Note that the value the CPU loaded from vector word 0 at reset is still the correct one; it is your \texttt{mov sp, r0} that forcefully overwrites it with the bad address).

\paragraph{Test 1: Address Outside of RAM (\texttt{0x30000000})}
If you intentionally force SP to an unmapped address like \texttt{0x30000000} and execute \texttt{make run}, the program yields no output. Instead, QEMU halts with a fatal exception:
\begin{lstlisting}[language=bash]
qemu: fatal: Lockup: can't escalate 3 to HardFault (current priority -1)
\end{lstlisting}
This sequence perfectly illustrates the Cortex-M exception mechanism. The instant \texttt{main()} begins, the CPU attempts to save local registers to the stack (\texttt{push}). Because \texttt{0x30000000} is not backed by physical memory, this write generates a fault. To report it, the CPU attempts to jump to the HardFault handler. However, the ARM architecture mandates that the hardware automatically pushes the current execution context (the exception frame) onto the stack \textit{before} executing the handler's first instruction. Since the stack pointer still points to invalid memory, this automatic push triggers a second, unresolvable fault. With no higher-priority exception left to handle a fault-within-a-fault, the processor gives up and enters a terminal state known as \textbf{Lockup}.

\paragraph{Test 2: Unaligned Stack Pointer (\texttt{0x20000001})}
If you configure SP to an odd address inside RAM, \texttt{make run} fails silently. To understand why, start a \texttt{make debug} session, step just past the \texttt{mov sp, r0} instruction, and check the register: \texttt{info registers sp} will output \texttt{0x20000000}. 

The Cortex-M3 hardware strictly enforces 32-bit word alignment for the Main Stack Pointer, silently discarding the two lowest bits (equivalent to \texttt{SP \& 0xFFFFFFFC}). Consequently, the stack incorrectly initializes at the absolute bottom of the RAM block (\texttt{0x20000000}). Because the ARM stack grows downwards (a full-descending architecture), the very first \texttt{push} instruction preemptively decrements the pointer to \texttt{0x1FFFFFFC}—an address strictly outside the RAM boundary. In QEMU's default memory map, writes to this specific region are silently ignored rather than trapped. No explicit crash is logged, but function calls inevitably fail because return addresses cannot be saved or retrieved. (\textit{Remember to restore} \texttt{ldr r0, =\_estack} \textit{before continuing}).

\subsection{Step 4: Zero the \texttt{.bss} Section}
The C standard strictly promises that global variables without an explicit initializer (e.g., \texttt{int counter;}) will start at \texttt{0}. They physically reside in the \texttt{.bss} section, mapped between \texttt{\_sbss} and \texttt{\_ebss} in RAM. Because nothing in flash holds their zeroed value, the boot code must explicitly write these zeros. 

This is the exact same looping logic as the data copy, but without a source pointer reading from flash:

\begin{table}[h!]
    \centering
    \begin{tabular}{|l|l|}
        \hline
        \textbf{C Equivalent} & \textbf{ARM Assembly} \\ \hline
        \texttt{uint32\_t *dst = \&\_sbss;} & \texttt{ldr r1, =\_sbss} \\
        \texttt{                      } & \texttt{ldr r2, =\_ebss} \\
        \texttt{                      } & \texttt{movs r3, \#0} \\ \hline
        \texttt{while (dst < \&\_ebss)} & \texttt{zero\_bss: cmp r1, r2} \\
        \texttt{                      } & \texttt{           bhs zero\_bss\_done} \\ \hline
        \texttt{    *dst++ = 0;       } & \texttt{           str r3, [r1], \#4} \\
        \texttt{                      } & \texttt{           b   zero\_bss} \\ \hline
        \texttt{                      } & \texttt{zero\_bss\_done:} \\ \hline
    \end{tabular}
\end{table}

This loop is labeled \texttt{zero\_bss} in \texttt{boot/startup.s}. In the current base skeleton, \texttt{.bss} happens to be empty (so \texttt{\_sbss} equals \texttt{\_ebss}), meaning the loop exits immediately. However, the first uninitialized global you add (like \texttt{int total;}) will absolutely rely on it. 

\textit{Warning:} Remember that RAM is \textit{not} zeroed at power-on on real hardware. While the QEMU emulator zeroing RAM for you is a convenience, you must not architecturally count on it.

With steps 1 through 4 completed, \texttt{Reset\_Handler} replicates everything that the previous C startup code did. The remaining steps go further: they configure the CPU so that errors are caught, escalated, and reported.

\section{Exceptions and Faults: One Family}
You have already encountered the concept of an \textbf{exception}: any hardware or software event that forces the CPU to stop executing the current code and run a specific handler function. The CPU fetches the address of this handler from the vector table and executes it in Handler mode. 

The Cortex-M3 physically defines the following family of exceptions:

\begin{table}[h!]
    \centering
    \begin{tabular}{|l|l|l|}
        \hline
        \textbf{\#} & \textbf{Exception} & \textbf{Raised by} \\ \hline
        0 & \textit{(not an exception)} & This slot holds the initial SP value \\ \hline
        1 & Reset & Power-on, reset button \\ \hline
        2 & NMI & Non-maskable interrupt: cannot be ignored \\ \hline
        3 & \textbf{HardFault} & Any fault with nowhere else to go \\ \hline
        4 & \textbf{MemManage} & Breaking memory protection rules \\ \hline
        5 & \textbf{BusFault} & Access to an address where nothing answers, or that refuses access \\ \hline
        6 & \textbf{UsageFault} & Bad use of an instruction: undefined opcode,Thumb bit 0,divide by 0 \\ \hline
        7--10 & \textit{reserved} & Unused: the slot must hold \texttt{0} \\ \hline
        11 & SVCall & The \texttt{svc} instruction \\ \hline
        12 & DebugMonitor & Debug events (unused here) \\ \hline
        13 & \textit{reserved} & Unused: the slot must hold \texttt{0} \\ \hline
        14 & PendSV & A request raised by software \\ \hline
        15 & SysTick & The CPU's built-in timer \\ \hline
        16+ & IRQs & External device interrupts \\ \hline
    \end{tabular}
\end{table}

Slots 7--10 and 13 are strictly reserved. The four specific faults (3 through 6) are the CPU's direct way of signaling that "the program did something wrong". 

Crucially, at power-on reset, only the \texttt{HardFault} exception is actively listening. The three more specific faults (\texttt{MemManage}, \texttt{BusFault}, \texttt{UsageFault}) are disabled by default. When a specific fault is disabled, it \textit{escalates} directly to a \texttt{HardFault}. This escalation mechanism explains the "can't escalate 3 to HardFault" lockup message we saw earlier: the CPU was trying to escalate to exception 3 (\texttt{HardFault}), but because the handler could not safely push to the stack, it failed.

\subsection{Completing the Vector Table with Weak Symbols}
The base table only has 2 words defined, but the Cortex-M3 expects one word for each exception from 0 to 15 (16 words in total). Every slot strictly needs \textit{some} valid address, even for exceptions you have no custom handler for yet, because if that hardware exception triggers, the CPU will blindly jump to whatever address the slot contains. (The reserved slots must contain \texttt{0}).

Therefore, \texttt{isr\_vector} in \texttt{boot/startup.s} gets 14 additional \texttt{.word} entries. Instead of writing a dozen empty functions for every single exception, the standard engineering practice is to route them all to a generic default loop using weak symbols and aliases in assembly:

\begin{lstlisting}
    .word HardFault_Handler                    @ slot 3, and so on up to 15
    .weak      HardFault_Handler               @ may be replaced from C
    .thumb_set HardFault_Handler, Default_Handler
Default_Handler:
    b Default_Handler                          @ for (;;) {}
\end{lstlisting}

Which translates to the following compiler directive in C:
\begin{lstlisting}[language=c]
void HardFault_Handler(void) __attribute__((weak, alias("Default_Handler")));
\end{lstlisting}

\textbf{How it works:}
\begin{itemize}
    \item \texttt{.word HardFault\_Handler} places the address of the label into the exact table slot.
    \item \texttt{.thumb\_set} dictates to the assembler: "Make \texttt{HardFault\_Handler} another name for \texttt{Default\_Handler} (sharing the same address, marked as Thumb code)".
    \item \texttt{.weak} makes that name a \textbf{weak symbol}: a default implementation that easily yields. If any other file (like \texttt{src/main.c}) explicitly defines a normal, non-weak function named \texttt{void HardFault\_Handler(void)}, the linker silently drops the weak assembly default and routes the hardware exception directly to the developer's custom C function.
\end{itemize}

\texttt{Default\_Handler} itself is simply an infinite loop. An unexpected exception is a critical system bug, and freezing the CPU at a known, predictable place is much easier to diagnose in a debugger than allowing it to run off into random memory addresses.

\subsubsection{The Effect on Memory Layout}
Completing the vector table immediately alters your memory layout. The table grows physically from 2 words to 16 words (from 8 bytes to 64 bytes). Because the executable code still flows right after it in FLASH, the start of \texttt{Reset\_Handler} moves down from address \texttt{0x8} to \texttt{0x40}. 

If you attach GDB at reset now, \texttt{info registers sp pc} will show \texttt{pc 0x40 <Reset\_Handler>}, and examining address 0 (\texttt{x/2wx 0}) will print \texttt{0x0 <isr\_vector>: 0x20400000 0x00000041} (proving the Thumb bit is added to the \texttt{0x40} address). 

If you examine the \texttt{nm} output of the final binary, you will clearly see the effect of the weak symbols: \texttt{NMI\_Handler}, \texttt{PendSV\_Handler}, \texttt{SysTick\_Handler}, and \texttt{DebugMon\_Handler} are explicitly marked \texttt{W} (weak) and all share the exact same memory address as \texttt{Default\_Handler}. Meanwhile, any handlers written and compiled from \texttt{src/main.c} are firmly marked \texttt{T} (Text) at their own unique addresses.

\subsection{CPU Settings Live at Memory Addresses}
The remaining configuration steps change settings inside the CPU core itself. You do not need special assembly instructions for most of them: the Cortex-M architecture makes these settings physically available as 32-bit registers at fixed memory addresses in the system area of the memory map (specifically, from \texttt{0xE000E000} to \texttt{0xE000EFFF}). 

The specific group of registers that controls exceptions is called the \textbf{System Control Block (SCB)}. You can change them using ordinary load and store instructions.

\begin{table}[h!]
    \centering
    \begin{tabular}{|l|l|}
        \hline
        \textbf{C Equivalent} & \textbf{ARM Assembly} \\ \hline
        \texttt{\#define SCB\_SHCSR (*(volatile uint32\_t *)0xE000ED24)} & \\ 
        \texttt{SCB\_SHCSR |= (1u << 16);} & \texttt{ldr r0, =0xE000ED24   @ address} \\
        & \texttt{ldr r1, [r0]          @ read} \\
        & \texttt{orr r1, r1, \#0x10000 @ modify} \\
        & \texttt{str r1, [r0]          @ write} \\ \hline
    \end{tabular}
\end{table}

\subsubsection{The Read-Modify-Write Pattern and \texttt{volatile}}
This architectural pattern is known as \textbf{read-modify-write}: you read the current value of the register, modify only the specific bits you care about using a bitwise OR, and write the result back. This ensures that all other configuration bits in the register keep their original values.

In the C version, the \texttt{volatile} keyword is mandatory. It explicitly tells the compiler that every memory access must truly happen exactly in the order written. Without it, the compiler's optimizer might skip a read (assuming "the value cannot have changed") or remove a write (assuming "nobody reads it"). For hardware registers, both assumptions are completely false.

\textit{Debugging tip:} You can read these registers from gdb just like any other memory address. For example, \texttt{x/wx 0xE000ED00} shows \texttt{0x410fc231}, which is the CPUID register identifying the chip as an ARM (\texttt{0x41}) Cortex-M3 (\texttt{0xc23}).

\subsection{Step 5: VTOR, Where the Vector Table Is}
When an exception happens, the CPU does not technically read slot $N$ strictly at address \texttt{4 * N}. It reads it at \texttt{\textbf{VTOR} + 4 * N}, where \textbf{VTOR} (the Vector Table Offset Register, located at \texttt{0xE000ED08}) holds the base address of the table. 

Its default value at reset is \texttt{0x00000000}, which is exactly why our initial table must reside at address 0. However, the boot code explicitly writes the address of \texttt{isr\_vector} into it anyway:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{C Equivalent} & \textbf{ARM Assembly} \\ \hline
\texttt{*(volatile uint32\_t *)0xE000ED08 = } & \texttt{ldr r0, =0xE000ED08} \\
\texttt{                       (uint32\_t)isr\_vector;} & \texttt{ldr r1, =isr\_vector} \\
& \texttt{str r1, [r0]} \\ \hline
\end{tabular}
\end{table}

(Note: The table address must be suitably aligned, at least to 128 bytes, because the low bits of VTOR are not used by the hardware).

Why perform this write if our table is already at 0? Because in real production systems, the table is often located elsewhere. A \textbf{bootloader} sitting at address 0 may start an application stored higher in the flash memory, whose own vector table is at a different address. The application must then point VTOR to its own table. Alternatively, an OS may copy its table into RAM to replace handlers dynamically while running. Explicitly writing VTOR ensures the boot code remains correct regardless of where the final image is placed.

\textbf{Where you write it:} In \texttt{Reset\_Handler}, right after the label \texttt{zero\_bss\_done:} (the end of step 4). Because you are setting the entire register to a new absolute address, no read-modify-write is needed. In gdb at \texttt{main}, \texttt{x/wx 0xE000ED08} will show \texttt{0x00000000}: the same as the reset value, confirming the table is at address 0 (verified by \texttt{p/x \&isr\_vector}).

\subsection{Step 6: SHCSR, Separate Fault Handlers}
The \textbf{SHCSR} (System Handler Control and State Register) at address \texttt{0xE000ED24} enables three specific hardware faults. By default, these bits are heavily restricted (set to 0), meaning all faults instantly escalate to a generic \texttt{HardFault}. This gives you a single handler for every kind of error, making it impossible to diagnose exactly \textit{what} went wrong inside it.

\begin{table}[h!]
    \centering
    \begin{tabular}{|c|l|l|}
        \hline
        \textbf{Bit} & \textbf{Name} & \textbf{When set} \\ \hline
        16 & MEMFAULTENA & MemManage faults run \texttt{MemManage\_Handler} \\ \hline
        17 & BUSFAULTENA & Bus faults run \texttt{BusFault\_Handler} \\ \hline
        18 & USGFAULTENA & Usage faults run \texttt{UsageFault\_Handler} \\ \hline
    \end{tabular}
\end{table}

The boot code must set bits 16--18 simultaneously with a bitwise OR (\texttt{|= 0x00070000}), ensuring each fault routes cleanly to its own dedicated handler. Because the other bits of SHCSR report critical system status (like which handlers are active or pending), you \textbf{must} use the read-modify-write pattern. Never simply overwrite the whole register.

\begin{lstlisting}
    ldr r0, =0xE000ED24         /* r0 = address of SHCSR */
    ldr r1, [r0]                /* r1 = SCB_SHCSR (read) */
    orr r1, r1, #0x00070000     /* r1 |= (1u<<16)|(1u<<17)|(1u<<18) (modify) */
    str r1, [r0]                /* SCB_SHCSR = r1 (write) */
\end{lstlisting}

\textit{Debugging tip:} In GDB at \texttt{main}, checking \texttt{x/wx 0xE000ED24} will correctly display \texttt{0x00070000}.


\subsection{Step 7: CCR, What Counts as a Fault}
\textbf{CCR}, the Configuration and Control Register physically located at \texttt{0xE000ED14}, dictates whether certain suspicious CPU operations are classified as faults at all.

\begin{table}[h!]
    \centering
    \begin{tabular}{|c|l|l|l|}
        \hline
        \textbf{Bit} & \textbf{Name} & \textbf{Meaning} & \textbf{Status} \\ \hline
        3 & UNALIGN\_TRP & Trap unaligned word/halfword accesses & Left off \\ \hline
        4 & DIV\_0\_TRP & Trap integer divide by 0 (as a UsageFault) & \textbf{Set (1)} \\ \hline
        9 & STKALIGN & 8-byte-align the stack on exception entry & Already 1 \\ \hline
    \end{tabular}
\end{table}

Without the \texttt{DIV\_0\_TRP} bit set, an integer division by zero on the Cortex-M3 does not inherently trigger a fault: the hardware divide instructions (\texttt{sdiv}/\texttt{udiv}) silently return \textbf{0}. The program would continue running with a mathematically incorrect value, hiding a potentially catastrophic bug. Setting bit 4 transforms that silent failure into an immediate \texttt{UsageFault}. 

Unaligned memory accesses, on the other hand, are strictly legal on the Cortex-M3 (though slightly slower). While trapping them can help identify sloppy pointer casts, it can also inadvertently break correct, optimized code produced by the C compiler or standard libraries. Therefore, it is intentionally left off.

This step is a perfect example of why the read-modify-write pattern is absolutely critical: bit 9 (\texttt{STKALIGN}) is already set to 1 at hardware reset and must remain 1. A direct write would accidentally clear it, corrupting exception entry behavior.

\begin{lstlisting}
    ldr r0, =0xE000ED14         /* r0 = address of CCR */
    ldr r1, [r0]                /* r1 = SCB_CCR (read) */
    orr r1, r1, #(1 << 4)       /* r1 |= (1u << 4), DIV_0_TRP (modify) */
    str r1, [r0]                /* SCB_CCR = r1 (write) */
\end{lstlisting}

\textit{Debugging tip:} In GDB at \texttt{main}, checking \texttt{x/wx 0xE000ED14} will successfully show \texttt{0x00000210} (which is \texttt{0x200} for bit 9, plus \texttt{0x10} for bit 4).

\subsection{Step 8: Exception Priorities}
Initial logic and parameters for exception priorities are validated: a lower number means a more urgent priority. Reset, NMI, and HardFault possess fixed negative priorities. Configurable exceptions use the System Handler Priority Registers (SHPR1, SHPR2, SHPR3), mapped as a contiguous byte array starting at \texttt{0xE000ED18}.

Standard processing is applied to bypass read-modify-write overhead by using direct byte stores (\texttt{strb}). We assign \texttt{0x00} to faults, \texttt{0x80} to SVCall, and \texttt{0xE0} to PendSV and SysTick.

\begin{lstlisting}
    ldr r0, =0xE000ED18         /* prio = r0 = address of SHPR1 byte 0 */
    movs r1, #0x00              /* r1 = 0x00, most urgent */
    strb r1, [r0, #0]           /* prio[0] = 0x00: MemManage */
    strb r1, [r0, #1]           /* prio[1] = 0x00: BusFault */
    strb r1, [r0, #2]           /* prio[2] = 0x00: UsageFault */
    movs r1, #0x80              /* r1 = 0x80, middle priority */
    strb r1, [r0, #7]           /* prio[7] = 0x80: SVCall */
    movs r1, #0xE0              /* r1 = 0xE0, least urgent */
    strb r1, [r0, #10]          /* prio[10] = 0xE0: PendSV */
    strb r1, [r0, #11]          /* prio[11] = 0xE0: SysTick */
\end{lstlisting}

\textit{Debugging tip:} Checking \texttt{x/3wx 0xE000ED18} in GDB will explicitly show \texttt{0x00000000 0x80000000 0xe0e00000}.


\subsection{Step 9 and After: PRIMASK and Handing Over to C}
At this point, the runtime environment is fully built: RAM is populated, the vector table is registered, and faults are routed. It is finally safe to "open the gates". The \texttt{cpsie i} instruction clears the 1-bit \textbf{PRIMASK} register (equivalent to calling \texttt{\_\_enable\_irq()} in C), allowing the CPU to accept external interrupts again. Any interrupt that triggered while PRIMASK was 1 (masked) was kept in a "pending" state by the hardware and will execute immediately now.

With the hardware ready, the boot code hands over control to your C application using \texttt{bl main} (Branch with Link). The "with link" part means the CPU saves the return address in the Link Register (\texttt{lr}), treating \texttt{main} exactly like a standard function call.

However, in a bare-metal embedded system, there is no Operating System to return to. If \texttt{main()} ever reaches the end of its code or executes a \texttt{return} statement, the CPU would pop a return address, jump into empty or invalid memory, and crash. To prevent this catastrophic behavior, the assembly code provides a deliberate safety net: the \texttt{hang} label. By executing \texttt{b hang}, the processor gets safely trapped in an infinite loop forever.

\begin{lstlisting}
        cpsie i           /* enable interrupts again */
        bl main           /* call main(); saves return address in LR */
    hang:
        b hang            /* for (;;) {}: fallback if main returns */
\end{lstlisting}

\textit{Debugging tip:} Inspecting \texttt{info registers primask} will correctly show \texttt{0} at reset, \texttt{1} after \texttt{cpsid i} executes, and \texttt{0} again right before execution jumps to \texttt{main}.


\subsection{Checking the Configuration from GDB}
Once all boot steps are written, you should definitively prove that the hardware registers are correctly configured by the time \texttt{main} starts. With \texttt{make debug} running in your first terminal, execute the following in GDB to inspect the physical memory directly:

\begin{lstlisting}[language=bash]
    (gdb) target remote :1234
    (gdb) break main
    (gdb) continue
    (gdb) x/wx 0xE000ED08           # Inspect VTOR (Vector Table)
    (gdb) x/wx 0xE000ED24           # Inspect SHCSR (Fault Handlers)
    (gdb) x/wx 0xE000ED14           # Inspect CCR (Trap Config)
    (gdb) x/3wx 0xE000ED18          # Inspect SHPR1, SHPR2, SHPR3 (Priorities)
\end{lstlisting}

The expected memory values should perfectly match your assembly logic:
\begin{itemize}
    \item \textbf{VTOR:} \texttt{0x00000000} (unchanged, meaning the CPU will look for the vector table at address 0).
    \item \textbf{SHCSR:} \texttt{0x00070000}. This exactly matches bits 16, 17, and 18 being active (\texttt{0x7} is \texttt{0111} in binary).
    \item \textbf{CCR:} \texttt{0x00000210}. This is bit 4 (\texttt{0x10}, the division-by-zero trap you added) plus bit 9 (\texttt{0x200}, the stack alignment bit already set by the hardware at reset).
    \item \textbf{SHPR:} \texttt{0x00000000 0x80000000 0xe0e00000}.
\end{itemize}

\paragraph{Understanding Little-Endian Priority Bytes:} 
When GDB prints \texttt{0x80000000} for SHPR2, it is crucial to remember that the Cortex-M architecture is \textbf{little-endian}. This means the least significant byte (byte 0) is stored at the lowest memory address and is printed on the far right of the hex word.

Reading from right (byte 0) to left (byte 3):
\begin{itemize}
    \item \textbf{SHPR1} (\texttt{0x00000000}): Bytes 0, 1, and 2 are \texttt{0x00}. MemManage, BusFault, and UsageFault are correctly set to the highest configurable priority.
    \item \textbf{SHPR2} (\texttt{0x80000000}): Byte 3 is \texttt{0x80}, and the rest are \texttt{0x00}. SVCall correctly sits at priority \texttt{0x80}.
    \item \textbf{SHPR3} (\texttt{0xe0e00000}): Bytes 2 and 3 are \texttt{0xe0}. PendSV and SysTick correctly sit at the lowest priority (\texttt{0xE0}).
\end{itemize}

\subsection{Catching a Divide by Zero}
The configuration performed in the \texttt{Reset\_Handler} is only useful if it successfully catches real errors in the code. To prove this, we can write custom fault handlers in C and intentionally trigger a fault.

In \texttt{src/main.c} (right after \texttt{data\_message} and before \texttt{main}), you can write four functions utilizing the exact names defined in the vector table: \texttt{HardFault\_Handler}, \texttt{MemManage\_Handler}, \texttt{BusFault\_Handler}, and \texttt{UsageFault\_Handler}. Each function prints its own name using the same \texttt{semihost\_write0} function that \texttt{main} uses, and then enters an infinite loop:

\begin{lstlisting}[language=c]
void UsageFault_Handler(void)
{
    semihost_write0("UsageFault_Handler: a usage fault happened\n");
    for (;;) { }
}
\end{lstlisting}

Because these are normal (strong) C definitions, the linker uses them to silently replace the weak assembly defaults established in \texttt{boot/startup.s}. They loop forever because a fault represents a critical bug; there is no sensible way to continue execution safely.

\subsubsection{Triggering the Fault}
To test the handlers, we can force \texttt{main} to divide by zero. Crucially, the divisor must be a \texttt{volatile} variable holding \texttt{0}: without \texttt{volatile}, the compiler's optimizer will detect the constant division, compute or remove it entirely at compile time, and no physical divide instruction will ever be executed by the CPU.

Using a preprocessor switch allows us to toggle the demo safely:
\begin{lstlisting}[language=c]
    #define DEMO_DIVIDE_BY_ZERO 1

    /* Inside main() */
    #if DEMO_DIVIDE_BY_ZERO
        volatile uint32_t numerator = 42;
        volatile uint32_t zero = 0;
        volatile uint32_t result = numerator / zero;
        (void)result; /* Suppresses the 'unused variable' compiler warning */
    #endif
\end{lstlisting}

Running \texttt{make run} will successfully halt the program and print:
\begin{lstlisting}[language=bash]
UsageFault_Handler: a usage fault happened
\end{lstlisting}

\subsubsection{Validating the Configuration Steps}
The two hardware configuration steps implemented in the boot code (Steps 6 and 7) serve distinct, complementary purposes. You can observe exactly how they interact by temporarily commenting them out one at a time in the assembly file:

\begin{itemize}
    \item \textbf{Disabling Step 6 (SHCSR bits):} The CPU still detects the division by zero (thanks to Step 7), but the dedicated \texttt{UsageFault} handler remains disabled. Consequently, the ARM architecture automatically escalates the exception, and the terminal prints \texttt{HardFault\_Handler: a hard fault happened}. While the application safely halts, the specific diagnostic context---knowing \textit{why} it crashed---is permanently lost.
    \item \textbf{Disabling Step 7 (DIV\_0\_TRP):} You see no fault message at all. Without this bit, the Cortex-M3 hardware defaults to treating division by zero as a valid operation that simply returns \texttt{0}. The application silently proceeds with mathematically corrupted data, demonstrating precisely the kind of invisible, catastrophic bug this configuration is designed to prevent.
\end{itemize}

\subsection{What Real Chips Add: The \texttt{SystemInit} Function}
The QEMU emulator provides an idealized environment where the CPU is ready to execute at full speed the moment it leaves reset. Physical silicon, however, is bound by electrical constraints. On a real microcontroller, the startup sequence must perform critical hardware configuration before invoking \texttt{main}. This low-level setup is typically encapsulated in a vendor-supplied C function named \texttt{SystemInit()}, which is called from the assembly \texttt{Reset\_Handler} just before initializing the RAM.

While our emulator bypasses these physical necessities, understanding the responsibilities of a standard \texttt{SystemInit()} is essential for bare-metal development:
\begin{itemize}
    \item \textbf{Clock and PLL Configuration:} To guarantee a safe boot regardless of external conditions, microcontrollers wake up using a slow, stable Internal RC Oscillator (e.g., 8 MHz or 16 MHz). To achieve the chip's maximum performance, \texttt{SystemInit} configures the Phase-Locked Loop (PLL) to multiply that frequency and typically switches the main clock source to a precise external crystal.
    \item \textbf{Flash Wait States (Latency):} Physical Flash memory is fundamentally slower than a high-speed CPU core. Before ramping up the system clock via the PLL, the code \textit{must} configure the flash controller to insert extra "wait states" (latency cycles) into each memory access. Without this synchronization, a fast CPU would fetch invalid data from the slower Flash, causing an immediate crash.
    \item \textbf{Hardware Watchdog Timers:} A watchdog timer automatically resets the chip if the software hangs and fails to periodically "feed" (reset) it. On certain chips, the watchdog is hardware-activated immediately upon power-on. The boot code must either explicitly disable it or feed it early—otherwise, the chip might unexpectedly reset itself while still stuck in the \texttt{.data} copy loop, before \texttt{main} even starts.
    \item \textbf{FPU Enable (Floating-Point Unit):} On architectures like the Cortex-M4F or M7, the FPU is powered down at reset to conserve energy. It must be explicitly enabled by writing to the Coprocessor Access Control Register (\textbf{CPACR}, \texttt{0xE000ED88}). Executing a single \texttt{float} instruction before completing this setup triggers an immediate \texttt{UsageFault}.
    \item \textbf{C++ Static Constructors:} If the application or RTOS is written in C++, the startup code must explicitly iterate through the \texttt{.init\_array} section in memory, invoking the constructors of all global and static objects before finally branching to \texttt{main}.
\end{itemize}

\section{Life Without an Operating System}
Your program now boots entirely on code you explicitly wrote. This unit examines what is \textit{not} there and the architectural consequences of those missing layers. It culminates with the program's final structural form: \texttt{main} intentionally relinquishing its privileges and then requesting privileged work back through a formal system call.

\subsection{Hosted vs. Freestanding C Environments}
The C standard strictly defines two distinct execution environments for any C program.

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|l|}
\hline
 & \textbf{Hosted} & \textbf{Freestanding} \\ \hline
\textbf{Example} & Your laptop program & Our Cortex-M3 image \\ \hline
\textbf{Under your code} & A C library (\textbf{libc}) and an OS & Nothing \\ \hline
\textbf{\texttt{printf}, \texttt{malloc}, \texttt{fopen}, \texttt{exit}} & Available & Not available \\ \hline
\textbf{Who starts \texttt{main()}} & libc startup code, called by the OS & Whoever you decide \\ \hline
\end{tabular}
\end{table}

On a standard laptop, writing \texttt{printf("hi\textbackslash{}n")} "just works" because two massive, complex layers sit directly beneath your program doing the heavy lifting: the C library and the Operating System. Our embedded image operates in a \textbf{freestanding} environment. Below your bare-metal code, there is absolutely nothing.

\subsubsection{What is Available in Freestanding C?}
A freestanding environment still provides a subset of standard headers. However, these are strictly headers that require \textbf{no code execution at run time}. They provide only data types, architectural constants, and macros that the compiler resolves entirely at build time.

\begin{table}[h!]
    \centering
    \begin{tabular}{|l|l|}
        \hline
        \textbf{Header} & \textbf{Provides} \\ \hline
        \texttt{<stdint.h>} & \texttt{uint32\_t}, \texttt{int8\_t}, ... \\ \hline
        \texttt{<stddef.h>} & \texttt{size\_t}, \texttt{NULL}, \texttt{offsetof} \\ \hline
        \texttt{<stdbool.h>} & \texttt{bool}, \texttt{true}, \texttt{false} \\ \hline
        \texttt{<stdarg.h>} & \texttt{va\_list}, for variadic functions \\ \hline
        \texttt{<limits.h>}, \texttt{<float.h>} & \texttt{INT\_MAX}, \texttt{FLT\_EPSILON}, ... \\ \hline
    \end{tabular}
\end{table}

This is precisely why \texttt{src/main.c} only includes \texttt{<stdint.h>}. There is no \texttt{<stdio.h>}, no \texttt{<stdlib.h>}, and no \texttt{<string.h>}: this means no printing, no dynamic allocation (\texttt{malloc}), no file I/O, no \texttt{exit}, and not even \texttt{memcpy}. Anything else required by the system, you must write yourself. (This lack of standard library support is the exact reason the assembly boot code had to manually copy the \texttt{.data} section with its own explicit loop rather than just calling a convenient \texttt{memcpy}).

\subsection{What is Really Under \texttt{printf}}
To understand why standard functions fail without an OS, it helps to dissect what \texttt{printf} actually does under the hood on a hosted system (like a laptop):

\begin{lstlisting}[language=make]
+---------------------------------------------------+
| 1. USER PROGRAM                                   |
|    Codice: printf("x=%d\n", x);                   |
+---------------------------------------------------+
                          |
                          | (Formatta il testo in un buffer)
                          v
+---------------------------------------------------+
| 2. libc (Libreria Standard C)                     |
|    Codice: write(1, "x=5\n", 4);                  |
+---------------------------------------------------+
                          |
                          | (System Call: entra nel kernel)
                          v
+---------------------------------------------------+
| 3. OS KERNEL (Sistema Operativo)                  |
|    Gestisce la chiamata e la passa al Driver      |
+---------------------------------------------------+
                          |
                          | (Comandi fisici/elettrici)
                          v
+---------------------------------------------------+
| 4. HARDWARE                                       |
|    Schermo / Porta Seriale (UART)                 |
+---------------------------------------------------+
\end{lstlisting}

\texttt{printf} itself only performs \textbf{formatting}: it takes a format string like \texttt{"x=\%d\textbackslash{}n"} and the value of \texttt{x}, and parses them into a raw sequence of ASCII characters stored in a memory buffer. 

However, getting those physical characters out of the machine to a screen is not \texttt{printf}'s job. To do that, it calls \texttt{write()}, which triggers a \textbf{system call}. A system call forces the CPU to enter the Operating System kernel. The kernel's specific device driver then takes over, physically sending the bytes to the terminal, a file, or a serial hardware device.

\texttt{printf} is not the only C library feature that relies on hidden, lower-level OS hooks:

\begin{table}[h!]
    \centering
    \begin{tabular}{|l|l|}
        \hline
        \textbf{libc feature} & \textbf{What it needs underneath} \\ \hline
        \texttt{printf}, \texttt{puts} & \texttt{write()}: a way to send bytes to a physical device \\ \hline
        \texttt{malloc}, \texttt{free} & a heap memory region, dynamically grown via \texttt{sbrk()} \\ \hline
        \texttt{exit} & an OS process manager to return control to \\ \hline
        \texttt{main()} being called & startup code (\textbf{crt0}): sets up the stack, \texttt{.data}, \texttt{.bss}, then calls \texttt{main} \\ \hline
    \end{tabular}
\end{table}

C libraries designed for embedded systems (such as \textbf{newlib}) implement the high-level formatting logic and data structures, but they intentionally leave these bottom-level hardware functions as empty \textbf{hooks} (stubs) that the developer must manually implement for their specific physical board.

\subsection{Why This Course Uses No libc At All}
There are three fundamental reasons we deliberately avoid linking any C library at all:
\begin{enumerate}
    \item \textbf{No Underlying Kernel Hooks:} Without an OS beneath us, nothing implements those required hooks. There is no kernel, no \texttt{write()} function, and no heap manager; if we linked libc, we would have to write these complex low-level stubs first anyway just to satisfy the linker.
    \item \textbf{Redundant Startup Logic:} The job of \texttt{crt0} (the standard libc startup code that prepares the C environment) is already perfectly handled by the custom \texttt{Reset\_Handler} we built in \texttt{boot/startup.s} (setting up the stack, copying \texttt{.data}, clearing \texttt{.bss}, and branching to \texttt{main}).
    \item \textbf{Absolute Visibility:} The primary educational goal is to \textbf{see every single layer}. Every byte that executes on the board is code you can actively read in the repository. The final compiled image contains exclusively \texttt{boot/startup.s}, \texttt{src/main.c}, and occasionally a few necessary compiler helper routines. Absolutely nothing is hidden from the developer.
\end{enumerate}

\subsection{Bypassing \texttt{libc}: The \texttt{printf} Problem}
If there is no OS kernel and no physical UART driver, how did our bare-metal program successfully print text to the laptop's terminal?

Why not just use standard \texttt{printf}? In a freestanding embedded environment, calling \texttt{printf} routes through the C standard library (like \texttt{newlib}). This library eventually attempts to invoke a low-level system call (like \texttt{\_write}) to pass the buffer to the OS. Since we have no OS, the call would crash or fail silently. Furthermore, our minimal \texttt{Reset\_Handler} does not perform the heavy C-runtime initialization required by standard I/O. To bypass this entirely, we use a technique called \textbf{semihosting}.

\subsection{Semihosting: How the Program Still Prints}
Semihosting is a hardware debug mechanism. It allows the embedded program to intentionally trap (pause execution and signal the debugger—in our case, QEMU) to request that the host machine perform I/O operations on the target's behalf.

Instead of driving real physical hardware, the execution follows this precise sequence:
\begin{enumerate}
    \item The target program places a specific operation code into register \texttt{r0}. We use \texttt{0x04} (\texttt{SYS\_WRITE0}), which means "print this null-terminated string".
    \item It places the memory address of the string into register \texttt{r1}.
    \item It executes \texttt{bkpt 0xab}: a software breakpoint instruction tagged with a special identifier recognized by ARM debuggers.
    \item QEMU intercepts this breakpoint, halts the emulated CPU, reads \texttt{r0} and \texttt{r1}, fetches the string directly from the target's RAM, and prints it to your host terminal.
    \item Once finished, QEMU commands the CPU to seamlessly resume execution.
\end{enumerate}

\subsection{Implementing Semihosting in C (\texttt{main.c})}
To achieve this without an operating system, the C implementation in \texttt{src/main.c} uses GNU C Extended Inline Assembly to force the CPU to fulfill this rigid hardware contract:

\begin{lstlisting}[language=c]
#include <stdint.h>

static void semihost_write0(const char *message)
{
    /* 1. Load Operation Code into physical r0 */
    register uint32_t r0 __asm__("r0") = 0x04;
    
    /* 2. Load String Address into physical r1 */
    register const char *r1 __asm__("r1") = message;
    
    /* 3. Execute the hardware trap */
    __asm__ volatile ("bkpt 0xab" : : "r"(r0), "r"(r1) : "memory");
}
\end{lstlisting}

This small function leverages three advanced compiler features:
\begin{itemize}
    \item \textbf{Explicit Register Binding:} The \texttt{register ... \_\_asm\_\_("rX")} syntax is a GCC extension that forces the compiler to place the variable into a specific physical CPU register. Standard C cannot guarantee register allocation, but the semihosting ABI strictly demands \texttt{r0} and \texttt{r1}.
    \item \textbf{Volatile Assembly:} \texttt{\_\_asm\_\_ volatile} inserts the raw \texttt{bkpt 0xab} machine instruction. The \texttt{volatile} keyword is crucial: it prevents the compiler from optimizing the instruction away (which it might otherwise do, assuming an instruction with no C-visible outputs is useless).
    \item \textbf{Memory Barrier:} The \texttt{"memory"} clobber at the end is a critical safeguard. It explicitly warns the compiler that this assembly instruction might read from arbitrary memory (our string). This prevents the optimizer from reordering memory writes, guaranteeing the entire string is safely stored in RAM before QEMU halts the CPU to read it.
\end{itemize}

\subsection{Semihosting as a System Call Proxy}
Look closely at what \texttt{bkpt 0xab} really does: the program stops executing its own code, passes control to a higher-privileged entity (QEMU, acting from outside the emulated CPU), asks it to perform an action, and waits for control to be returned.

This is the exact architectural shape of a Linux system call. Because your bare-metal program lacks an OS kernel to drive a terminal, it uses the debugger as a proxy OS to achieve the same result.

\subsection{Privileged and Unprivileged Code on Cortex-M}
The Cortex-M3 implements the kernel/user mode concept directly in hardware, combined with the two CPU modes:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|l|}
\hline
\textbf{CPU mode} & \textbf{When} & \textbf{Privilege} \\ \hline
\textbf{Handler} mode & running an exception handler & always \textbf{privileged} \\ \hline
\textbf{Thread} mode & normal code (\texttt{main}, ...) & privileged \textbf{or} unprivileged \\ \hline
\end{tabular}
\end{table}

After reset, the CPU defaults to Thread mode and is \textbf{privileged}. That is exactly how \texttt{Reset\_Handler} was able to freely write to VTOR, SHCSR, and CCR. \textbf{Unprivileged} Thread mode is the equivalent of user mode: the restricted mode for code that a kernel would not trust.

\subsubsection{The CONTROL Register}
Which privilege level Thread mode uses is selected by the \textbf{CONTROL} register, a special register inside the CPU (like PRIMASK, it is not mapped in standard memory):

\begin{table}[h!]
    \centering
    \begin{tabular}{|l|l|l|}
        \hline
        \textbf{Bit} & \textbf{Name} & \textbf{Meaning} \\ \hline
        0 & \textbf{nPRIV} & 0 = privileged, 1 = unprivileged (Thread mode only) \\ \hline
        1 & SPSEL & selects which stack pointer Thread mode uses (not used here) \\ \hline
    \end{tabular}
\end{table}

Because special registers are not reachable with standard \texttt{ldr} and \texttt{str} instructions, two dedicated instructions are used to read and write them:

\begin{table}[h!]
    \centering
    \begin{tabular}{|l|l|}
        \hline
        \textbf{Instruction} & \textbf{C equivalent} \\ \hline
        \texttt{mrs r0, control} & \texttt{r0 = CONTROL;} (read a special register) \\ \hline
        \texttt{msr control, r0} & \texttt{CONTROL = r0;} (write a special register) \\ \hline
    \end{tabular}
\end{table}

\subsection{Dropping Privilege: A One-Way Street}
In \texttt{src/main.c}, after the first two lines are printed, the program intentionally drops its own privilege using a short block of inline assembly:

\begin{table}[h!]
    \centering
    \begin{tabular}{|l|l|}
        \hline
        \textbf{ARM Assembly} & \textbf{C Equivalent} \\ \hline
        \texttt{mrs r0, control} & \texttt{uint32\_t r0 = CONTROL;} \\
        \texttt{orr r0, r0, \#1} & \texttt{r0 = r0 | 1;} \\
        \texttt{msr control, r0} & \texttt{CONTROL = r0;} \\
        \texttt{isb} & \textit{(Pipeline flush)} \\ \hline
    \end{tabular}
\end{table}

This is the standard read-modify-write pattern, applied here to the special \textbf{CONTROL} register. Setting bit 0 (\texttt{nPRIV}) to 1 forces the CPU into unprivileged execution. 

The final instruction, \texttt{isb} (Instruction Synchronization Barrier), is absolutely critical. Modern CPUs are heavily pipelined and fetch instructions well ahead of the current execution point. Without \texttt{isb}, the instructions immediately following the privilege drop might have already been fetched under the old, privileged rules. The \texttt{isb} instruction flushes the CPU pipeline, discarding those pre-fetched instructions and forcing the processor to re-fetch them under the newly enforced unprivileged rules.

\textbf{The Privilege Trap:} This transition is a \textbf{one-way street}. Writing to the CONTROL register is inherently a privileged operation. If unprivileged code attempts to execute \texttt{msr control, r0} to clear the \texttt{nPRIV} bit and regain privilege, the hardware treats it as a security violation and silently \textbf{ignores} the write. Code cannot maliciously promote itself. There are only two ways back to a privileged state: a full hardware \textbf{reset}, or triggering \textbf{an exception} (because exception handlers automatically run in Handler mode, which is unconditionally privileged by hardware design).

\subsection{What Unprivileged Code Cannot Do (The Sandbox)}
Once restricted, the CPU actively blocks critical operations to create a secure sandbox. The processor enforces the following constraints:

\begin{table}[h!]
    \centering
    \begin{tabular}{|p{0.55\linewidth}|l|}
        \hline
        \textbf{Attempted Action} & \textbf{Hardware Response} \\ \hline
        Read/Write the \textbf{System Control Space} (\texttt{0xE000E000} and above, which includes SysTick, NVIC, SCB) & \textbf{BusFault} \\ \hline
        Write to the \textbf{CONTROL} register to regain privilege & \textbf{Silently Ignored} \\ \hline
        Execute \texttt{cpsid i} / \texttt{cpsie i} to mask/unmask interrupts & \textbf{Silently Ignored} \\ \hline
        Execute \texttt{bkpt 0xab} (Semihosting trap) & \textbf{HardFault} (Debugger refuses) \\ \hline
    \end{tabular}
\end{table}

\textit{(Note: The NVIC is the hardware block that manages device interrupts; it lives in the exact same restricted system memory area as the SCB).}

Ordinary RAM, flash memory, and standard code execution continue to work normally. The restricted code simply cannot \textbf{reconfigure the machine}, and it cannot silence the system by masking interrupts.

\subsubsection{Try It: The HardFault Escalation}
The semihosting restriction provides a highly observable tripwire. If you attempt to execute \texttt{semihost\_write0("main: unprivileged hello\textbackslash{}n");} immediately after the privilege-drop block, the terminal yields:

\begin{lstlisting}[language=bash]
main: privileged hello
main: this text lives in .data
HardFault_Handler: a hard fault happened
\end{lstlisting}

Your unprivileged line never prints. By stepping through the code in GDB, you can see exactly when the execution state shatters. As soon as the CPU attempts to execute the \texttt{bkpt 0xab} instruction inside the \texttt{semihost\_write0} function, QEMU actively rejects the unauthorized debug request. The hardware treats it as a strict security violation and instantly escalates it to Exception 3: \textbf{HardFault}.

Notice a crucial architectural detail: the \texttt{HardFault\_Handler} \textit{is} able to print its error message via semihosting, even though the Thread code that caused the fault was completely unprivileged. Entering an exception handler automatically forces the CPU into Handler mode, seamlessly restoring full hardware privileges. \textit{(Remember to remove the offending line in main before continuing).}

\subsubsection{Debugging the CONTROL Register}
You can capture the \texttt{nPRIV} bit flip and the ensuing crash by stepping through the execution in GDB:

\begin{lstlisting}[language=bash]
(gdb) target remote :1234
(gdb) break main
(gdb) continue
(gdb) p/x $control
$1 = 0x0                  # 0x0: Thread mode is currently Privileged

# ... step through the first prints and the inline assembly block ...

(gdb) stepi               # Execute the privilege drop (msr control, r0)
(gdb) p/x $control
$2 = 0x1                  # 0x1: Thread mode is now securely Unprivileged!

# ... step into the forbidden semihost_write0 call ...

(gdb) stepi               # Execute bkpt 0xab
HardFault_Handler () at src/main.c:35
(gdb) p/x $control
$4 = 0x1                  # The bit is still 1!
\end{lstlisting}

\textbf{The Handler Mode Override:} Seeing \texttt{\$control = 0x1} inside the \texttt{HardFault\_Handler} reveals a profound paradigm of the Cortex-M architecture. The \texttt{nPRIV} bit in the CONTROL register \textit{only} dictates the privilege level of \textbf{Thread mode} (the background application). \textbf{Handler mode} (processing exceptions and interrupts) is unconditionally privileged by hardware design. Therefore, the fault handler can successfully execute its own \texttt{bkpt 0xab} instruction despite the CONTROL register still indicating an unprivileged background state.

\subsection{SVC: The Door That Stays Open}
Unprivileged code is strictly blocked from touching hardware directly, but it is still allowed to \textbf{ask} for tasks to be done on its behalf. The \texttt{svc \#n} ("Supervisor Call") instruction is explicitly designed to be executed by unprivileged code.

When executed, it raises the \textbf{SVCall} exception (Exception 11), instantly transferring execution to the \texttt{SVC\_Handler} defined in slot 11 of the vector table. Because it is an exception, the CPU switches into Handler mode, meaning the handler runs fully \textbf{privileged}. When the handler completes and returns, the CPU drops back into Thread mode, resuming execution at the instruction immediately following the \texttt{svc}—\textbf{still entirely unprivileged}.

\begin{lstlisting}
 Thread mode, UNPRIVILEGED               Handler mode, PRIVILEGED
 -------------------------               ------------------------
 main:
   ...
   svc #0  ----- SVCall exception ----> SVC_Handler:
                                          semihost_write0("...")
                                          (Can print, can configure
                                           SysTick, NVIC, SCB)
   next instruction <--- exception return --- return
   ... (still unprivileged)
\end{lstlisting}

Hardware privilege is \textbf{borrowed} only for the strict duration of the handler, and only the specific, trusted code \textit{you} compiled into the handler runs with it. The unprivileged application does not get to choose what the handler executes; it can only knock on the door.

The number \texttt{\#n} inside \texttt{svc \#n} is encoded directly into the machine instruction. Real OS kernels read this number (often combined with arguments passed in registers like \texttt{r0}-\texttt{r3}) to determine \textit{which} specific system service the user application is requesting. For our bare-metal proof of concept, there is only one service, so we simply execute \texttt{svc \#0}.


\subsection{This Is a System Call}
Compare this bare-metal sequence directly with what happens on a standard desktop environment:

\begin{table}[h!]
    \centering
    \begin{tabular}{|l|l|l|}
        \hline
        \textbf{Concept} & \textbf{Linux on your laptop} & \textbf{Our Cortex-M3} \\ \hline
        \textbf{Restricted code} & User-space application & \texttt{main()} after \texttt{nPRIV} = 1 \\ \hline
        \textbf{Trap instruction} & \texttt{syscall} (x86-64), \texttt{svc} (ARM) & \texttt{svc \#0} \\ \hline
        \textbf{Privileged side} & The OS Kernel & \texttt{SVC\_Handler} \\ \hline
        \textbf{Requested Service} & \texttt{write()} (print to terminal) & Print via semihosting \\ \hline
    \end{tabular}
\end{table}

The architectural mechanism remains identical at every scale. The restricted side cannot safely perform a privileged job itself, so it intentionally traps into code that can. That privileged code securely evaluates the request, performs the action, and returns control. The \texttt{write()} system call located at the bottom of the \texttt{libc} stack on your laptop works via this exact paradigm.


\subsection{Adding the System Call}
The final steps to turn this theory into working code occur in \texttt{src/main.c}.

First, write the \texttt{SVC\_Handler}. It prints a message using \texttt{semihost\_write0} and safely returns:

\begin{lstlisting}[language=c]
void SVC_Handler(void)
{
    semihost_write0("SVC Handler: privileged code printing on behalf of unprivileged code\n");
}
\end{lstlisting}

Unlike the hardware fault handlers you wrote earlier, this function does \textit{not} end in an infinite loop. An \texttt{svc} trap is a deliberate, synchronous request for service, not a fatal bug. Reaching the end of the C function triggers a clean exception return, dropping privileges and jumping back to the instruction after \texttt{svc \#0}. 

\textit{(Note: A standard C function can serve flawlessly as an exception handler on the Cortex-M architecture because the hardware automatically pushes and pops the caller-saved registers to the stack upon exception entry and exit).}

Next, immediately after the privilege drop in \texttt{main}, insert the trap instruction using inline assembly:

\begin{lstlisting}[language=c]
    __asm__ volatile ("svc #0" ::: "memory");
\end{lstlisting}

Executing \texttt{make run} now correctly yields the expected output, confirming the handler executed and returned successfully:
\begin{lstlisting}[language=bash]
    main: privileged hello
    main: this text lives in .data
    SVC Handler: privileged code printing on behalf of unprivileged code
\end{lstlisting}

\textit{Troubleshooting tip:} If you forget to write the \texttt{SVC\_Handler} explicitly in C, the \texttt{svc} instruction seamlessly lands in the weak \texttt{Default\_Handler} defined in \texttt{boot/startup.s}. The program will silently hang in that infinite loop—proving that the weak default fallback successfully did its job.


\subsection{Touching the Hardware Without Privilege}
Finally, to definitively verify that the hardware sandbox is actively enforced, we will attempt a malicious action. 

After the \texttt{svc \#0} line, while \texttt{main} is still running unprivileged, attempt to write \texttt{0} into the SysTick timer's control register (located at \texttt{0xE000E010} in the restricted System Control Space):

\begin{lstlisting}[language=c]
    volatile uint32_t *systick_ctrl = (volatile uint32_t *) 0xE000E010;
    *systick_ctrl = 0;
\end{lstlisting}

Recompile the project and run it again in your terminal:
\begin{lstlisting}[language=bash]
    make: 
        main: hello from the base
        main: this text lives in .data
        main: privileged hello
        main: this text lives in .data
        SVC Handler: privileged code printing on behalf of unprivileged code
        BusFault_Handler: a bus fault happened
\end{lstlisting}
\textit{(Note: Ensure your \texttt{SVC\_Handler} string ends with a \texttt{\textbackslash{}n} so the \texttt{BusFault} message prints cleanly on a new line, rather than colliding with the previous output!)}

This terminal output perfectly validates the entire architecture. First, it proves that the \texttt{svc} handler successfully returned execution to the unprivileged code. Second, it proves that the System Control Space hardware actively intercepted the unprivileged store instruction and blocked it, forcing the CPU to raise a \textbf{BusFault}. Because the \texttt{Reset\_Handler} previously enabled discrete bus faults via the SHCSR, the fault routed directly to its own specific handler, instantly identifying the precise nature of the security violation.

\subsubsection{Conclusion: Privilege and CPU Modes}
One final observation completes the picture. In GDB, put a breakpoint on \texttt{SVC\_Handler}, \texttt{continue} execution, and print \texttt{\$control} inside the handler: it is still \texttt{0x1}. 

The handler is privileged \textit{not} because the \texttt{nPRIV} bit magically cleared itself, but because the CPU is currently running in \textbf{Handler mode}. The Cortex-M architecture strictly dictates that Handler mode is unconditionally privileged, overriding whatever the \texttt{CONTROL} register says about the background Thread mode. This dual-mode design ensures the kernel can always recover, manage faults, and serve user applications securely.

\subsection*{1.2 Analisi della Mappa di Memoria}
L'immagine in formato TikZ illustra la dicotomia fondamentale dei sistemi embedded bare-metal: la separazione netta tra l'immagine fisica memorizzata (LMA) e la sua proiezione a runtime (VMA). Analizziamo lo schema seguendo i tre blocchi logici principali.

\subsubsection*{Il lato sinistro: FLASH (Load Memory Address - LMA)}
La FLASH è la memoria permanente, mappata a partire dall'indirizzo \texttt{0x00000000}. Nei microcontrollori questa memoria opera in modalità \textit{Execute-in-Place} (XIP): il processore preleva ed esegue le istruzioni direttamente da qui, senza doverle prima caricare in RAM.

Procedendo dall'alto verso il basso:
\begin{itemize}
    \item \textbf{\texttt{.isr\_vector} (Vector Table):} Deve risiedere obbligatoriamente all'inizio della memoria (\texttt{0x00000000}). L'hardware è progettato per leggere le prime due word a questo indirizzo al momento del boot per inizializzare lo Stack Pointer e il Program Counter.
    \item \textbf{\texttt{.text} e \texttt{.rodata}:} Subito dopo troviamo il codice compilato e i dati in sola lettura (come le stringhe letterali e le costanti). Questi elementi non verranno mai modificati durante l'esecuzione, pertanto restano permanentemente in FLASH.
    \item \textbf{\texttt{.data} (LMA):} Qui risiede il cuore del problema architettonico. Se nel codice viene dichiarata una variabile come \texttt{int x = 5;}, il valore iniziale "5" deve sopravvivere a un riavvio. Il Linker Script archivia questo valore in FLASH, identificando il suo punto di inizio fisico con il simbolo \texttt{\_sidata}.
\end{itemize}

\subsubsection*{Il lato destro: SRAM (Virtual Memory Address - VMA)}
La SRAM è la memoria di lavoro volatile e ad alta velocità, mappata a partire dall'indirizzo \texttt{0x20000000}. Qui è dove le variabili del programma risiedono attivamente (VMA significa \textit{Virtual/Run Memory Address}).

Procedendo dal basso verso l'alto (indirizzi crescenti):
\begin{itemize}
    \item \textbf{\texttt{.data} (VMA):} Questa è la destinazione fisica delle variabili inizializzate durante l'esecuzione. Lo spazio è delimitato dai simboli \texttt{\_sdata} (inizio) ed \texttt{\_edata} (fine).
    \item \textbf{\texttt{.bss}:} Contiene le variabili globali non inizializzate, che secondo lo standard C devono valere zero di default. Questa sezione non occupa spazio fisico nella FLASH (non ha un LMA), ma è solo spazio allocato in RAM che dovrà essere azzerato via software.
    \item \textbf{Heap e Stack (Memoria Dinamica):} Il sistema prevede due aree che si espandono a runtime in direzioni opposte all'interno della porzione rimanente di RAM.
    \begin{itemize}
        \item L'\textbf{Heap} parte dalla fine della \texttt{.bss} (\texttt{\_heap\_bottom}) e cresce verso l'alto (indirizzi crescenti).
        \item Lo \textbf{Stack} del Cortex-M parte dalla cima assoluta della RAM (\texttt{\_estack}, calcolato a \texttt{0x20400000}) e decresce verso il basso (architettura \textit{full-descending}).
        \item \textbf{\texttt{\_\_StackLimit}:} È una linea di guardia di sicurezza. Il Linker Script usa una direttiva \texttt{ASSERT} per assicurarsi matematicamente in fase di compilazione (\textit{build-time}) che l'Heap e lo Stack non si incrocino mai. Se si scontrassero a runtime, sovrascriverebbero reciprocamente i propri dati causando crash catastrofici e imprevedibili.
    \end{itemize}
\end{itemize}

\subsubsection*{La Freccia Verde: Il "Boot Copy"}
Questa singola freccia rappresenta concettualmente il ruolo fondamentale del codice Assembly nel \texttt{Reset\_Handler} (\texttt{startup.s}).

All'accensione, la SRAM contiene solo uno stato elettrico casuale (spazzatura non inizializzata). Il runtime C pretende che le variabili globali abbiano i loro valori pronti prima di iniziare a eseguire la funzione \texttt{main()}. Poiché in un ambiente \textit{bare-metal} non abbiamo un Sistema Operativo che esegue un loader al posto nostro[cite: 13, 52], il nostro codice Assembly agisce da ponte: legge i byte dall'indirizzo di partenza \texttt{\_sidata} (LMA in FLASH) e li copia uno per uno nel range target compreso tra \texttt{\_sdata} e \texttt{\_edata} (VMA in RAM).

Senza l'azione rappresentata da questa freccia, il codice C tenterebbe di leggere la variabile in RAM e troverebbe un valore del tutto casuale ereditato dall'accensione.


\subsection{1.3 Reset: Il Contratto Hardware e \texttt{boot.s}}
Quando il microcontrollore Cortex-M3 riceve alimentazione, non esiste ancora alcun ambiente C o runtime valido[cite: 31]. Il processore segue invece un rigoroso "contratto hardware" automatico composto da due soli passaggi: preleva la word all'indirizzo \texttt{0x0} e la inserisce nello Stack Pointer (SP), dopodiché preleva la word all'indirizzo \texttt{0x4}, la carica nel Program Counter (PC) e inizia l'esecuzione da quell'indirizzo[cite: 32]. Tutto il resto dell'inizializzazione del sistema (come copiare la sezione \texttt{.data} e azzerare la \texttt{.bss}) è esclusiva responsabilità del codice Assembly \textit{bare-metal} contenuto in \texttt{boot/startup.s}[cite: 32].

\begin{figure}[h]
    \centering
    \includegraphics[width=0.8\textwidth]{contents/images/week_02/cortex_m3_reset_contratto_hardware.png}
    \caption{Step iniziali Hardware Reset}
\end{figure}

Questi due indirizzi iniziali costituiscono l'inizio della \textbf{Vector Table}, un array collocato rigidamente a \texttt{0x00000000}, in cui ogni slot \textit{N} contiene l'indirizzo di memoria dell'handler per l'eccezione \textit{N}[cite: 32]. Questa struttura è soggetta a due vincoli architettonici cruciali:
\begin{itemize}
    \item \textbf{Thumb Bit Constraint:} Essendo il Cortex-M3 capace di eseguire esclusivamente codice Thumb, l'hardware pretende che il bit meno significativo (bit 0) degli indirizzi di esecuzione nella Vector Table sia impostato a 1[cite: 33].
    \item \textbf{Garbage Collection:} Poiché il software applicativo non invoca mai direttamente questa tabella, il linker tenderebbe a eliminarla per ottimizzare lo spazio; per evitare un blocco fatale al boot, si utilizza la direttiva \texttt{KEEP} nel Linker Script per forzarne il mantenimento nell'immagine finale[cite: 33].
\end{itemize}

Queste meccaniche spiegano perché il programma base stampa solo la prima stringa: le stringhe letterali residenti in \texttt{.rodata} (FLASH) vengono lette direttamente e stampate con successo, mentre le variabili globali in \texttt{.data} (RAM) risultano vuote poiché il ciclo Assembly responsabile di copiare i loro valori iniziali dalla FLASH alla RAM non è ancora stato implementato[cite: 34, 35].

\subsection{1.4 Il Controllo della CPU: Debugger e Assembly}
Senza un sistema operativo, un errore di esecuzione non genera messaggi di crash, ma si traduce in un blocco silenzioso della macchina[cite: 35]. L'unico modo per diagnosticare lo stato della CPU è affidarsi a un \textbf{debugger remoto}: l'emulatore QEMU simula l'hardware (FLASH, RAM, CPU) e funge da server TCP sulla porta 1234, mentre il client GDB sul terminale dell'utente si connette per ispezionare o alterare il flusso di esecuzione[cite: 35].

Tramite GDB è possibile esplorare il \textit{Programmer's Model}, ovvero l'insieme dei registri visibili:
\begin{itemize}
    \item \textbf{R0--R12:} Registri general-purpose[cite: 37].
    \item \textbf{R13 (SP), R14 (LR), R15 (PC):} Rispettivamente Stack Pointer, Link Register (per gli indirizzi di ritorno) e Program Counter[cite: 37].
    \item \textbf{xPSR (Status Register):} Un registro vitale che aggrega i flag logico-aritmetici (NZCV), il bit Thumb e il numero dell'eccezione corrente[cite: 37]. Quest'ultimo campo determina fisicamente la modalità operativa della CPU: \textit{Thread mode} per l'esecuzione normale (eccezione 0) o \textit{Handler mode} durante il processamento di un'interruzione[cite: 37, 38].
\end{itemize}

\begin{figure}[h]
    \centering
    \includegraphics[width=0.8\textwidth]{contents/images/week_02/registri_arm_cortex_m3.png}
    \caption{Schema concettuale: registers categories}
\end{figure}

Per interagire con questi registri al momento del boot, è necessario padroneggiare i fondamenti dell'Assembly ARM, che segue un'architettura rigidamente \textbf{Load/Store}: le operazioni matematiche avvengono esclusivamente tra registri, e la memoria può essere letta o scritta solo tramite istruzioni \texttt{ldr} e \texttt{str}[cite: 38]. Infine, a causa della dimensione fissa delle istruzioni a 16 o 32 bit, l'Assembly non può caricare direttamente costanti a 32 bit inline; delega questo compito a un \textbf{Literal Pool} (creato con la direttiva \texttt{.ltorg}), da cui la CPU carica le costanti calcolando l'indirizzo in relazione al Program Counter[cite: 38, 39].


\subsection*{1.5 Scrittura del Boot Script (\texttt{Reset\_Handler})}
Il \texttt{Reset\_Handler} ha un compito fondamentale: trasformare una CPU "nuda" appena alimentata in un ambiente in grado di eseguire codice C in totale sicurezza[cite: 34]. Questo processo si articola in una sequenza rigorosa di sette passaggi logici: mascherare gli interrupt, inizializzare lo stack, copiare la sezione \texttt{.data}, azzerare la \texttt{.bss}, configurare i registri di sistema, passare il controllo alla funzione \texttt{main} e garantire un fallback in caso di ritorno[cite: 34].

\begin{figure}[h]
    \centering
    \includegraphics[width=0.8\textwidth]{contents/images/week_02/reset_handler_costruzione_ambiente_c.png}
    \caption{Schema concettuale: costruzione ambiente}
\end{figure}

\subsubsection*{Step 1 e 2: Mascherare gli Interrupt e Impostare lo Stack}
La primissima istruzione eseguita, \texttt{cpsid i}, impone alla CPU di ignorare qualsiasi interrupt hardware[cite: 34]. Questo è vitale perché l'ambiente C (variabili e stack) non è ancora stato costruito; se un handler in C tentasse di eseguire durante questa fase transitoria, il sistema crasherebbe[cite: 34].

Successivamente, il codice inizializza lo Stack Pointer (SP)[cite: 34]. Nonostante l'hardware carichi automaticamente il valore di \texttt{\_estack} dalla Vector Table al momento del reset, sovrascriverlo esplicitamente via software (\texttt{ldr r0, =\_estack} seguito da \texttt{mov sp, r0}) garantisce che il sistema si avvii correttamente anche se invocato da un bootloader custom o da un debugger che ha bypassato la sequenza di reset hardware[cite: 34, 35].

\subsubsection*{Step 3: Copiare \texttt{.data} dalla FLASH alla RAM}
Questo step risolve il problema delle variabili globali inizializzate (come l'array \texttt{data\_message})[cite: 35]. Un ciclo Assembly trasferisce fisicamente i valori di inizializzazione dalla memoria permanente FLASH (a partire dal Load Memory Address \texttt{\_sidata}) alla memoria di lavoro RAM (nel range delimitato dai Virtual Memory Address \texttt{\_sdata} ed \texttt{\_edata})[cite: 35].

Ispezionando l'esecuzione \textit{step-by-step} in GDB, è possibile osservare il meccanismo hardware in azione: la CPU utilizza il \textit{Literal Pool} per caricare gli indirizzi a 32 bit, e ad ogni ciclo i registri si incrementano popolando concretamente la SRAM con i byte corretti della stringa[cite: 35, 36, 37]. 

\paragraph*{Rompere lo Stack intenzionalmente} Per dimostrare l'assoluta criticità dello Stack Pointer, si possono condurre due test distruttivi[cite: 37]:
\begin{itemize}
    \item \textbf{Indirizzo fuori dalla RAM (\texttt{0x30000000}):} Provoca un blocco terminale noto come \textbf{Lockup}[cite: 37]. Al primo tentativo di scrittura su stack, la CPU genera un fault; l'hardware tenta allora di salvare automaticamente il contesto (\textit{exception frame}) per invocare l'handler del fault, ma fallendo nuovamente a causa dello stack corrotto, genera un errore irrisolvibile[cite: 37].
    \item \textbf{Indirizzo disallineato (\texttt{0x20000001}):} Genera un fallimento silenzioso[cite: 37]. Il Cortex-M3 impone un allineamento rigoroso a 32 bit, troncando automaticamente i due bit meno significativi (forzando l'indirizzo a \texttt{0x20000000})[cite: 37]. Poiché l'architettura è \textit{full-descending}, il primissimo inserimento decrementa il puntatore a \texttt{0x1FFFFFFC} (fuori dalla RAM), causando l'impossibilità di salvare gli indirizzi di ritorno per le chiamate a funzione[cite: 37].
\end{itemize}

\subsubsection*{Step 4: Azzerare la sezione \texttt{.bss}}
Lo standard C garantisce rigorosamente che le variabili globali prive di inizializzazione esplicita assumano valore zero all'avvio del programma[cite: 37]. Siccome al power-on la RAM fisica contiene esclusivamente dati elettrici casuali, il boot code deve iterare sull'intero blocco di memoria compreso tra \texttt{\_sbss} ed \texttt{\_ebss}, scrivendo fisicamente degli zeri in ogni singolo indirizzo[cite: 37, 38].



\subsection*{1.6 Eccezioni, Fault e Configurazione della CPU}
La CPU Cortex-M3 utilizza una famiglia di eccezioni per gestire sia gli interrupt esterni sia gli errori di esecuzione (i Fault)[cite: 38]. Al momento dell'accensione, la maggior parte dei fault specifici è disabilitata; di conseguenza, qualsiasi errore critico \textit{escala} automaticamente nell'unica eccezione sempre attiva: l'\texttt{HardFault}[cite: 39]. Questo comportamento unifica tutti gli errori in un singolo calderone, rendendo impossibile la diagnosi precisa del problema[cite: 39, 41].

\subsubsection*{Completare la Vector Table con i Weak Symbols}
La Vector Table deve contenere obbligatoriamente un indirizzo valido per ciascuno dei 16 slot architetturali, anche per le eccezioni non ancora implementate[cite: 39]. Invece di scrivere 16 funzioni C vuote, il codice Assembly popola la tabella utilizzando la direttiva \texttt{.weak} e \texttt{thumb\_set}[cite: 39].
\begin{itemize}
    \item Tutti i gestori (es. \texttt{UsageFault\_Handler}) vengono aliasati a un singolo \texttt{Default\_Handler}, che consiste in un loop di blocco infinito[cite: 39].
    \item Il termine \textit{weak} istruisce il Linker: se lo sviluppatore definisce una funzione C standard con lo stesso nome, il Linker scarta silenziosamente il default Assembly e instrada l'eccezione hardware direttamente alla funzione C[cite: 39].
\end{itemize}

\subsubsection*{Registri Mappati in Memoria e il Pattern RMW}
Le impostazioni interne del core Cortex-M3 risiedono nel System Control Space (SCS), una porzione di memoria fissa a partire da \texttt{0xE000E000}[cite: 40]. L'interazione con questi registri in Assembly e in C richiede due accortezze fondamentali:
\begin{itemize}
    \item \textbf{Pattern Read-Modify-Write (RMW):} Si legge l'intero registro, si alterano esclusivamente i bit desiderati tramite un \texttt{OR} logico e si riscrive il valore[cite: 40]. Una sovrascrittura diretta azzererebbe inavvertitamente altri bit di stato critici (es. il bit di allineamento dello stack)[cite: 40, 42].
    \item \textbf{Keyword \texttt{volatile}:} In C, obbliga il compilatore a eseguire fisicamente ogni singola lettura e scrittura, impedendo all'ottimizzatore di rimuovere operazioni che giudica logicamente superflue[cite: 40, 45].
\end{itemize}

\subsubsection*{La Catena di Configurazione (Step 5-9)}
Il \texttt{Reset\_Handler} procede con una configurazione hardware puntuale prima di cedere il controllo:
\begin{itemize}
    \item \textbf{VTOR (Step 5):} Dichiara esplicitamente nel registro \texttt{0xE000ED08} che la Vector Table si trova all'indirizzo \texttt{0x0}[cite: 41]. Sebbene sia il default, riscriverlo rende il codice robusto per un eventuale bootloader che sposti la tabella[cite: 41].
    \item \textbf{SHCSR (Step 6):} Impostando i bit 16, 17 e 18 del registro \texttt{0xE000ED24}, abilita i fault specifici[cite: 41]. Questo smembra l'escalation: da questo momento, i MemManage, BusFault e UsageFault vengono instradati nei loro handler dedicati[cite: 41].
    \item \textbf{CCR (Step 7):} Impostando il bit \texttt{DIV\_0\_TRP} a \texttt{0xE000ED14}, si impone alla CPU di generare un \texttt{UsageFault} in caso di divisione per zero[cite: 42]. Senza questo bit, la divisione hardware restituisce silenziosamente zero, nascondendo un potenziale bug catastrofico[cite: 42].
    \item \textbf{Priorità (Step 8):} Nel Cortex-M, un numero minore indica una priorità più urgente[cite: 42]. I registri SHPR sono configurati scrivendo i singoli byte direttamente (\texttt{strb}): i fault diventano i più urgenti (\texttt{0x00}), seguiti dalla System Call (\texttt{0x80}) e da SysTick/PendSV (\texttt{0xE0})[cite: 42, 43]. Essendo architettura Little-Endian, in GDB il byte 0 appare come le due cifre esadecimali più a destra[cite: 44].
    \item \textbf{Apertura e Salto (Step 9):} L'istruzione \texttt{cpsie i} riabilita globalmente gli interrupt (azzerando il \texttt{PRIMASK})[cite: 43]. L'istruzione \texttt{bl main} trasferisce il controllo al C[cite: 43]. Se il \texttt{main} dovesse ritornare, un branch di fallback (\texttt{b hang}) blocca l'esecuzione per evitare il collasso[cite: 43].
\end{itemize}

\subsubsection*{Validazione Pratica e \texttt{SystemInit}}
Forzando una divisione per zero con una variabile \texttt{volatile} nel codice C, la catena di configurazione dimostra il suo valore in modo empirico[cite: 45]:
\begin{itemize}
    \item Disabilitando lo step 6 (SHCSR), il programma crasha e stampa \texttt{HardFault}: il fault si innesca ma perde la sua identità diagnostica[cite: 45].
    \item Disabilitando lo step 7 (CCR), la divisione ritorna 0 e il programma avanza silenziosamente con dati matematicamente corrotti[cite: 45].
\end{itemize}
Infine, va notato che su hardware in silicio (al di fuori dell'emulatore QEMU), la startup phase include un'ulteriore funzione chiamata \texttt{SystemInit()}[cite: 45]. Questa si occupa di configurare il PLL per innalzare il clock, impostare i Flash Wait States (essenziali per non estrarre dati corrotti da una FLASH troppo lenta per la CPU), disabilitare il Watchdog hardware e accendere la FPU prima di inizializzare la RAM[cite: 46].



\subsection{1.7 La Vita Senza un Sistema Operativo}
Un programma C per PC gira in un ambiente \textit{Hosted}, supportato da un Sistema Operativo e da una vasta libreria standard (\texttt{libc})[cite: 46]. Il nostro microcontrollore opera invece in un ambiente \textit{Freestanding}: sotto il nostro codice non c'è assolutamente nulla[cite: 46, 47]. Possiamo includere solo librerie "statiche" (come \texttt{<stdint.h>}) che non richiedono l'esecuzione di codice a runtime, perdendo l'accesso a funzioni complesse come \texttt{malloc} e \texttt{printf}[cite: 47].

\subsubsection*{Bypassare la \texttt{libc} e il Problema di \texttt{printf}}
In un sistema desktop, \texttt{printf} si limita a formattare il testo, delegando poi la scrittura fisica a una System Call (es. \texttt{write()}) che invoca il kernel del Sistema Operativo[cite: 47, 48]. Essendo sprovvisti di un kernel, questa catena crollerebbe[cite: 49]. Deliberatamente non includiamo alcuna \texttt{libc} esterna per evitare configurazioni ridondanti e per mantenere una trasparenza assoluta sul codice in esecuzione[cite: 48].

Per stampare a schermo aggiriamo il problema sfruttando il \textbf{Semihosting}: una funzionalità di debug hardware[cite: 49]. L'applicazione carica un codice operativo nel registro \texttt{r0} (\texttt{0x04}), l'indirizzo della stringa in \texttt{r1}, ed esegue l'istruzione Assembly \texttt{bkpt 0xab}[cite: 49]. Questo \textit{breakpoint} blocca il processore, permettendo all'emulatore host (QEMU) di leggere la RAM, stampare la stringa sul nostro terminale, e far ripartire la CPU[cite: 49]. 
In C, tutto questo viene implementato tramite assembly inline (\texttt{\_\_asm\_\_ volatile}), assicurandosi di usare la clausola \texttt{"memory"} per vietare al compilatore di riordinare le istruzioni, garantendo che la stringa sia scritta in memoria prima di mettere in pausa la CPU[cite: 49, 50].

\subsubsection*{Modalità Operative e la Sandbox (Privilege Drop)}
Il processore Cortex-M3 divide rigidamente l'esecuzione in due modalità fisiche:
\begin{itemize}
    \item \textbf{Thread mode:} Esegue il codice applicativo (es. \texttt{main()}) e può operare con o senza privilegi[cite: 50].
    \item \textbf{Handler mode:} Esegue la gestione delle eccezioni ed è \textbf{sempre e incondizionatamente privilegiato} per design hardware[cite: 50, 55].
\end{itemize}

All'avvio, il sistema parte in \textit{Thread mode} privilegiato[cite: 50]. Tuttavia, il nostro codice impone volontariamente un declassamento (Privilege Drop) scrivendo il valore 1 nel bit \texttt{nPRIV} del registro speciale \texttt{CONTROL}[cite: 51]. Un'istruzione \texttt{isb} (\textit{Instruction Synchronization Barrier}) svuota immediatamente la pipeline della CPU per applicare le nuove restrizioni sul codice successivo[cite: 51].

Questo è un "biglietto di sola andata": una volta declassato in \textit{Unprivileged}, il programma viene rinchiuso in una \textbf{Sandbox}[cite: 51]. La CPU hardware blocca fisicamente l'accesso ai registri di sistema critici (come il NVIC o il SysTick timer) e ignora silenziosamente qualsiasi tentativo di riscrivere il registro \texttt{CONTROL} per recuperare i privilegi[cite: 51]. Inoltre, intercetta l'istruzione di semihosting \texttt{bkpt} considerandola una violazione di sicurezza, scatenando un \texttt{HardFault}[cite: 52].

\subsubsection*{\texttt{SVC}: La Porta per il Sistema Operativo}
Se il codice è intrappolato nella Sandbox e non può comunicare con l'hardware, come può compiere azioni utili? Esattamente come fa un'app utente su Linux: chiede il permesso tramite una \textbf{System Call}.

L'istruzione \texttt{svc \#0} (\textit{Supervisor Call}) è deliberatamente consentita al codice non privilegiato[cite: 53]. Quando eseguita, innesca intenzionalmente un'eccezione, forzando la CPU a saltare nel vettore \texttt{SVC\_Handler} passando automaticamente in \textbf{Handler mode} (massimi privilegi)[cite: 53]. 
All'interno del gestore, il codice può stampare in semihosting in totale sicurezza[cite: 53, 54]. Al termine della funzione (al \texttt{return}), l'eccezione si chiude e la CPU ripristina la modalità originaria, rilasciando l'applicazione nuovamente senza privilegi nella sua Sandbox[cite: 53, 54].

Per dimostrare in modo definitivo l'affidabilità di questa protezione, il codice finale tenta un'azione malevola scrivendo nel registro hardware del SysTick \textit{dopo} esser tornato in \textit{Unprivileged}[cite: 54, 55]. L'hardware non ha esitazioni: intercetta l'accesso illecito e sputa un \texttt{BusFault}, confermando che l'infrastruttura di sicurezza del nostro sistema \textit{bare-metal} è inviolabile[cite: 55].

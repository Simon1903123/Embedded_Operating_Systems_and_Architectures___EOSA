\section{Introduction to Low-Level CPU Control}
In the previous week, we built a tiny program for a Cortex-M3, ran it in QEMU, and saw it print one line[cite: 101]. Several pieces of that program were handed to us as-is: the linker script that decided where everything goes in memory, and the startup code that ran before \texttt{main()}. We were asked to trust them. This phase is about stopping that trust and building those components from scratch.
By the end of this phase, developers will understand, and will have written, every instruction that the CPU executes between power-on and the first line of \texttt{main()}[cite: 101]. The development process covers knowing where each piece of a C program lives in the chip's memory and why, how the CPU finds its first instruction, how to watch the CPU one instruction at a time with a debugger, how to configure the CPU so that errors are reported clearly instead of silently, and what it means to run C with nothing underneath it (no C library, no operating system)[cite: 101]. Finally, the program will be split into a privileged and an unprivileged part, building the smallest possible version of a system call (\texttt{svc})[cite: 101].

The process is organized into three core units[cite: 101]:
\begin{enumerate}
    \item \textbf{Where code and data live:} The kinds of memory a microcontroller has, the Cortex-M memory map, how the linker script turns that map into decisions, and what the CPU does at reset[cite: 101].
    \item \textbf{Taking control of the CPU:} The debugger, the CPU registers, just enough ARM assembly to read and write boot code, and writing the reset handler step by step (stack, \texttt{.data}, \texttt{.bss}, vector table, fault configuration, priorities)[cite: 101].
    \item \textbf{Life without an OS underneath:} What ``freestanding'' C means, how the program prints without a C library, privileged and unprivileged code, and the \texttt{svc} instruction as a system call[cite: 101].
\end{enumerate}

\subsection{Where You Start and Where You End}
All the in-class work happens on top of a starting skeleton, specifically the folder \texttt{week-02/base/}[cite: 101]. It is derived from the previous week with one major difference: the original C startup code, which did all the setup work, has been thrown away[cite: 101]. 

In its place is a new, almost empty assembly file (\texttt{base/boot/startup.s})[cite: 101]. It contains only the two words the CPU absolutely needs at reset (a stack address and the address of the first instruction), and a \texttt{Reset\_Handler} that does nothing except call \texttt{main()} and then loop forever if \texttt{main()} ever returns[cite: 101].

The program in \texttt{base/src/main.c} attempts to print two lines[cite: 101]:
\begin{enumerate}
    \item A standard string literal[cite: 101].
    \item \texttt{data\_message}, a global character array initialized with the text \texttt{"main: this text lives in .data\textbackslash{}n"}[cite: 101].
\end{enumerate}

If we build and run the base skeleton (\texttt{make} and \texttt{make run}), we see only one line[cite: 101]:
\begin{lstlisting}[language=bash]

\end{lstlisting}

The second line is missing[cite: 102]. Nothing crashes, and no error is printed: the second call simply prints an empty string[cite: 102]. Understanding exactly why this happens is the goal of Unit 1, and fixing it is the first objective in Unit 2[cite: 102]. 

By the end of the week, the fully implemented program will print four distinct lines, each serving as evidence that a specific piece of the low-level architecture is in place[cite: 102]:
\begin{lstlisting}[language=bash]

\end{lstlisting}

\textit{Practical Note:} QEMU does not exit automatically when the program finishes because the bare-metal image enters an infinite spin loop (there is nowhere to return to)[cite: 102]. It must be manually stopped using \texttt{Ctrl-C}[cite: 102].

\section{Memory Technologies in Embedded Systems}
When writing a C program on a standard laptop, developers rarely think about \textit{which} memory their variables reside in. On a microcontroller, this is a critical consideration because the chip contains two very different kinds of memory, and each piece of the program can live in only one of them[cite: 102].

\subsection{SRAM (Static RAM): The Working Memory}
The first kind of memory is \textbf{SRAM} (Static RAM)[cite: 102]. 
\begin{itemize}
    \item \textbf{Direct Bus Connection:} SRAM is connected directly to the CPU's memory bus[cite: 102]. Every byte in it has a specific address, and the CPU reads or writes any byte using ordinary load or store instructions (the same instructions the compiler uses for \texttt{x = y;})[cite: 102].
    \item \textbf{Speed:} It is extremely fast; on a microcontroller, one access typically takes about one clock cycle[cite: 102].
    \item \textbf{Writeability:} You can write to a single byte at any time, as often as you like[cite: 102].
    \item \textbf{Volatility:} Its primary weakness is that it is \textbf{volatile}: when power goes off, its content is completely lost[cite: 102]. Furthermore, when power comes back on, the content is not zero; it is \textbf{undefined}, consisting of a random pattern of bits left by the physical state of the memory cells[cite: 102].
\end{itemize}
Because of these characteristics, SRAM is the designated location for everything that \textit{changes} while the program runs, specifically your variables and the stack[cite: 102].
\subsection{NOR Flash: Execute-in-Place Memory}
The second kind of memory is \textbf{NOR flash}. NOR flash sits on the memory bus, similar to a ROM: every word has a specific address, allowing the CPU to read any of them quickly and in any order. Because of this, the CPU can fetch instructions directly from the flash and execute them right where they are stored, without needing to copy the program into RAM first. This capability is known as \textbf{execute-in-place} (XIP). 

NOR flash is \textbf{non-volatile}, meaning your program remains intact even after the board is unplugged or powered off. The price for these features is paid when writing data. Writing to flash is not a simple store instruction. It requires a two-step process: 

\begin{enumerate}
    \item An entire \textbf{sector} (a block of a few kilobytes) must be \textbf{erased}, setting every bit within it to 1. 
    \item An individual words can be \textbf{programmed}, which only turns bits from 1 to 0.
\end{enumerate}

Both operations take microseconds to milliseconds and require a special command sequence sent to the flash controller. Consequently, for a running program, NOR flash is effectively \textbf{read-only}.

\subsection{Contrasting with NAND Flash and Block Devices}
It is worth contrasting this with the storage technologies commonly found in standard laptops, such as \textbf{NAND flash} (used in SD cards and SSDs) and hard disks. 

These storage devices are \textbf{not} on the memory bus. They are accessed through a controller, one \textbf{block} (or page) at a time (typically 512 bytes to 4 KB). A block has no CPU address. The CPU cannot fetch an instruction from it, nor can it read a single variable directly: the contents must first be copied into RAM and then used from there. 

This is exactly what a desktop operating system does when you start a program: the OS \textbf{loader} copies the executable from the SSD into RAM before running it. A microcontroller, however, has no loader. Its program already sits in NOR flash, at the exact address it runs from.

\subsection{Applying Constraints to C Code}
Put these facts side by side, and you get the rules for a C program on a microcontroller:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|l|l|l|}
\hline
\textbf{Technology} & \textbf{On the bus?} & \textbf{Execute from it?} & \textbf{Write at run time?} & \textbf{Keeps data at power-off?} \\ \hline
SRAM & yes & yes & yes, bytes & no \\ \hline
NOR flash & yes & yes (XIP) & no (erase/program) & yes \\ \hline
NAND / disk & no (blocks) & no & through a driver & yes \\ \hline
\end{tabular}
\end{table}

Based on these constraints:
\begin{itemize}
    \item \textbf{Code and Constants:} Code stays in flash and runs directly from there. Constants (anything declared \texttt{const}, and string literals such as \texttt{"hello"}) also stay in flash and are read in place.
    \item \textbf{Uninitialized Variables:} Variables must live in RAM because they change.
    \item \textbf{Initialized Variables:} The interesting case is an \textbf{initialized} variable such as \texttt{int x = 5;}. The variable lives in RAM, but RAM is random at power-on. Therefore, the value \texttt{5} has to come from somewhere that survives power-off (flash). So the \texttt{5} is \textbf{stored in flash}, and something must \textbf{copy it into RAM at boot}, before \texttt{main()} runs and reads \texttt{x}. This missing copy mechanism is the whole reason the base program prints only one line.
\end{itemize}

\subsection{The Linker Script and the Memory Map}
The CPU physically sees a single address space of 4 GB (using 32-bit addresses)[cite: 8]. On every Cortex-M chip, this space is rigidly divided into regions whose purpose is fixed by the ARM architecture[cite: 8]. Our emulated board provides specific hardware at specific addresses: 4 MB of executable memory (FLASH) starting at address \texttt{0x0}, and 4 MB of working memory (RAM) starting at \texttt{0x20000000}[cite: 8].

The \textbf{Linker Script} (\texttt{.ld} file) is the architectural blueprint that tells the compiler tools exactly where these physical regions are and how to place the C program into them. Let us analyze the complete script provided for our board:

\begin{lstlisting}
MEMORY
{
    FLASH (rx)  : ORIGIN = 0x00000000, LENGTH = 4M  /* code + read-only data */
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 4M  /* data, bss, stack */
}

ENTRY(Reset_Handler)

_estack = ORIGIN(RAM) + LENGTH(RAM);   /* initial SP = top of RAM */
_Min_Stack_Size = 0x1000;              /* 4 KB reserved for stack */
_Min_Heap_Size = 0x1000;               /* 4 KB reserved for heap */
\end{lstlisting}

\subsubsection{MEMORY: Defining the Regions}
In the \texttt{MEMORY} block, each line explicitly describes one physical region[cite: 9]: a name you choose (\texttt{FLASH}, \texttt{RAM}), a start address (\texttt{ORIGIN}), a size (\texttt{LENGTH}), and access attributes (like \texttt{r} for read, \texttt{x} for execute)[cite: 9]. 

The linker actively uses the \texttt{LENGTH} values to protect your program: if you ask it to place more code than the flash memory can hold, the link intentionally fails at build time with an overflow error rather than producing a broken image that crashes at runtime[cite: 9, 15].

Immediately following the regions, the script calculates the \texttt{\_estack} symbol[cite: 9]. This value (\texttt{0x20400000}) represents exactly one byte past the last available address in the RAM[cite: 9]. Because the Cortex-M stack physically grows downwards (toward lower memory addresses), initializing the stack pointer at the absolute top of the RAM gives it the maximum possible room to grow[cite: 9].

\subsection{SECTIONS: Building the Executable Image}
The \texttt{SECTIONS} block dictates exactly how the raw code and variables from your C files (the input sections) are packed into the final executable image (the output sections)[cite: 9].

\begin{lstlisting}
SECTIONS
{
    /* 1. Vector table first, at address 0 */
    .isr_vector :
    {
        . = ALIGN(4);            /* word-align */
        KEEP(*(.isr_vector))     /* never garbage-collect it */
        . = ALIGN(4);
    } > FLASH

    /* 2. Executable code and read-only data */
    .text :
    {
        . = ALIGN(4);
        *(.text*)                /* all executable code */
        *(.rodata*)              /* string literals, const variables */
        . = ALIGN(4);
    } > FLASH
\end{lstlisting}

The rules are strictly applied in top-to-bottom order[cite: 9]. The single dot (\texttt{.}) is the \textbf{Location Counter}: it represents the address the linker is currently at while placing bytes[cite: 10]. 

The \texttt{.isr\_vector} section is placed into \texttt{FLASH} first, meaning it lands perfectly at address \texttt{0x0}, exactly where the hardware will look for it at boot[cite: 10]. The executable code (\texttt{.text}) and read-only constants (\texttt{.rodata}) are immediately packed after it, also in \texttt{FLASH}[cite: 9, 10].

\subsubsection{Run Address and Load Address: The \texttt{.data} Section}
The \texttt{.data} section, which holds initialized global variables (like our \texttt{data\_message} string), introduces a critical architectural challenge[cite: 10]:

\begin{lstlisting}
    _sidata = LOADADDR(.data);  /* FLASH address of the stored initial values */

    /* 3. Initialized variables */
    .data :
    {
        . = ALIGN(4);
        _sdata = .;             /* start of .data in RAM */
        *(.data*)               /* initialized variables */
        . = ALIGN(4);
        _edata = .;             /* end of .data in RAM */
    } > RAM AT > FLASH          /* run address in RAM, load address in FLASH */
\end{lstlisting}

Every output section possesses two distinct memory addresses[cite: 10]:
\begin{itemize}
    \item \textbf{VMA (Virtual/Run Memory Address):} Where the program expects the section to be when it runs[cite: 10].
    \item \textbf{LMA (Load Memory Address):} Where the section's raw bytes are actually stored in the physical flash image[cite: 10].
\end{itemize}

For code (\texttt{.text}), the VMA and LMA are identical because the CPU executes code directly from flash. For variables (\texttt{.data}), they \textit{must} differ: variables must physically live in RAM so they can be written to, but their initial values must be permanently stored in FLASH so they survive power-off[cite: 10]. 

The directive \texttt{> RAM AT > FLASH} enforces exactly this: run address in RAM, load address in FLASH[cite: 10]. The script defines symbols (\texttt{\_sidata}, \texttt{\_sdata}, \texttt{\_edata}) to record the exact boundary addresses so our assembly boot code knows exactly where to copy the bytes from and to[cite: 10].

\subsubsection{bss, Heap, and Stack: RAM With No Stored Image}
The final regions defined in the script exist purely in RAM and require zero physical storage space in the executable image[cite: 11]:

\begin{lstlisting}
    /* 4. Zero-initialized variables */
    .bss :
    {
        . = ALIGN(4);
        _sbss = .;              /* start of .bss */
        *(.bss*)                /* zero-initialized variables */
        *(COMMON)
        . = ALIGN(4);
        _ebss = .;              /* end of .bss */
    } > RAM

    /* 5. Heap region */
    .heap :
    {
        . = ALIGN(8);
        _heap_bottom = .;
        . = . + _Min_Heap_Size; /* advance location counter by 4 KB */
        _heap_top = .;
    } > RAM

    /* 6. Link-time guard */
    __StackLimit = _estack - _Min_Stack_Size;
    ASSERT(__StackLimit >= _heap_top, "region RAM overflowed...")
}
\end{lstlisting}

\begin{itemize}
    \item \textbf{The \texttt{.bss} section:} Holds global variables that explicitly start at zero (e.g., \texttt{int counter;})[cite: 11]. There is no point storing thousands of zeros in the Flash image, so \texttt{.bss} has no LMA[cite: 11]. The boot code must actively fill this RAM range with zeros at runtime[cite: 11].
    \item \textbf{The Heap and Stack:} These are not standard input sections[cite: 11]. The script simply advances the location counter (\texttt{. = . + \_Min\_Heap\_Size;}) to carve out a 4 KB chunk of empty RAM for the heap[cite: 11]. 
    \item \textbf{Safety Asserts:} The script dynamically calculates \texttt{\_\_StackLimit} and ends with an \texttt{ASSERT} directive[cite: 11]. This prevents catastrophic memory corruption by intentionally failing the build if the calculated top of the heap collides with the bottom of the stack reservation[cite: 11].
\end{itemize}

\subsection{Linker-Defined Symbols Are Addresses, Not Variables}
Symbols defined in the linker script such as \texttt{\_sdata}, \texttt{\_edata}, and \texttt{\_estack} are unique: \textbf{they have no physical storage}[cite: 11]. 

There is no physical memory cell called \texttt{\_sdata} holding a value[cite: 11]. The linker simply assigns each symbol an address, and that address \textit{itself} is the information[cite: 11]. This distinction is critical when referencing them from C:
\begin{lstlisting}[language=c]
extern uint32_t _sdata;
uint32_t start = (uint32_t)&_sdata; /* OK: gets the actual address */
uint32_t oops = _sdata;              /* WRONG: reads garbage from RAM */
\end{lstlisting}

In assembly, the boot code utilizes these symbols strictly as mathematical boundaries (e.g., looping from \texttt{\_sidata} to \texttt{\_sdata}) to initialize the C runtime[cite: 11].

\subsection{Reading the Result: The Map File, \texttt{nm}, and \texttt{objdump}}
You now know what the linker script asks for. You can verify what the linker and compiler actually did using standard toolchain utilities:
\begin{itemize}
    \item \textbf{The Map File (\texttt{.map}):} Generated by the linker, it repeats your \texttt{MEMORY} regions and lists every output section, its size, and the load address for \texttt{.data}.
    \item \textbf{\texttt{arm-none-eabi-nm -n}:} Lists all symbols inside an object file (\texttt{.o}) or final executable (\texttt{.axf}), sorted by address. The letter before each name identifies its kind:
    \begin{itemize}
        \item \textbf{T / t:} Code (\texttt{.text}; uppercase means global, lowercase means local/static).
        \item \textbf{R:} Read-only data (\texttt{.rodata} or constants).
        \item \textbf{D:} Initialized data destined for RAM (\texttt{.data}).
        \item \textbf{B:} Uninitialized data destined for RAM (\texttt{.bss}).
        \item \textbf{U:} Undefined symbol (an external reference waiting for the linker to resolve it).
    \end{itemize}
    \item \textbf{\texttt{arm-none-eabi-objdump -h}:} Prints one line per output section, revealing its exact size, its VMA (run address), and its LMA (load address).
\end{itemize}

\subsubsection{Analyzing the Map File (\texttt{.map})}
When the linker successfully finishes linking the object files, it produces an \texttt{output.map} file. This file is the absolute source of truth for understanding exactly where every single byte of your program physically landed in memory.

Looking at the generated \texttt{output.map} for our base skeleton, we can observe the Linker strictly enforcing our rules:

\begin{lstlisting}[language=bash]
Memory Configuration
Name             Origin             Length             Attributes
FLASH            0x00000000         0x00400000         xr
RAM              0x20000000         0x00400000         xrw
\end{lstlisting}
The \texttt{Memory Configuration} block confirms that the physical hardware map was understood exactly as we defined it.

As we scroll down into the \texttt{Linker script and memory map} section, we see the individual output sections being populated:

\begin{lstlisting}[language=bash]
.isr_vector     0x00000000        0x8
 *(.isr_vector)
 .isr_vector    0x00000000        0x8 build/boot/startup.o
                0x00000000                isr_vector

.text           0x00000008       0x58
 *(.text*)
 .text          0x00000008        0x6 build/boot/startup.o
                0x00000008                Reset_Handler
 .text          0x00000010       0x34 build/src/main.o
                0x00000028                main
\end{lstlisting}
This section clearly demonstrates the "folding" behavior: 
\begin{itemize}
    \item The vector table (\texttt{.isr\_vector}) was correctly placed at address \texttt{0x00000000}.
    \item Immediately after it, at address \texttt{0x00000008}, the linker began packing the executable code (\texttt{.text}). 
    \item It first placed \texttt{Reset\_Handler} from \texttt{startup.o}, and then placed the \texttt{main} function from \texttt{main.o} starting at \texttt{0x00000028}.
\end{itemize}

Finally, analyzing the \texttt{.data} section reveals the LMA/VMA split perfectly:
\begin{lstlisting}[language=bash]
                0x00000060                _sidata = LOADADDR (.data)
...
.data           0x20000000       0x20 load address 0x00000060
                0x20000000                _sdata = .
 .data          0x20000000       0x20 build/src/main.o
                0x20000000                data_message
\end{lstlisting}
Here, the linker explicitly proves that our initialized array \texttt{data\_message} is mapped to run from RAM at address \texttt{0x20000000} (its VMA), but its physical load address (LMA) in the image is \texttt{0x00000060}, exactly as configured via \texttt{LOADADDR}.

\subsubsection{Analyzing the Final Executable (\texttt{.axf})}
Once the linker has stitched all the object files together using the rules defined in the Linker Script, we can inspect the final executable image (\texttt{scratch-os.axf}) using \texttt{nm}:

\begin{lstlisting}[language=bash]
$ arm-none-eabi-nm scratch-os.axf
00000008 T Reset_Handler
00001000 A _Min_Heap_Size
00001000 A _Min_Stack_Size
203ff000 A __StackLimit
20000020 B _ebss
20000020 D _edata
20400000 R _estack
00000060 T _etext
20000020 B _heap_bottom
20001020 B _heap_top
20000020 B _sbss
20000000 D _sdata
00000060 A _sidata
20000000 D data_message
0000000c t hang
00000000 R isr_vector
00000028 T main
00000010 t semihost_write0
\end{lstlisting}

This final output perfectly validates our entire architecture:
\begin{itemize}
    \item \textbf{Resolved Symbols:} The previously undefined (\textbf{U}) symbols from the object files have been assigned exact physical addresses. \texttt{main} is now located at \texttt{0x00000028}, and \texttt{Reset\_Handler} is at \texttt{0x00000008} (both marked \textbf{T} for executable text).
    \item \textbf{Vector Table:} \texttt{isr\_vector} is perfectly anchored at \texttt{0x00000000} (\textbf{R} for read-only).
    \item \textbf{Variables in RAM:} Our writable global array, \texttt{data\_message}, sits precisely at \texttt{0x20000000} (\textbf{D} for initialized data), which perfectly matches the linker-defined symbol \texttt{\_sdata}.
    \item \textbf{Absolute Linker Symbols:} Symbols defined purely by math in the linker script (like \texttt{\_Min\_Stack\_Size} or \texttt{\_sidata}) are tagged as \textbf{A} (Absolute). They do not belong to any specific code section; they are simply hardcoded constant addresses used by our assembly boot loop.
\end{itemize}

\subsubsection{Analyzing the Object Files (\texttt{.o})}
Before the linker merges everything into the final image, we can inspect the raw object files generated by the compiler and assembler using \texttt{nm}. 

If we inspect the compiled assembly boot code (\texttt{startup.o}), we see:
\begin{lstlisting}[language=bash]
$ arm-none-eabi-nm startup.o
00000000 T Reset_Handler
         U _estack
00000004 t hang
00000000 R isr_vector
         U main
\end{lstlisting}
This output perfectly validates our code:
\begin{itemize}
    \item \texttt{Reset\_Handler} is global code (\textbf{T}), while \texttt{hang} is a local assembly label (\textbf{t}).
    \item \texttt{isr\_vector} is treated as read-only data (\textbf{R}) destined for FLASH.
    \item \texttt{\_estack} and \texttt{main} are marked as \textbf{U} (Undefined). The assembler encountered these names but did not find them in \texttt{boot.s}. It leaves them blank, trusting the Linker Script and \texttt{main.o} to provide their actual addresses later.
\end{itemize}

Similarly, if we inspect our C program (\texttt{main.o}):
\begin{lstlisting}[language=bash]
$ arm-none-eabi-nm main.o
00000000 D data_message
00000018 T main
00000000 t semihost_write0
\end{lstlisting}
Here, the C compiler correctly categorized our components:
\begin{itemize}
    \item \texttt{main} is a globally visible C function (\textbf{T}).
    \item \texttt{semihost\_write0} is a \texttt{static} C function, making it strictly local to this file (\textbf{t}).
    \item \texttt{data\_message} is an initialized global array, so the compiler explicitly tagged it for the \texttt{.data} section (\textbf{D}).
\end{itemize}
When the linker runs, it will stitch \texttt{startup.o} and \texttt{main.o} together, replacing the \textbf{U} symbols with the real addresses assigned during the layout phase.

\subsubsection{Pointers, Local, and Static Variables}
Pointers deserve a moment of care, because a pointer is itself a variable[cite: 109]. In the declaration \texttt{const char *p = "hi";}, the characters \texttt{"hi"} are a string literal and go to \texttt{.rodata}; however, \texttt{p}, the variable holding their address, is an initialized writable variable and goes to \texttt{.data}[cite: 109].

This table of section rules only applies to declarations made \textbf{outside any function}[cite: 109]. A local variable inside a function has no section at all: it lives on the stack while the function runs, and it is gone as soon as the function returns[cite: 109].

\subsubsection{Try It: Testing Global Declarations}
You can test these placement rules by adding the following \textbf{global} variables to \texttt{src/main.c}, right after the line that defines \texttt{data\_message} (before \texttt{main}), so outside any function[cite: 109]:

\begin{lstlisting}[language=c]
const int limit = 100;
int counter = 5;
int total;
int zero = 0;
const char *greeting = "hi";
char buffer[64];
\end{lstlisting}

Write down your prediction for each one, then check[cite: 109]:
\begin{lstlisting}[language=bash]
make
arm-none-eabi-nm build/src/main.o
arm-none-eabi-nm -n build/scratch-os.axf
\end{lstlisting}

You find \texttt{counter} and \texttt{greeting} marked \texttt{D} (initialized data), and \texttt{total}, \texttt{zero}, and \texttt{buffer} marked \texttt{B} (bss)[cite: 109]. The variable \texttt{limit} is the interesting one: in \texttt{main.o} it is marked \texttt{R} (read-only data), but in the final image it is marked \texttt{T}, as if it were code[cite: 109, 110]. The reason is the linker script: it puts \texttt{.rodata} \textit{inside} the \texttt{.text} output section, and in the final image \texttt{nm} classifies a symbol by the output section it ended up in[cite: 110]. 

The string \texttt{"hi"} has no name, so \texttt{nm} does not show it, but the map file shows the \texttt{.rodata} input sections of \texttt{main.o} inside \texttt{.text}[cite: 110]. You can find its bytes directly by dumping the contents of the \texttt{.text} output section[cite: 110]:
\begin{lstlisting}[language=bash]
$ arm-none-eabi-objdump -s -j .text build/scratch-os.axf
 ...
 0038 00bffde7 4c000000 00000020 64000000  ....L...... d...
 0048 68690000 6d61696e 3a206865 6c6c6f20  hi..main: hello
\end{lstlisting}
Each line starts with the address of its first byte, shows 16 bytes, and repeats the same bytes as text on the right. At address \texttt{0x44} you find \texttt{64 00 00 00}: that is \texttt{limit}, whose value is 100 (\texttt{0x64})[cite: 110]. At \texttt{0x48} you find \texttt{68 69 00}, the characters \texttt{h} and \texttt{i} followed by the terminating zero: the string \texttt{"hi"} starts at address \texttt{0x48}, in FLASH[cite: 110].

\subsubsection{Pointers in RAM and Little-Endianness}
How does the program find it? Through \texttt{greeting}, which is a pointer stored in RAM. Dump \texttt{.data}[cite: 110]:
\begin{lstlisting}[language=bash]
$ arm-none-eabi-objdump -s -j .data build/scratch-os.axf
 20000000 6d61696e 3a207468 69732074 65787420  main: this text
 20000010 6c697665 7320696e 202e6461 74610a00  lives in .data..
 20000020 05000000 48000000                    ....H...
\end{lstlisting}
Because you added the variables right after \texttt{data\_message} in \texttt{src/main.c}, the first two lines, from \texttt{0x20000000} to \texttt{0x2000001F}, are \texttt{data\_message} (you can read its text on the right), and your variables follow: \texttt{counter} at \texttt{0x20000020} and \texttt{greeting} at \texttt{0x20000024}[cite: 110]. The compiler places variables in \texttt{.data} in the order you define them. 

To read the numbers you need one more fact: the Cortex-M3 is \textbf{little-endian}, which means that a 32-bit number is stored with its lowest byte first[cite: 110]. 
\begin{itemize}
    \item The four bytes \texttt{05 00 00 00} are the number 5 (the value of \texttt{counter})[cite: 110].
    \item The four bytes \texttt{48 00 00 00} are the number \texttt{0x00000048}[cite: 110]. That is the value of \texttt{greeting}, and it is exactly the FLASH address where \texttt{"hi"} starts[cite: 110]. 
\end{itemize}
This is all a pointer is: a variable whose value is an address[cite: 110]. 

\subsubsection{Local vs. Static Local Variables}
You can see the local-vs-global contrast directly. Inside \texttt{main}, add \texttt{int local = 7;} and \texttt{static int s = 3;}, then check \texttt{nm} again[cite: 109].
\begin{itemize}
    \item \texttt{local} never appears at all: it is not a global, it has no fixed address, and it only exists on the stack while \texttt{main} is running[cite: 109].
    \item \texttt{s} does appear, as \texttt{d s.0}: lowercase \texttt{d} means it lives in \texttt{.data} but is visible only inside this file, and the compiler appends a \texttt{.0} (or \texttt{.N} suffix) to tell one function's static local apart from another's if they share a name[cite: 109]. Unlike \texttt{local}, a \texttt{static} local keeps one fixed address for the whole run of the program, exactly like a global — it is only its \textit{name} that stays private to the function[cite: 109].
\end{itemize}

\subsection{Advanced Memory Layout: Custom Sections and Orphans}
You are not strictly limited to the default sections the compiler chooses[cite: 110]. GCC provides compiler attributes that allow you to explicitly name the input section of a variable or a function[cite: 110]:

\begin{lstlisting}[language=c]
int tagged __attribute__((section(".mysection"))) = 42;
\end{lstlisting}

Where that custom section physically ends up is entirely up to the linker script, \textbf{if the script names it}[cite: 110]. A section that does not match any rule in the \texttt{SECTIONS} block is called an \textbf{orphan}[cite: 110]. The linker does not reject an orphan section; instead, it places it by guessing based on its flags (e.g., whether it is writable or executable) and places it adjacent to sections with similar properties[cite: 110]. 

While this guess usually allows the program to link successfully, the orphan section is placed completely outside your control and, critically, outside any predefined symbol ranges[cite: 110].

If you add the \texttt{tagged} variable to the base project and examine the output using \texttt{arm-none-eabi-nm -n}, you will see the linker symbols placed next to your variable[cite: 110]:

\begin{lstlisting}[language=bash]
20000000 D _sdata
20000020 D _edata
20000020 D tagged
\end{lstlisting}

A new output section \texttt{.mysection} appears. The linker saw a writable, initialized section, so it placed it in RAM \textbf{right after \texttt{.data}}, and gave it its own load address in FLASH. 

Now compare its address with \texttt{\_edata}: \texttt{tagged} sits exactly at \texttt{\_edata}, that is, \textit{after} the end of the range \texttt{\_sdata}...\texttt{\_edata}. A boot loop that copies only \texttt{\_sdata}...\texttt{\_edata} will never copy it, so \texttt{tagged} will not hold 42 when \texttt{main()} runs. The program links without a single warning and is still wrong. That is the fundamental danger of orphans.

If you declare a \texttt{const int} in a section called \texttt{.myconst} instead, the linker sees a read-only section and places it safely in FLASH, between \texttt{.isr\_vector} and \texttt{.text}. 

\subsection{Overflowing a Region}
The \texttt{LENGTH} values in the \texttt{MEMORY} block are not decoration: the linker actively enforces them. First, measure how much flash the base image needs:

\begin{lstlisting}[language=bash]
arm-none-eabi-size build/scratch-os.axf
\end{lstlisting}

The FLASH region has to hold \texttt{text + data}: the code and constants, plus the stored copy of \texttt{.data}'s initial values. For the base skeleton, this is $96 + 32 = 128$ bytes. 

If you edit \texttt{scripts/mps2\_m3.ld} and set FLASH \texttt{LENGTH = 100}, you can test this enforcement. Rebuild with \texttt{make -B} (the \texttt{Makefile} does not automatically list the linker script as a prerequisite, so \texttt{-B} forces everything to be rebuilt). The link will intentionally fail with:

\begin{lstlisting}[language=bash]
region 'FLASH' overflowed by 28 bytes
\end{lstlisting}

$128 - 100$ is exactly 28. If you set \texttt{LENGTH = 128}, the link succeeds because the image fits exactly.

If you then restore FLASH and set RAM \texttt{LENGTH = 8K} instead, \texttt{\_estack} moves down to \texttt{0x20002000}. The 4 KB stack reservation starts 4 KB below it, meaning the 4 KB heap no longer fits between \texttt{.bss} and the stack. The build failure in this scenario comes directly from the script's own \texttt{ASSERT} line, printing its custom message about the heap colliding with the stack.

\section{Reset: The Hardware Contract and \texttt{boot.s}}
Once the memory layout is finalized in the linker script and loaded into memory, the machine can be powered on. The next question is how the CPU starts using it[cite: 16].

When the Cortex-M3 comes out of reset, before any of your code runs, there is absolutely no C runtime available[cite: 16]. The `.data` section is not copied to RAM yet, and `.bss` is not zeroed. To boot the system, the hardware automatically executes a strictly predefined sequence. It does exactly two things[cite: 16]:
\begin{enumerate}
    \item It reads the 32-bit word at address `0x0` and puts it directly into the Stack Pointer (`SP`)[cite: 16].
    \item It reads the word at address `0x4` and puts it directly into the Program Counter (`PC`)[cite: 16]. Execution starts at that exact address.
\end{enumerate}

Everything else (copying `.data`, zeroing `.bss`, configuring the CPU, calling `main()`) is entirely the responsibility of your bare-metal code[cite: 16]. This foundational runtime setup is written entirely in assembly in a file named \texttt{boot/startup.s}.

\subsection{The Assembly Environment}
Before writing the actual instructions, the assembly file configures the build tools using assembler directives:
\begin{itemize}
    \item \textbf{\texttt{.syntax unified}:} Instructs the assembler to use modern ARM syntax[cite: 23].
    \item \textbf{\texttt{.cpu cortex-m3}:} Ensures the assembler only accepts instructions physically present on the Cortex-M3, catching typos at compile-time.
    \item \textbf{\texttt{.thumb}:} Emits Thumb instructions. Cortex-M CPUs can \textit{only} execute Thumb code; they lack a standard 32-bit ARM mode.
\end{itemize}
Any symbol the assembler does not find defined locally (like \texttt{\_estack} from the linker script, or \texttt{main} from \texttt{main.c}) is automatically treated as an external reference, leaving it up to the linker to fill in the correct addresses.

\subsection{The Vector Table}
Those two initial words read at reset are the beginning of the \textbf{Vector Table}: an array of addresses at a fixed place in memory (address `0x00000000` at reset)[cite: 16].

The table exists because of exceptions[cite: 16]. An exception is an event that forces the CPU to stop its current task and run a specific piece of code called a handler[cite: 16]. Slot $N$ of the table physically holds the memory address of the handler for exception $N$[cite: 16]. Slot 0 is unique: it is not executable code, but purely the initial value of the Stack Pointer[cite: 16].

In \texttt{boot/startup.s}, we construct this table explicitly. Notice how the assembly mirrors standard C array initialization:

\begin{lstlisting}
    .section .isr_vector,"a",%progbits
    .global isr_vector
    .type isr_vector, %object

isr_vector:
    .word _estack               /* 0: initial SP = top of RAM */
    .word Reset_Handler         /* 1: reset: first code after power-on */
\end{lstlisting}

\textbf{C Equivalent:}
\begin{lstlisting}[language=c]
void (* const isr_vector[])(void) = {
    (void (*)(void)) &_estack,  /* Slot 0: Initial Stack Pointer */
    Reset_Handler,              /* Slot 1: Reset execution address */
};
\end{lstlisting}

\textit{Directive breakdown:} The \texttt{.section .isr\_vector,"a",\%progbits} directive explicitly tells the tools to place these words into a section named \texttt{.isr\_vector}. The linker script ensures this specific section is always physically placed first in the FLASH memory, guaranteeing it lands precisely at address `0x0`.

\subsubsection{The Thumb Bit Constraint}
One critical detail you will observe in a debugger: the value stored in word 1 is not exactly the raw address of 'Reset\_Handler', but that address with its lowest bit set to 1.

Instructions always sit at even addresses (2-byte or 4-byte aligned), so bit 0 of a code address is physically unused[cite: 16]. ARM repurposes bit 0 as a flag to mean "this is Thumb code"[cite: 16]. Because the Cortex-M3 executes only the Thumb instruction set, the hardware strictly requires this bit to be 1[cite: 16].

\subsubsection{KEEP and Garbage Collection}
The linker possesses an optional optimization feature known as section garbage collection[cite: 16]. It drops every section of code or data that no other software actively references[cite: 16]. 

Because no software code actively calls or reads \texttt{isr\_vector} (only the hardware reads it at power-on), the garbage collector would consider the table useless and throw it away, causing an immediate hardware lockup at boot[cite: 16, 17]. The \texttt{KEEP (*(.isr\_vector))} directive in the linker script explicitly forces the linker to preserve the table regardless of software references[cite: 16, 17].

\subsection{The Reset Handler}
Once the vector table is read, execution officially begins at the 'Reset\_Handler'. This is standard executable code, placed into the \texttt{.text} section.

\begin{lstlisting}
    .section .text,"ax",%progbits
    .global Reset_Handler
    .type Reset_Handler, %function
    .thumb_func
Reset_Handler:
    /* Runtime setup steps (stack, data, bss) go here. */

    bl main                     /* Branch with Link to C code */
hang:
    b hang                      /* Infinite loop if main returns */

    .ltorg                      /* Literal pool placement */
\end{lstlisting}

\textbf{C Equivalent:}
\begin{lstlisting}[language=c]
void Reset_Handler(void) {
    /* Setup runtime... */
    main();
    for (;;) { }
}
\end{lstlisting}

\textit{Directive breakdown:} 
\begin{itemize}
    \item \textbf{.thumb\_func}: Instructs the tools that the immediately following label ('Reset\_Handler') is a Thumb function. When the assembler builds the vector table above, it sees this tag and automatically sets bit 0 to 1, fulfilling the hardware's Thumb bit constraint.
    \item \textbf{.ltorg}: Generates the \textbf{Literal Pool}. ARM instructions are only 16 or 32 bits wide, meaning they cannot physically contain a full 32-bit constant (like the memory address of \textit{\_estack}) inside the instruction itself. The assembler stores the actual 32-bit constant in a nearby table (the literal pool) and translates your instruction into a PC-relative load. \textit{.ltorg} guarantees this table of constants is placed safely after the last instruction, where the CPU will never accidentally attempt to execute it as code.
\end{itemize}

\subsection{Back to the Base: Why Only One Line Prints}
With the memory layout and hardware contract fully mapped, we can finally explain the behavior of the base skeleton observed at the beginning of the chapter[cite: 18].

If you run the base code (\texttt{make run}), the \texttt{main()} function attempts to print two lines:
\begin{enumerate}
    \item A standard string literal[cite: 18].
    \item \texttt{data\_message}, an initialized global array[cite: 18].
\end{enumerate}

Let us look closely at how these are defined in \texttt{src/main.c}, as it perfectly illustrates the memory concepts from Unit 1:

\begin{lstlisting}[language=c]
/* A global array with an initial value. 
 * Because it is writable data, it MUST live in RAM. */
char data_message[] = "main: this text lives in .data\n";

int main(void)
{
    /* 1. Printing a string literal */
    semihost_write0("main: hello from the base\n");

    /* 2. Printing the global array */
    semihost_write0(data_message);

    for (;;) { }
}
\end{lstlisting}

When \texttt{main()} executes, here is exactly what happens at the hardware level:
\begin{itemize}
    \item \textbf{The String Literal (Line 1):} A string literal like \texttt{"main: hello..."} is read-only \texttt{const} data. The compiler naturally places it in the \texttt{.rodata} section, which the linker script puts directly into FLASH memory alongside the executable code. It needs no copying to be read: it is already sitting at the physical address it will be read from, right from the very first instruction. Therefore, this line always prints correctly[cite: 18].
    \item \textbf{The Global Array (Line 2):} Unlike a string literal, a global array is \textit{writable} data, so it must physically live in RAM (since FLASH cannot be written to at runtime). As confirmed by the linker script, the \texttt{.data} section has its VMA (Run Address) at \texttt{0x20000000} in RAM, but its initial bytes are stored at a FLASH LMA (Load Address)[cite: 18]. 
\end{itemize}

Until something physically copies its initial value from FLASH to RAM, this array's content in RAM is whatever happened to already be there at power-on. In our base skeleton, \texttt{Reset\_Handler} contains no code to move the bytes from the LMA to the VMA[cite: 18]. Consequently, the RAM at \texttt{0x20000000} in QEMU is filled with zeros, which C interprets as an empty string[cite: 18]. Thus, the second call prints nothing[cite: 18].

Writing the assembly loop to perform this missing memory copy is the very first task in building our C runtime.

\section{Taking Control of the CPU}
In this unit, you rebuild \texttt{Reset\_Handler} in \texttt{boot/startup.s} yourself, in assembly, one step at a time. To do that, you need two things you have not used before: a debugger to \textit{see} what the CPU does, and enough ARM assembly to read and write the boot code.

\subsection{What is a Debugger?}
A \textbf{debugger} is a program that controls another program while it runs. It can \textbf{stop} the program at any instruction you choose (a \textbf{breakpoint}) or right at the start, before anything has run. It can \textbf{step} it forward one machine instruction, or one C line, at a time. While the program is stopped, it can \textbf{inspect} the CPU registers and any memory address, and even change them. And it can \textbf{continue} the program until the next breakpoint.

On a desktop, a crashing program at least prints an error message. On a microcontroller, there is often no console at all, and a crash simply looks like "nothing happens". A debugger is frequently the \textit{only} way to see what the CPU is really doing. The standard tool is \textbf{gdb}, the GNU debugger, part of the same toolchain family as gcc. The ARM version you use is \texttt{arm-none-eabi-gdb}; on Linux, the gdb that understands ARM is usually called \texttt{gdb-multiarch} instead.

\subsection{A Remote Debugger: Two Programs, Two Terminals}
In this setup, the program being debugged does not run on the same "machine" as gdb. It runs inside QEMU, which emulates the Cortex-M3 board on your laptop. gdb talks to QEMU over a network connection (a TCP socket on your own machine). So you use two terminals:

\begin{verbatim}
 Terminal 1: make debug               Terminal 2: arm-none-eabi-gdb build/scratch-os.axf
 +-------------------------+          +--------------------------+
 | QEMU: CPU + Flash + RAM |  TCP     | gdb: knows your symbols  |
 | halted at reset         |<-------->| (main, Reset_Handler...) |
 | gdb server on port 1234 |  :1234   | from the .axf file       |
 +-------------------------+          +--------------------------+
   program output shows here            you type commands here
\end{verbatim}

In terminal 1, you start QEMU with \texttt{make debug}. The \texttt{debug} target in the \texttt{Makefile} runs the same QEMU command as \texttt{make run}, plus two options: \texttt{-S}, which freezes the emulated CPU before its very first instruction, and \texttt{-gdb tcp::1234}, which starts a gdb server that waits for a connection on TCP port 1234. Anything the program prints still appears in this terminal.

\subsubsection{Reconstructing the Debug Target}
The \texttt{debug} target is therefore nothing more than a shorthand, and you can reconstruct it for any image. Take the QEMU command from the \texttt{run} target of the \texttt{Makefile} you are working with, and append \texttt{-S -gdb tcp::1234}:

\begin{lstlisting}[language=bash]
qemu-system-arm -machine mps2-an385 -monitor null -semihosting \
    -semihosting-config enable=on,target=native \
    -kernel build/scratch-os.axf -serial stdio -nographic \
    -S -gdb tcp::1234
\end{lstlisting}

This matters after this week: the later checkpoints' Makefiles have a \texttt{run} target but no \texttt{debug} target, and this command, run from the checkpoint's folder after \texttt{make}, is how you debug them.

In terminal 2, you start gdb and give it the ELF file, \texttt{arm-none-eabi-gdb build/scratch-os.axf}. gdb reads the ELF only for its \textbf{symbols} and debug information, so that it knows the addresses of \texttt{main}, \texttt{Reset\_Handler}, \texttt{data\_message}, and so on. It does not load the code: QEMU already holds the program. You then connect with \texttt{target remote :1234}.

\subsubsection{The GDB Commands You Need}
This small set of commands is enough for everything this week:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{Command} & \textbf{What it does} \\ \hline
\texttt{target remote :1234} & connect to the gdb server (QEMU) on this machine \\ \hline
\texttt{info registers sp pc} & show some registers (\texttt{info registers} alone: all of them) \\ \hline
\texttt{x/2wx 0} & e\textbf{x}amine memory: 2 \textbf{w}ords (32 bits each) in he\textbf{x}, at address 0 \\ \hline
\texttt{x/s \&data\_message} & examine memory as a C \textbf{s}tring \\ \hline
\texttt{p/x \$r1} & \textbf{p}rint one register (or a C expression) in hex \\ \hline

\subsection{Attaching at Reset}
The first thing to do with the debugger is to catch the CPU \textit{before} its first instruction, and check the reset contract from Unit 1. In the base folder:

\begin{lstlisting}[language=bash]
make debug                                  # terminal 1: QEMU waits
arm-none-eabi-gdb build/scratch-os.axf      # terminal 2
\end{lstlisting}

and in gdb:

\begin{lstlisting}[language=bash]
(gdb) target remote :1234
(gdb) info registers sp pc
(gdb) x/2wx 0
\end{lstlisting}

You see \texttt{sp} equal to \texttt{0x20400000}, \texttt{pc} equal to \texttt{0x8 <Reset\_Handler>}, and at address 0 the two words \texttt{0x20400000 0x00000009}. \textbf{No instruction has run yet}, yet SP and PC already have values: the CPU itself copied vector word 0 into SP and vector word 1 into PC. 

Compare the two: word 1 is \texttt{0x9}, PC is \texttt{0x8}. This is the Thumb bit from Unit 1. The CPU uses bit 0 to check that the target is Thumb code and then clears it; the instruction really starts at \texttt{0x8}. And why \texttt{0x8} in the first place? The base's vector table has only two words (8 bytes), and the code is placed right after it in FLASH.

\subsection{Cortex-M3 Programmer's Model: The Registers}
To follow the CPU instruction by instruction, you need to know what it holds. The \textbf{programmer's model} is the set of registers your code, and gdb, can see. All of them are 32 bits wide.

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|l|}
\hline
\textbf{Register} & \textbf{Name} & \textbf{Role} \\ \hline
R0--R12 & general purpose & your values; a C function call passes its first arguments in R0--R3 \\ \hline
R13 & \textbf{SP} & stack pointer: address of the top of the stack \\ \hline
R14 & \textbf{LR} & link register: where to return after a function call \\ \hline
R15 & \textbf{PC} & program counter: address of the next instruction \\ \hline
--- & \textbf{xPSR} & status: flags, Thumb bit, current exception \\ \hline
\end{tabular}
\end{table}

At this level, there are no variables: only these registers and memory. When your C code says \texttt{x = x + 1}, the compiler turns it into "load \texttt{x} from memory into a register, add 1 to the register, store the register back". The stack, as you know, grows \textbf{downwards}: pushing a value first does \texttt{SP = SP - 4}, then writes the value at the new SP.

\subsubsection{The Status Register (xPSR) and CPU Modes}
\textbf{xPSR} (program status register) packs three critical pieces of information into one register:
\begin{itemize}
    \item \textbf{Flags (Bits 31--28):} The \textbf{N Z C V} flags (negative, zero, carry, overflow), set by comparison instructions and used by conditional jumps.
    \item \textbf{Thumb Bit (Bit 24):} The \textbf{T} state bit, which must always be 1 on Cortex-M (this is where bit 0 of the vector entry ends up).
    \item \textbf{Exception Number (Bits 8--0):} Holds the number of the exception currently being handled, or 0 if none.
\end{itemize}

That last field dictates which of the two \textbf{modes} the CPU is in:
\begin{itemize}
    \item \textbf{Thread mode:} The CPU runs normal code (\texttt{Reset\_Handler}, \texttt{main()}, and the functions they call); the exception number is 0.
    \item \textbf{Handler mode:} The CPU runs an exception handler, and the field holds that exception's number.
\end{itemize}
\textit{Note:} Code in Thread mode can also be privileged or unprivileged; everything in this specific unit runs privileged, and Unit 3 explains the difference.

\subsection{ARM Assembly Basics: A Load/Store Architecture}
The boot code has to be written in assembly because, before it runs, there is no valid stack and no initialized data, so C code cannot yet be trusted. You need only a handful of instructions, and each has a direct C equivalent.

\textbf{A load/store machine:} ARM arithmetic works only on registers. Memory is touched only by \textbf{load} instructions (\texttt{ldr}, memory to register) and \textbf{store} instructions (\texttt{str}, register to memory).

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{Assembly} & \textbf{C equivalent} \\ \hline
\texttt{ldr r3, [r0]} & \texttt{r3 = *r0;} \\ \hline
\texttt{str r3, [r1]} & \texttt{*r1 = r3;} \\ \hline
\texttt{ldr r3, [r0], \#4} & \texttt{r3 = *r0; r0 += 4;} (that is, \texttt{r3 = *src++;}) \\ \hline
\texttt{str r3, [r1], \#4} & \texttt{*r1 = r3; r1 += 4;} (that is, \texttt{*dst++ = r3;}) \\ \hline
\texttt{strb r1, [r0, \#7]} & \texttt{((uint8\_t *)r0)[7] = r1;} (one \textbf{b}yte, at offset 7) \\ \hline
\end{tabular}
\end{table}

The square brackets mean "the memory at this address". The form \texttt{[r0], \#4} is called \textbf{post-increment}: the instruction first uses the address in \texttt{r0}, then adds 4 to \texttt{r0}. One word is 4 bytes, so a loop using this syntax walks through memory word by word, exactly like \texttt{*dst++} in C.

\subsubsection{Constants, Labels, and Jumps}
Moving data between registers and controlling program flow requires another set of basic instructions:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{Assembly} & \textbf{C equivalent} \\ \hline
\texttt{ldr r0, =\_estack} & \texttt{r0 = (uint32\_t)\&\_estack;} (any 32-bit value) \\ \hline
\texttt{mov sp, r0} & \texttt{sp = r0;} (register to register) \\ \hline
\texttt{movs r3, \#0} & \texttt{r3 = 0;} (small constants only) \\ \hline
\texttt{copy\_data:} & a \textbf{label}: a name for this address, like a C \texttt{goto} label \\ \hline
\texttt{b copy\_data} & \texttt{goto copy\_data;} \\ \hline
\texttt{bl main} & \texttt{main();}: \textbf{b}ranch with \textbf{l}ink, saves the return address in LR \\ \hline
\end{tabular}
\end{table}

\textbf{The 32-bit Instruction Encoding Constraint (Literal Pools):} 
The \texttt{ldr rX, =value} form needs a word of explanation because you will see it look different in gdb. An instruction is only 16 or 32 bits long, so it mathematically cannot contain an arbitrary 32-bit constant alongside its opcode. 

The assembler therefore stores the constant in a small table of constants near the code, called the \textbf{literal pool}, and turns your \texttt{ldr r0, =\_estack} into "load r0 from that table". In gdb, this appears as something like \texttt{ldr r0, [pc, \#92]} (an address relative to the PC). 

The \texttt{.ltorg} directive at the end of \texttt{Reset\_Handler} in \texttt{boot/startup.s} tells the assembler where to put this pool: typically after the last instruction, where the CPU will never try to execute it as code.

\subsubsection{Control Flow: Decisions, Bits, and Interrupts}
Branching and loops in assembly rely entirely on the \texttt{xPSR} status register. A decision is a two-step process: compare values to set condition flags, then jump based on those flags.

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{Assembly} & \textbf{C equivalent} \\ \hline
\texttt{cmp r1, r2} & compute \texttt{r1 - r2}, keep only the flags N Z C V \\ \hline
\texttt{bhs done} & \texttt{if (r1 >= r2) goto done;} (\textbf{h}igher or \textbf{s}ame, unsigned) \\ \hline
\texttt{orr r1, r1, \#0x10} & \texttt{r1 |= 0x10;} \\ \hline
\texttt{cpsid i} & stop accepting interrupts (\texttt{\_\_disable\_irq()} in vendor C code) \\ \hline
\texttt{cpsie i} & accept interrupts again (\texttt{\_\_enable\_irq()}) \\ \hline
\end{tabular}
\end{table}

With \texttt{cmp} and a conditional branch, you can build any loop. A C \texttt{while} loop becomes "test at the top, jump back at the bottom":
\begin{lstlisting}
loop:  cmp r1, r2        @ while (r1 < r2) {
       bhs done          @
       ...               @     body
       b   loop          @ }
done:
\end{lstlisting}
The loop continues while \texttt{r1 < r2}; as soon as \texttt{r1 >= r2}, \texttt{bhs} jumps out of the loop.

\subsubsection{Assembler Directives}
Lines that start with a dot (\texttt{.}) produce no instructions: they steer the assembler itself. The directives used in \texttt{boot/startup.s} are:

\begin{lstlisting}
    .section .isr_vector,"a",%progbits   @ put what follows in section .isr_vector
    .global isr_vector                   @ make the name visible to the linker
isr_vector:
    .word _estack                        @ one 32-bit value
    .word Reset_Handler

    .section .text,"ax",%progbits
    .global Reset_Handler
    .thumb_func                          @ next label is Thumb code: its address gets bit 0 = 1
Reset_Handler:
\end{lstlisting}

The vector table block translates to the following C equivalent:
\begin{lstlisting}
__attribute__((section(".isr_vector")))
const uint32_t isr_vector[] = { (uint32_t)&_estack, (uint32_t)Reset_Handler };
\end{lstlisting}

\begin{itemize}
    \item \texttt{.section}: Chooses the section, with flags. \texttt{"a"} means the section occupies space in the image; \texttt{"x"} means it is executable.
    \item \texttt{.global}: Makes a name visible to other files and to the linker. Without it, a label acts like a \texttt{static} name in C.
    \item \texttt{.word}: Allocates exactly one 32-bit word and stores the given value inside it.
    \item \texttt{.thumb\_func}: Dictates that the next label is Thumb code. This instructs the tools to store \texttt{Reset\_Handler} with bit 0 set to 1, which is where the \texttt{0x9} in the base (and \texttt{0x41} in the solution) comes from.
\end{itemize}
The file also uses \texttt{.type} and \texttt{.size} to tell \texttt{gdb} and \texttt{nm} whether a name is code or data and its total size.

\section{Writing the Startup Script (\texttt{Reset\_Handler})}
The \texttt{Reset\_Handler} in \texttt{boot/startup.s} has one critical job: to turn a bare CPU into an environment that can safely run C code.

Here is the complete sequence of operations, in the exact order the boot code executes them:
\begin{table}[h!]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{Step} & \textbf{Why} \\ \hline
1. Mask interrupts & Nothing may interrupt a half-built system \\ \hline
2. Set SP & C functions inherently need a stack \\ \hline
3. Copy \texttt{.data} FLASH $\rightarrow$ RAM & Initialized global variables must get their values \\ \hline
4. Zero \texttt{.bss} & C promises uninitialized global variables start at 0 \\ \hline
5. Configure the CPU & Set up vector table address, fault handlers, traps, priorities \\ \hline
6. Unmask interrupts, \texttt{bl main} & Hand execution over to C \\ \hline
7. Loop forever & If \texttt{main} ever returns, there is nowhere to go \\ \hline
\end{tabular}
\end{table}

In the base skeleton, \texttt{Reset\_Handler} has only steps 6 and 7 (and without the unmask). The following sections go through building the remaining steps in order.

\subsection{Steps 1 and 2: Mask Interrupts and Set the Stack}
An \textbf{interrupt} is an exception raised by hardware (e.g., a timer expiring or a device receiving data): the CPU drops what it is doing and runs that interrupt's handler. During setup, absolutely nothing is ready to handle one: a handler written in C could attempt to read a variable that has not been initialized yet.

Therefore, the very first instruction, \texttt{cpsid i}, tells the CPU to explicitly ignore interrupts for now. (While no device has been told to raise an interrupt yet, writing it makes the rule explicit instead of relying on luck).

Next, the stack pointer (\texttt{SP}) must be set:
\begin{lstlisting}
@ C equivalent: sp = &_estack;
ldr r0, =_estack    @ top of RAM, 0x20400000
mov sp, r0
\end{lstlisting}

Because C has no way to name SP directly, the C equivalent is pseudo-code. One might wonder why this step is strictly needed, since the hardware already loaded SP from word 0 of the vector table at reset. The answer is that \texttt{Reset\_Handler} is not \textit{always} reached through a real hardware reset: a custom bootloader or a debugger may jump to it directly, with SP holding an arbitrary or invalid value. 

Setting SP explicitly makes the code robust and correct in every case, and demonstrates that the stack is nothing more than an address in a register. Notice the two-step ARM pattern: because SP is a special register, the address is first loaded into an ordinary general-purpose register (\texttt{r0}), and then explicitly copied into SP using \texttt{mov}.

\subsection{Step 3: Copy \texttt{.data} from FLASH to RAM}
This is the critical step that fixes the base skeleton's missing print line. The linker script gives you three key addresses:

\begin{lstlisting}[language=make]
FLASH:  [ .text | .rodata | initial values of .data ]
                             ^ _sidata
RAM:    [ .data             | .bss | ...        stack ]
          ^ _sdata          ^ _edata                  ^ _estack
\end{lstlisting}

The copy operation is a simple loop, which you can write first in C and then translate line by line into assembly:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{C Equivalent} & \textbf{ARM Assembly} \\ \hline
\texttt{uint32\_t *src = \&\_sidata;} & \texttt{ldr r0, =\_sidata} \\
\texttt{uint32\_t *dst = \&\_sdata;} & \texttt{ldr r1, =\_sdata} \\
\texttt{                      } & \texttt{ldr r2, =\_edata} \\ \hline
\texttt{while (dst < \&\_edata)} & \texttt{copy\_data: cmp r1, r2} \\
\texttt{                      } & \texttt{            bhs copy\_data\_done} \\ \hline
\texttt{    *dst++ = *src++;  } & \texttt{            ldr r3, [r0], \#4} \\
\texttt{                      } & \texttt{            str r3, [r1], \#4} \\
\texttt{                      } & \texttt{            b   copy\_data} \\ \hline
\texttt{                      } & \texttt{copy\_data\_done:} \\ \hline
\end{tabular}
\end{table}

Register \texttt{r0} plays the role of \texttt{src}, \texttt{r1} of \texttt{dst}, and \texttt{r2} holds the end address. The loop is named \texttt{copy\_data} in \texttt{boot/startup.s}, and it exits to \texttt{copy\_data\_done}. It copies whole words, 4 bytes at a time; this is perfectly safe because the linker script intentionally aligns the start and end of \texttt{.data} to multiples of 4.

If you write steps 1--3 into the base skeleton (just before \texttt{bl main}) and run it, the missing line finally appears:
\begin{lstlisting}[language=bash]
make run
main: hello from the base
main: this text lives in .data
\end{lstlisting}
Before the copy, \texttt{data\_message} sat in RAM as all zeros and printed as an empty string; now it successfully holds its initial value.

\subsubsection{Watching the Copy Loop in GDB}
It is worth watching your loop run because it makes the abstract ideas of LMA and VMA concrete. Start \texttt{make debug} in terminal 1 and gdb in terminal 2, then:

\begin{lstlisting}[language=bash]
(gdb) target remote :1234
(gdb) display/i $pc
(gdb) stepi                      # press Enter to repeat, until "cmp r1, r2"
(gdb) p/x $r0                    # src: a FLASH address
(gdb) p/x $r1                    # dst: 0x20000000, start of RAM
(gdb) x/s &data_message          # "" : nothing copied yet
(gdb) stepi 5                    # one full turn of the loop
(gdb) p/x $r1                    # 0x20000004
(gdb) break copy_data_done
(gdb) continue
(gdb) x/s &data_message          # "main: this text lives in .data\n"
\end{lstlisting}

As you step, \texttt{display/i \$pc} shows each instruction just before it runs: \texttt{cpsid i}, then the \texttt{ldr} from the literal pool, then \texttt{mov sp, r0}, then the three \texttt{ldr} commands that load the loop bounds. 

When you reach \texttt{cmp r1, r2}, \texttt{r0} holds a small flash address (e.g., \texttt{0x88}, depending on how much code precedes it), and \texttt{r1} holds \texttt{0x20000000}. \texttt{x/s \&data\_message} shows the empty string because nothing has been copied yet. 

Five more \texttt{stepi} commands execute one full turn of the loop (\texttt{cmp}, \texttt{bhs}, \texttt{ldr}, \texttt{str}, \texttt{b}), and \texttt{r1} moves to \texttt{0x20000004} (one word copied). Instead of stepping 8 times more, you put a breakpoint on the label after the loop and continue. \texttt{r1} climbs until it equals \texttt{r2} (\texttt{\&\_edata}, which is \texttt{0x20000020}), and only then does \texttt{x/s \&data\_message} show the full string perfectly mapped in RAM.

\subsubsection{Try It: Breaking the Stack on Purpose}
Seeing a wrong SP fail is the best way to believe that SP matters. In \texttt{boot/startup.s}, inside \texttt{Reset\_Handler}, find the line you wrote in Step 2 (\texttt{ldr r0, =\_estack}) and intentionally replace \texttt{\_estack} with a bad address. (Note that the value the CPU loaded from vector word 0 at reset is still the correct one; it is your \texttt{mov sp, r0} that forcefully overwrites it with the bad address).

\paragraph{Test 1: Address Outside of RAM (\texttt{0x30000000})}
If you force SP to \texttt{0x30000000} and run \texttt{make run}, nothing is printed at all. QEMU stops with:
\begin{lstlisting}[language=bash]
qemu: fatal: Lockup: can't escalate 3 to HardFault (current priority -1)
\end{lstlisting}
Here is what happened: the first thing \texttt{main} does is push registers onto the stack, writing below \texttt{0x30000000}, where there is no physical memory. That access triggers a fault. The CPU tries to report the fault by executing a fault handler, but entering a handler inherently requires writing to the stack, which fails again. With no way to report the fault, the CPU gives up and enters a state called \textbf{lockup}.

\paragraph{Test 2: Unaligned Stack Pointer (\texttt{0x20000001})}
If you force SP to an odd address inside RAM, \texttt{make run} prints nothing. To see why, start \texttt{make debug}, stop right after your \texttt{mov sp, r0}, and check the register: \texttt{info registers sp} returns \texttt{0x20000000}. 

The CPU silently drops the two lowest bits of SP because the stack pointer must always be a multiple of 4. The stack now inadvertently starts at the very bottom of RAM and grows \textit{below} it. At \texttt{break main}, SP is already under \texttt{0x20000000} (e.g., \texttt{0x1ffffff0}), in an address range where QEMU simply ignores writes. There is no explicit crash, just no output at all because the function calls fail silently. (Remember to restore \texttt{ldr r0, =\_estack} before continuing).

\subsection{Step 4: Zero the \texttt{.bss} Section}
The C standard strictly promises that global variables without an explicit initializer (e.g., \texttt{int counter;}) will start at \texttt{0}[cite: 46]. They physically reside in the \texttt{.bss} section, mapped between \texttt{\_sbss} and \texttt{\_ebss} in RAM[cite: 46]. Because nothing in flash holds their zeroed value, the boot code must explicitly write these zeros[cite: 46]. 

This is the exact same looping logic as the data copy, but without a source pointer reading from flash[cite: 46]:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{C Equivalent} & \textbf{ARM Assembly} \\ \hline
\texttt{uint32\_t *dst = \&\_sbss;} & \texttt{ldr r1, =\_sbss} \\
\texttt{                      } & \texttt{ldr r2, =\_ebss} \\
\texttt{                      } & \texttt{movs r3, \#0} \\ \hline
\texttt{while (dst < \&\_ebss)} & \texttt{zero\_bss: cmp r1, r2} \\
\texttt{                      } & \texttt{           bhs zero\_bss\_done} \\ \hline
\texttt{    *dst++ = 0;       } & \texttt{           str r3, [r1], \#4} \\
\texttt{                      } & \texttt{           b   zero\_bss} \\ \hline
\texttt{                      } & \texttt{zero\_bss\_done:} \\ \hline
\end{tabular}
\end{table}

This loop is labeled \texttt{zero\_bss} in \texttt{boot/startup.s}[cite: 46]. In the current base skeleton, \texttt{.bss} happens to be empty (so \texttt{\_sbss} equals \texttt{\_ebss}), meaning the loop exits immediately[cite: 46]. However, the first uninitialized global you add (like \texttt{int total;}) will absolutely rely on it[cite: 46]. 

\textit{Warning:} Remember that RAM is \textit{not} zeroed at power-on on real hardware[cite: 46]. While the QEMU emulator zeroing RAM for you is a convenience, you must not architecturally count on it[cite: 46].

With steps 1 through 4 completed, \texttt{Reset\_Handler} replicates everything that the previous C startup code did[cite: 46]. The remaining steps go further: they configure the CPU so that errors are caught, escalated, and reported[cite: 46].

\section{Exceptions and Faults: One Family}
You have already encountered the concept of an \textbf{exception}: any hardware or software event that forces the CPU to stop executing the current code and run a specific handler function[cite: 46]. The CPU fetches the address of this handler from the vector table and executes it in Handler mode[cite: 46]. 

The Cortex-M3 physically defines the following family of exceptions[cite: 46]:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|l|}
\hline
\textbf{\#} & \textbf{Exception} & \textbf{Raised by} \\ \hline
0 & \textit{(not an exception)} & This slot holds the initial SP value \\ \hline
1 & Reset & Power-on, reset button \\ \hline
2 & NMI & Non-maskable interrupt: cannot be ignored \\ \hline
3 & \textbf{HardFault} & Any fault with nowhere else to go \\ \hline
4 & \textbf{MemManage} & Breaking memory protection rules \\ \hline
5 & \textbf{BusFault} & Access to an address where nothing answers, or that refuses access \\ \hline
6 & \textbf{UsageFault} & Bad use of an instruction: undefined opcode, Thumb bit 0, divide by 0 \\ \hline
7--10 & \textit{reserved} & Unused: the slot must hold \texttt{0} \\ \hline
11 & SVCall & The \texttt{svc} instruction \\ \hline
12 & DebugMonitor & Debug events (unused here) \\ \hline
13 & \textit{reserved} & Unused: the slot must hold \texttt{0} \\ \hline
14 & PendSV & A request raised by software \\ \hline
15 & SysTick & The CPU's built-in timer \\ \hline
16+ & IRQs & External device interrupts \\ \hline
\end{tabular}
\end{table}

Slots 7--10 and 13 are strictly reserved[cite: 46]. The four specific faults (3 through 6) are the CPU's direct way of signaling that "the program did something wrong"[cite: 46]. 

Crucially, at power-on reset, only the \texttt{HardFault} exception is actively listening[cite: 46]. The three more specific faults (\texttt{MemManage}, \texttt{BusFault}, \texttt{UsageFault}) are disabled by default[cite: 46]. When a specific fault is disabled, it \textit{escalates} directly to a \texttt{HardFault}[cite: 46]. This escalation mechanism explains the "can't escalate 3 to HardFault" lockup message we saw earlier: the CPU was trying to escalate to exception 3 (\texttt{HardFault}), but because the handler could not safely push to the stack, it failed[cite: 46].

\subsection{Completing the Vector Table with Weak Symbols}
The base table only has 2 words defined, but the Cortex-M3 expects one word for each exception from 0 to 15 (16 words in total)[cite: 46]. Every slot strictly needs \textit{some} valid address, even for exceptions you have no custom handler for yet, because if that hardware exception triggers, the CPU will blindly jump to whatever address the slot contains[cite: 46]. (The reserved slots must contain \texttt{0})[cite: 46].

Therefore, \texttt{isr\_vector} in \texttt{boot/startup.s} gets 14 additional \texttt{.word} entries[cite: 46]. Instead of writing a dozen empty functions for every single exception, the standard engineering practice is to route them all to a generic default loop using weak symbols and aliases in assembly[cite: 47]:

\begin{lstlisting}
    .word HardFault_Handler                    @ slot 3, and so on up to 15
    .weak      HardFault_Handler               @ may be replaced from C
    .thumb_set HardFault_Handler, Default_Handler
Default_Handler:
    b Default_Handler                          @ for (;;) {}
\end{lstlisting}

Which translates to the following compiler directive in C[cite: 47]:
\begin{lstlisting}[language=c]
void HardFault_Handler(void) __attribute__((weak, alias("Default_Handler")));
\end{lstlisting}

\textbf{How it works:}
\begin{itemize}
    \item \texttt{.word HardFault\_Handler} places the address of the label into the exact table slot[cite: 47].
    \item \texttt{.thumb\_set} dictates to the assembler: "Make \texttt{HardFault\_Handler} another name for \texttt{Default\_Handler} (sharing the same address, marked as Thumb code)"[cite: 47].
    \item \texttt{.weak} makes that name a \textbf{weak symbol}: a default implementation that easily yields[cite: 47]. If any other file (like \texttt{src/main.c}) explicitly defines a normal, non-weak function named \texttt{void HardFault\_Handler(void)}, the linker silently drops the weak assembly default and routes the hardware exception directly to the developer's custom C function[cite: 47].
\end{itemize}

\texttt{Default\_Handler} itself is simply an infinite loop[cite: 47]. An unexpected exception is a critical system bug, and freezing the CPU at a known, predictable place is much easier to diagnose in a debugger than allowing it to run off into random memory addresses[cite: 47].

\subsubsection{The Effect on Memory Layout}
Completing the vector table immediately alters your memory layout[cite: 47]. The table grows physically from 2 words to 16 words (from 8 bytes to 64 bytes)[cite: 47]. Because the executable code still flows right after it in FLASH, the start of \texttt{Reset\_Handler} moves down from address \texttt{0x8} to \texttt{0x40}[cite: 47]. 

If you attach GDB at reset now, \texttt{info registers sp pc} will show \texttt{pc 0x40 <Reset\_Handler>}, and examining address 0 (\texttt{x/2wx 0}) will print \texttt{0x0 <isr\_vector>: 0x20400000 0x00000041} (proving the Thumb bit is added to the \texttt{0x40} address)[cite: 47]. 

If you examine the \texttt{nm} output of the final binary, you will clearly see the effect of the weak symbols: \texttt{NMI\_Handler}, \texttt{PendSV\_Handler}, \texttt{SysTick\_Handler}, and \texttt{DebugMon\_Handler} are explicitly marked \texttt{W} (weak) and all share the exact same memory address as \texttt{Default\_Handler}[cite: 47]. Meanwhile, any handlers written and compiled from \texttt{src/main.c} are firmly marked \texttt{T} (Text) at their own unique addresses[cite: 47].

\subsection{CPU Settings Live at Memory Addresses}
The remaining configuration steps change settings inside the CPU core itself. You do not need special assembly instructions for most of them: the Cortex-M architecture makes these settings physically available as 32-bit registers at fixed memory addresses in the system area of the memory map (specifically, from \texttt{0xE000E000} to \texttt{0xE000EFFF}). 

The specific group of registers that controls exceptions is called the \textbf{System Control Block (SCB)}. You can change them using ordinary load and store instructions.

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{C Equivalent} & \textbf{ARM Assembly} \\ \hline
\texttt{\#define SCB\_SHCSR (*(volatile uint32\_t *)0xE000ED24)} & \\ 
\texttt{SCB\_SHCSR |= (1u << 16);} & \texttt{ldr r0, =0xE000ED24   @ address} \\
& \texttt{ldr r1, [r0]          @ read} \\
& \texttt{orr r1, r1, \#0x10000 @ modify} \\
& \texttt{str r1, [r0]          @ write} \\ \hline
\end{tabular}
\end{table}

\subsubsection{The Read-Modify-Write Pattern and \texttt{volatile}}
This architectural pattern is known as \textbf{read-modify-write}: you read the current value of the register, modify only the specific bits you care about using a bitwise OR, and write the result back. This ensures that all other configuration bits in the register keep their original values.

In the C version, the \texttt{volatile} keyword is mandatory. It explicitly tells the compiler that every memory access must truly happen exactly in the order written. Without it, the compiler's optimizer might skip a read (assuming "the value cannot have changed") or remove a write (assuming "nobody reads it"). For hardware registers, both assumptions are completely false.

\textit{Debugging tip:} You can read these registers from gdb just like any other memory address. For example, \texttt{x/wx 0xE000ED00} shows \texttt{0x410fc231}, which is the CPUID register identifying the chip as an ARM (\texttt{0x41}) Cortex-M3 (\texttt{0xc23}).

\subsection{Step 5: VTOR, Where the Vector Table Is}
When an exception happens, the CPU does not technically read slot $N$ strictly at address \texttt{4 * N}. It reads it at \texttt{\textbf{VTOR} + 4 * N}, where \textbf{VTOR} (the Vector Table Offset Register, located at \texttt{0xE000ED08}) holds the base address of the table. 

Its default value at reset is \texttt{0x00000000}, which is exactly why our initial table must reside at address 0. However, the boot code explicitly writes the address of \texttt{isr\_vector} into it anyway:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{C Equivalent} & \textbf{ARM Assembly} \\ \hline
\texttt{*(volatile uint32\_t *)0xE000ED08 = } & \texttt{ldr r0, =0xE000ED08} \\
\texttt{                       (uint32\_t)isr\_vector;} & \texttt{ldr r1, =isr\_vector} \\
& \texttt{str r1, [r0]} \\ \hline
\end{tabular}
\end{table}

(Note: The table address must be suitably aligned, at least to 128 bytes, because the low bits of VTOR are not used by the hardware).

Why perform this write if our table is already at 0? Because in real production systems, the table is often located elsewhere. A \textbf{bootloader} sitting at address 0 may start an application stored higher in the flash memory, whose own vector table is at a different address. The application must then point VTOR to its own table. Alternatively, an OS may copy its table into RAM to replace handlers dynamically while running. Explicitly writing VTOR ensures the boot code remains correct regardless of where the final image is placed.

\textbf{Where you write it:} In \texttt{Reset\_Handler}, right after the label \texttt{zero\_bss\_done:} (the end of step 4). Because you are setting the entire register to a new absolute address, no read-modify-write is needed. In gdb at \texttt{main}, \texttt{x/wx 0xE000ED08} will show \texttt{0x00000000}: the same as the reset value, confirming the table is at address 0 (verified by \texttt{p/x \&isr\_vector}).

\subsection{Step 6: SHCSR, Separate Fault Handlers}
The \textbf{SHCSR} (System Handler Control and State Register) at address \texttt{0xE000ED24} enables the three specific hardware faults:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|l|}
\hline
\textbf{Bit} & \textbf{Name} & \textbf{When set} \\ \hline
16 & MEMFAULTENA & MemManage faults run \texttt{MemManage\_Handler} \\ \hline
17 & BUSFAULTENA & Bus faults run \texttt{BusFault\_Handler} \\ \hline
18 & USGFAULTENA & Usage faults run \texttt{UsageFault\_Handler} \\ \hline
\end{tabular}
\end{table}

At reset, these bits are heavily restricted (set to 0), meaning all faults instantly escalate to a \texttt{HardFault}. This gives you a single handler for every kind of error, making it impossible to tell \textit{what} specifically went wrong inside it. 

The boot code must set bits 16--18 simultaneously with a bitwise OR (\texttt{|= 0x00070000}), ensuring each fault routes cleanly to its own dedicated handler. Because the other bits of SHCSR report critical system status (like which handlers are active or pending), you \textbf{must} use the read-modify-write pattern and never simply overwrite the whole register.

\textbf{Where you write it:} Right after step 5. You implement the read-modify-write pattern: \texttt{ldr r0, =0xE000ED24}, then \texttt{ldr r1, [r0]} (read), \texttt{orr r1, r1, \#0x00070000} (modify), and finally \texttt{str r1, [r0]} (write). In gdb at \texttt{main}, checking \texttt{x/wx 0xE000ED24} will correctly display \texttt{0x00070000}.

\subsection{Step 7: CCR, What Counts as a Fault}
\textbf{CCR}, the Configuration and Control Register physically located at \texttt{0xE000ED14}, dictates whether certain suspicious CPU operations are classified as faults at all.

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|l|l|}
\hline
\textbf{Bit} & \textbf{Name} & \textbf{Meaning} & \textbf{Here} \\ \hline
3 & UNALIGN\_TRP & Trap unaligned word/halfword accesses & left off \\ \hline
4 & DIV\_0\_TRP & Trap integer divide by 0 (as a UsageFault) & \textbf{set} \\ \hline
9 & STKALIGN & 8-byte-align the stack on exception entry & already 1 \\ \hline
\end{tabular}
\end{table}

Without the \texttt{DIV\_0\_TRP} bit set, an integer division by zero on the Cortex-M3 does not inherently trigger a fault: the hardware divide instruction silently returns \textbf{0}. The program would continue running with a mathematically incorrect value, and nobody would notice. Setting bit 4 transforms that silent, catastrophic bug into an immediate \texttt{UsageFault}. 

Unaligned memory accesses, on the other hand, are strictly legal on the Cortex-M3 (though slightly slower). While trapping them can help identify sloppy pointer casts, it can also inadvertently break correct, optimized code produced by the C compiler or standard libraries. Therefore, it is intentionally left off. Bit 9 (\texttt{STKALIGN}) is already set to 1 at hardware reset, and the read-modify-write pattern safely preserves it.

\textbf{Where you write it:} Right after step 6. The implementation requires the same four read-modify-write instructions: the address becomes \texttt{0xE000ED14} and the bitwise OR utilizes \texttt{\#(1 << 4)}. The C equivalent is \texttt{*(volatile uint32\_t *)0xE000ED14 |= (1u << 4);}. Here, read-modify-write is absolutely critical because bit 9 (\texttt{STKALIGN}) is already 1 and must remain 1. In gdb at \texttt{main}, checking \texttt{x/wx 0xE000ED14} will successfully show \texttt{0x00000210}.

\subsection{Step 8: Exception Priorities}
When two exceptions compete simultaneously, the more urgent one executes first. An urgent exception can even pre-empt and interrupt a handler that is already currently running for a less urgent one. 

On the Cortex-M architecture, \textbf{a lower number means a more urgent priority}. Reset (-3), NMI (-2), and HardFault (-1) possess fixed, immutable priorities that are mathematically more urgent than anything a developer can configure. (This finally explains the lockup message encountered earlier: "current priority -1" means the CPU was already executing at the HardFault level, meaning there was physically nowhere higher left to escalate).

Every other exception has a configurable priority, stored as a single byte in the \textbf{SHPR} (System Handler Priority Registers):

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|l|l|l|}
\hline
\textbf{Register} & \textbf{Byte 0} & \textbf{Byte 1} & \textbf{Byte 2} & \textbf{Byte 3} \\ \hline
SHPR1 (\texttt{0xE000ED18}) & MemManage & BusFault & UsageFault & --- \\ \hline
SHPR2 (\texttt{0xE000ED1C}) & --- & --- & --- & SVCall \\ \hline
SHPR3 (\texttt{0xE000ED20}) & --- & --- & PendSV & SysTick \\ \hline
\end{tabular}
\end{table}

Because each priority is strictly a byte of its own, the boot code writes it directly using a byte store instruction (\texttt{strb}). This entirely bypasses the need for the read-modify-write pattern:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{C Equivalent} & \textbf{ARM Assembly} \\ \hline
\texttt{uint8\_t *prio = (uint8\_t *)0xE000ED18;} & \texttt{ldr r0, =0xE000ED18} \\
\texttt{movs r1, \#0x00} & \texttt{strb r1, [r0, \#1]} \\
\texttt{prio[1] = 0x00; /* BusFault: urgent */} & \\ \hline
\end{tabular}
\end{table}

The architectural choice made in \texttt{Reset\_Handler} is structured as follows: faults are the most urgent (\texttt{0x00}), SVCall sits in the middle (\texttt{0x80}), and PendSV alongside SysTick are the least urgent (\texttt{0xE0}). Real physical chips typically implement only the \textbf{upper} 3 or 4 bits of each priority byte (the lower bits always read as 0), so you must purposefully choose hexadecimal values that differ in their top bits, such as these.

\textbf{Where you write it:} Right after step 7. Think of SHPR1, SHPR2, and SHPR3 collectively as a contiguous array of 12 bytes starting at address \texttt{0xE000ED18}. 
\begin{itemize}
    \item \texttt{prio[0]}, \texttt{prio[1]}, and \texttt{prio[2]} map to MemManage, BusFault, and UsageFault (set to \texttt{0x00}).
    \item \texttt{prio[7]} maps to SVCall (SHPR2 byte 3, which is $4 + 3$; set to \texttt{0x80}).
    \item \texttt{prio[10]} and \texttt{prio[11]} map to PendSV and SysTick (SHPR3 bytes 2 and 3; set to \texttt{0xE0}).
\end{itemize}
In assembly, you load the base address \texttt{0xE000ED18} into \texttt{r0} exactly once. Then, for each distinct value, you execute a \texttt{movs r1, \#value} followed by one \texttt{strb r1, [r0, \#index]} instruction per byte. In gdb at \texttt{main}, checking \texttt{x/3wx 0xE000ED18} will explicitly show \texttt{0x00000000 0x80000000 0xe0e00000}.

\subsection{Step 9 and After: PRIMASK and Handing Over to C}
The \texttt{cpsid i} and \texttt{cpsie i} instruction pair operates directly on \textbf{PRIMASK}, a special 1-bit register physically located inside the CPU core (it is not mapped in standard memory). When PRIMASK is set to 1, the CPU aggressively ignores every exception that has a configurable priority; only NMI and HardFault are allowed to pass through.

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|l|}
\hline
\textbf{Instruction} & \textbf{PRIMASK State} & \textbf{C (vendor headers)} \\ \hline
\texttt{cpsid i} & 1: masked & \texttt{\_\_disable\_irq()} \\ \hline
\texttt{cpsie i} & 0: accepted & \texttt{\_\_enable\_irq()} \\ \hline
\end{tabular}
\end{table}

PRIMASK defaults to \texttt{0} at reset. The boot code deliberately sets it at the very beginning (Step 1) and meticulously clears it just before calling \texttt{bl main}, ensuring that the vector table, handlers, and exception priorities are entirely configured before any interrupts are permitted. 

Interrupts that arrive while the system is masked are not discarded or lost: the hardware registers them as \textbf{pending}, forcing them to wait, and immediately executes them as soon as PRIMASK is cleared. You can observe the PRIMASK state in gdb by typing \texttt{info registers primask}.

After \texttt{cpsie i} comes the \texttt{bl main} instruction, seamlessly handing execution over to your C code. Following this, the assembly file implements a \texttt{hang} label with a \texttt{b hang} instruction. This is the architectural equivalent of an infinite \texttt{for (;;) \{\}} loop: on a bare-metal machine, if \texttt{main} ever inadvertently returns, there is physically nowhere to return to, so the CPU must spin safely forever.

\textbf{Where you write it:} \texttt{cpsid i} is already present as Step 1. Step 9 is a single \texttt{cpsie i} instruction, inserted right after Step 8 and just before \texttt{bl main}. In gdb, inspecting \texttt{info registers primask} will correctly show \texttt{0} at reset, \texttt{1} after a single \texttt{stepi} (past \texttt{cpsid i}), and \texttt{0} again once execution reaches \texttt{main}.

\subsection{Checking the Configuration from GDB}
Once steps 4 through 9 are written, you can definitively prove that all hardware bits are correctly configured by the time \texttt{main} starts. With \texttt{make debug} running in your first terminal, execute the following in GDB:

\begin{lstlisting}[language=bash]
(gdb) target remote :1234
(gdb) info registers primask    # 0 at reset; after stepping past cpsid i: 1
(gdb) break main
(gdb) continue
(gdb) x/wx 0xE000ED08           # VTOR
(gdb) x/wx 0xE000ED24           # SHCSR
(gdb) x/wx 0xE000ED14           # CCR
(gdb) x/3wx 0xE000ED18          # SHPR1..3
\end{lstlisting}

The expected memory values are precisely as follows:
\begin{itemize}
    \item \textbf{VTOR:} \texttt{0x00000000} (unchanged, meaning the table is actively at address 0).
    \item \textbf{SHCSR:} \texttt{0x00070000}, which exactly corresponds to bits 16, 17, and 18 being active.
    \item \textbf{CCR:} \texttt{0x00000210}, which is bit 4 (\texttt{0x10}, the division-by-zero trap you added) plus bit 9 (\texttt{0x200}, the stack alignment bit already set at reset).
    \item \textbf{SHPR:} \texttt{0x00000000 0x80000000 0xe0e00000}.
\end{itemize}

\textbf{Reading the SHPR byte by byte:} Because the Cortex-M architecture is little-endian, byte 0 is the rightmost pair of hex digits.
\begin{itemize}
    \item \textbf{SHPR1} is all zeros (the three specific faults are set to the highest configurable priority).
    \item \textbf{SHPR2} has \texttt{0x80} strictly in byte 3 (corresponding to SVCall).
    \item \textbf{SHPR3} has \texttt{0xe0} strictly in bytes 2 and 3 (corresponding to PendSV and SysTick, the lowest priorities).
\end{itemize}

\subsection{Catching a Divide by Zero}
The configuration performed in the \texttt{Reset\_Handler} is only useful if it successfully catches real errors in the code. To prove this, we can write custom fault handlers in C and intentionally trigger a fault.

In \texttt{src/main.c} (right after \texttt{data\_message} and before \texttt{main}), you can write four functions utilizing the exact names defined in the vector table: \texttt{HardFault\_Handler}, \texttt{MemManage\_Handler}, \texttt{BusFault\_Handler}, and \texttt{UsageFault\_Handler}. Each function prints its own name using the same \texttt{semihost\_write0} function that \texttt{main} uses, and then enters an infinite loop:

\begin{lstlisting}[language=c]
void UsageFault_Handler(void)
{
    semihost_write0("UsageFault_Handler: a usage fault happened\n");
    for (;;) { }
}
\end{lstlisting}

Because these are normal (strong) C definitions, the linker uses them to silently replace the weak assembly defaults established in \texttt{boot/startup.s}. They loop forever because a fault represents a critical bug; there is no sensible way to continue execution safely.

\subsubsection{Triggering the Fault}
To test the handlers, we can force \texttt{main} to divide by zero. Crucially, the divisor must be a \texttt{volatile} variable holding \texttt{0}: without \texttt{volatile}, the compiler's optimizer will detect the constant division, compute or remove it entirely at compile time, and no physical divide instruction will ever be executed by the CPU.

Using a preprocessor switch allows us to toggle the demo safely:
\begin{lstlisting}[language=c]
#define DEMO_DIVIDE_BY_ZERO 1

/* Inside main() */
#if DEMO_DIVIDE_BY_ZERO
    volatile uint32_t numerator = 42;
    volatile uint32_t zero = 0;
    volatile uint32_t result = numerator / zero;
    (void)result; /* Suppresses the 'unused variable' compiler warning */
#endif
\end{lstlisting}

Running \texttt{make run} will successfully halt the program and print:
\begin{lstlisting}[language=bash]
UsageFault_Handler: a usage fault happened
\end{lstlisting}

\subsubsection{Validating the Configuration Steps}
The two hardware configuration steps we added each play a distinct role, which can be verified by disabling them one at a time:
\begin{itemize}
    \item \textbf{Without Step 6 (SHCSR bits):} The specific usage fault is disabled. The hardware escalates the error, and you see \texttt{HardFault\_Handler: a hard fault happened}. The critical information regarding \textit{what} specific kind of fault occurred is permanently lost.
    \item \textbf{Without Step 7 (DIV\_0\_TRP):} You see no fault message at all. The division silently returns \texttt{0}, and \texttt{main} continues executing its usual lines as if nothing happened. This is precisely the silent, catastrophic bug the trap was configured to catch.
\end{itemize}

\subsection{What Real Chips Add (\texttt{SystemInit})}
The QEMU emulator's CPU is ready to run at full speed the moment it leaves reset. However, on a real physical microcontroller, the startup code usually must perform significantly more initialization before \texttt{main} is called. This is typically done in a vendor-supplied function called \texttt{SystemInit()}, which is called directly from \texttt{Reset\_Handler}. 

Even though our emulator does not strictly require them, you should understand what a standard \texttt{SystemInit()} typically handles:
\begin{itemize}
    \item \textbf{Clock and PLL:} The chip naturally starts on a slow internal oscillator for stability. A Phase-Locked Loop (PLL) circuit must be configured to multiply that frequency up to the chip's maximum operational speed.
    \item \textbf{Flash Wait States:} Physical Flash memory is fundamentally slower than a high-speed CPU. Before ramping up the clock frequency, the code must instruct the flash controller to insert extra "wait cycles" into each memory access; otherwise, the CPU would fetch invalid garbage data.
    \item \textbf{Watchdog Timer:} A watchdog is a hardware timer that automatically resets the chip unless the software periodically "feeds" (resets) it. This acts as a physical safeguard against a program that hangs. On some chips, the watchdog is active immediately upon reset, so the boot code must either explicitly turn it off or begin feeding it.
    \item \textbf{FPU (Floating-Point Unit):} On architectures like the Cortex-M4F, the FPU is disabled at reset to save power. It must be explicitly enabled via the \textbf{CPACR} register (\texttt{0xE000ED88}); otherwise, executing the very first \texttt{float} instruction will trigger a \texttt{UsageFault}.
    \item \textbf{C++ Static Constructors:} If writing an OS or application in C++, the startup code must explicitly iterate through the \texttt{.init\_array} section and call all static object constructors before jumping to \texttt{main}.
\end{itemize}

\section{Life Without an Operating System}
Your program now boots entirely on code you explicitly wrote. This unit examines what is \textit{not} there and the architectural consequences of those missing layers. It culminates with the program's final structural form: \texttt{main} intentionally relinquishing its privileges and then requesting privileged work back through a formal system call.

\subsection{Hosted vs. Freestanding C Environments}
The C standard strictly defines two distinct execution environments for any C program.

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|l|}
\hline
 & \textbf{Hosted} & \textbf{Freestanding} \\ \hline
\textbf{Example} & Your laptop program & Our Cortex-M3 image \\ \hline
\textbf{Under your code} & A C library (\textbf{libc}) and an OS & Nothing \\ \hline
\textbf{\texttt{printf}, \texttt{malloc}, \texttt{fopen}, \texttt{exit}} & Available & Not available \\ \hline
\textbf{Who starts \texttt{main()}} & libc startup code, called by the OS & Whoever you decide \\ \hline
\end{tabular}
\end{table}

On a standard laptop, writing \texttt{printf("hi\textbackslash{}n")} "just works" because two massive, complex layers sit directly beneath your program doing the heavy lifting: the C library and the Operating System. Our embedded image operates in a \textbf{freestanding} environment. Below your bare-metal code, there is absolutely nothing.

\subsubsection{What is Available in Freestanding C?}
A freestanding environment still provides a subset of standard headers. However, these are strictly headers that require \textbf{no code execution at run time}. They provide only data types, architectural constants, and macros that the compiler resolves entirely at build time.

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{Header} & \textbf{Provides} \\ \hline
\texttt{<stdint.h>} & \texttt{uint32\_t}, \texttt{int8\_t}, ... \\ \hline
\texttt{<stddef.h>} & \texttt{size\_t}, \texttt{NULL}, \texttt{offsetof} \\ \hline
\texttt{<stdbool.h>} & \texttt{bool}, \texttt{true}, \texttt{false} \\ \hline
\texttt{<stdarg.h>} & \texttt{va\_list}, for variadic functions \\ \hline
\texttt{<limits.h>}, \texttt{<float.h>} & \texttt{INT\_MAX}, \texttt{FLT\_EPSILON}, ... \\ \hline
\end{tabular}
\end{table}

This is precisely why \texttt{src/main.c} only includes \texttt{<stdint.h>}. There is no \texttt{<stdio.h>}, no \texttt{<stdlib.h>}, and no \texttt{<string.h>}: this means no printing, no dynamic allocation (\texttt{malloc}), no file I/O, no \texttt{exit}, and not even \texttt{memcpy}. Anything else required by the system, you must write yourself. (This lack of standard library support is the exact reason the assembly boot code had to manually copy the \texttt{.data} section with its own explicit loop rather than just calling a convenient \texttt{memcpy}).

\subsection{What is Really Under \texttt{printf}}
To understand why standard functions fail without an OS, it helps to dissect what \texttt{printf} actually does under the hood on a hosted system (like a laptop):

\begin{lstlisting}[language=make]
printf("x=%d\n", x)          your program
   |  format the text into a buffer          ]   v                                         | libc
write(1, buf, len)                           ]
   |  system call: the CPU enters the kernel   ]
   v                                           | OS kernel
terminal / file / serial device driver         ]
   |
   v
hardware (screen, UART, disk)
\end{lstlisting}

\texttt{printf} itself only performs \textbf{formatting}: it takes a format string like \texttt{"x=\%d\textbackslash{}n"} and the value of \texttt{x}, and parses them into a raw sequence of ASCII characters stored in a memory buffer. 

However, getting those physical characters out of the machine to a screen is not \texttt{printf}'s job. To do that, it calls \texttt{write()}, which triggers a \textbf{system call}. A system call forces the CPU to enter the Operating System kernel. The kernel's specific device driver then takes over, physically sending the bytes to the terminal, a file, or a serial hardware device.

\texttt{printf} is not the only C library feature that relies on hidden, lower-level OS hooks:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{libc feature} & \textbf{What it needs underneath} \\ \hline
\texttt{printf}, \texttt{puts} & \texttt{write()}: a way to send bytes to a physical device \\ \hline
\texttt{malloc}, \texttt{free} & a heap memory region, dynamically grown via \texttt{sbrk()} \\ \hline
\texttt{exit} & an OS process manager to return control to \\ \hline
\texttt{main()} being called & startup code (\textbf{crt0}): sets up the stack, \texttt{.data}, \texttt{.bss}, then calls \texttt{main} \\ \hline
\end{tabular}
\end{table}

C libraries designed for embedded systems (such as \textbf{newlib}) implement the high-level formatting logic and data structures, but they intentionally leave these bottom-level hardware functions as empty \textbf{hooks} (stubs) that the developer must manually implement for their specific physical board.

\subsection{Why This Course Uses No libc At All}
There are three fundamental reasons we deliberately avoid linking any C library at all:
\begin{enumerate}
    \item \textbf{No Underlying Kernel Hooks:} Without an OS beneath us, nothing implements those required hooks. There is no kernel, no \texttt{write()} function, and no heap manager; if we linked libc, we would have to write these complex low-level stubs first anyway just to satisfy the linker.
    \item \textbf{Redundant Startup Logic:} The job of \texttt{crt0} (the standard libc startup code that prepares the C environment) is already perfectly handled by the custom \texttt{Reset\_Handler} we built in \texttt{boot/startup.s} (setting up the stack, copying \texttt{.data}, clearing \texttt{.bss}, and branching to \texttt{main}).
    \item \textbf{Absolute Visibility:} The primary educational goal is to \textbf{see every single layer}. Every byte that executes on the board is code you can actively read in the repository. The final compiled image contains exclusively \texttt{boot/startup.s}, \texttt{src/main.c}, and occasionally a few necessary compiler helper routines. Absolutely nothing is hidden from the developer.
\end{enumerate}

\subsection{Bypassing \texttt{libc}: The \texttt{printf} Problem}
If there is no \texttt{libc} and no physical UART driver, how did our bare-metal program successfully print lines to the laptop's terminal[cite: 37]? 

Why not just use standard \texttt{printf}? Our hand-rolled \texttt{Reset\_Handler} does not perform the massive C-runtime initialization that \texttt{newlib}'s semihosting-backed standard I/O (\texttt{rdimon}) expects. Simply routing through \texttt{printf} would silently fail and produce no output. Instead, we use \textbf{direct semihosting} to sidestep the C library entirely, which our freestanding build does not link against anyway.

\subsection{Semihosting: How the Program Still Prints}
Semihosting is a hardware debug convention where the embedded program intentionally traps to the debugger (here, QEMU) to ask it to perform host I/O operations on the target's behalf[cite: 37].

Instead of driving real physical hardware, the execution follows this precise sequence[cite: 37, 38]:
\begin{enumerate}
    \item The program places an operation code into register \texttt{r0}. Here, it uses \texttt{0x04}, known as \texttt{SYS\_WRITE0}, meaning "print this string terminated by a zero byte"[cite: 37]. 
    \item It places the memory address of the string into register \texttt{r1}[cite: 37].
    \item It executes \texttt{bkpt 0xab}: a software breakpoint instruction tagged with a special identifying number[cite: 38].
    \item QEMU intercepts this breakpoint, halts the CPU, reads \texttt{r0} and \texttt{r1}, fetches the string directly from the target's RAM, and prints it on your laptop's terminal[cite: 38].
    \item Once finished, the host commands the program to resume execution seamlessly[cite: 38].
\end{enumerate}

\subsection{Implementing Semihosting in C (\texttt{main.c})}
To achieve this without an operating system, the C implementation in \texttt{src/main.c} uses Extended Inline Assembly to force the CPU to fulfill this hardware contract:

\begin{lstlisting}[language=c]
#include <stdint.h>

static void semihost_write0(const char *message)
{
    /* 1. Operation Code into r0 */
    register uint32_t r0 __asm__("r0") = 0x04;
    
    /* 2. String Address into r1 */
    register const char *r1 __asm__("r1") = message;
    
    /* 3. Execute the hardware trap */
    __asm__ volatile ("bkpt 0xab" : : "r"(r0), "r"(r1) : "memory");
}
\end{lstlisting}

This small function introduces advanced compiler features:
\begin{itemize}
    \item \textbf{Register Binding:} The \texttt{register ... \_\_asm\_\_("r0")} syntax is a GCC extension that forces the compiler to place the value into that exact physical CPU register. Standard C does not guarantee which register a variable will use, but the semihosting convention rigidly demands \texttt{r0} and \texttt{r1}[cite: 38].
    \item \textbf{The Instruction:} \texttt{\_\_asm\_\_ volatile} allows the insertion of the raw \texttt{bkpt 0xab} assembly instruction, which has no C equivalent[cite: 38].
    \item \textbf{Memory Barrier:} The \texttt{"memory"} clobber at the end is a critical safeguard. It warns the compiler that this instruction may arbitrarily read memory (the string). This explicitly prevents the C optimizer from reordering earlier variable writes past this point, guaranteeing the string is fully assembled in RAM before QEMU halts the CPU to read it[cite: 38].
\end{itemize}

\subsection{Semihosting is a Trap}
Look closely at what \texttt{bkpt 0xab} really does[cite: 38]. The program stops doing its own work; control passes to someone more powerful (QEMU, outside the emulated CPU); that someone performs the job and hands control back[cite: 38, 39]. 

This is the exact same architectural shape as a system call on Linux: your program cannot drive the terminal itself, so it asks the kernel to do it, and the kernel returns control when the job is done[cite: 39].

\subsection{Privileged and Unprivileged Code on Cortex-M}
The Cortex-M3 implements the kernel/user mode concept directly in hardware, combined with the two CPU modes[cite: 79]:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|l|}
\hline
\textbf{CPU mode} & \textbf{When} & \textbf{Privilege} \\ \hline
\textbf{Handler} mode & running an exception handler & always \textbf{privileged} \\ \hline
\textbf{Thread} mode & normal code (\texttt{main}, ...) & privileged \textbf{or} unprivileged \\ \hline
\end{tabular}
\end{table}

After reset, the CPU defaults to Thread mode and is \textbf{privileged}[cite: 80]. That is exactly how \texttt{Reset\_Handler} was able to freely write to VTOR, SHCSR, and CCR[cite: 80]. \textbf{Unprivileged} Thread mode is the equivalent of user mode: the restricted mode for code that a kernel would not trust[cite: 80].

\subsubsection{The CONTROL Register}
Which privilege level Thread mode uses is selected by the \textbf{CONTROL} register, a special register inside the CPU (like PRIMASK, it is not mapped in standard memory)[cite: 81]:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|l|}
\hline
\textbf{Bit} & \textbf{Name} & \textbf{Meaning} \\ \hline
0 & \textbf{nPRIV} & 0 = privileged, 1 = unprivileged (Thread mode only) \\ \hline
1 & SPSEL & selects which stack pointer Thread mode uses (not used here) \\ \hline
\end{tabular}
\end{table}

Because special registers are not reachable with standard \texttt{ldr} and \texttt{str} instructions, two dedicated instructions are used to read and write them[cite: 81]:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{Instruction} & \textbf{C equivalent} \\ \hline
\texttt{mrs r0, control} & \texttt{r0 = CONTROL;} (read a special register) \\ \hline
\texttt{msr control, r0} & \texttt{CONTROL = r0;} (write a special register) \\ \hline
\end{tabular}
\end{table}

\subsection{Dropping Privilege: A One-Way Street}
In \texttt{src/main.c}, after the first two lines are printed, the program intentionally drops its own privilege using a small block of inline assembly[cite: 81]:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{ARM Assembly} & \textbf{C Equivalent} \\ \hline
\texttt{mrs r0, control} & \texttt{CONTROL = CONTROL | 1;} \\
\texttt{orr r0, r0, \#1} & \\
\texttt{msr control, r0} & \\
\texttt{isb} & \\ \hline
\end{tabular}
\end{table}

This is a read-modify-write pattern, this time executed on a special register[cite: 81]. The last instruction, \texttt{isb} (Instruction Synchronization Barrier), is critical because modern CPUs fetch instructions ahead of time[cite: 81]. Some of the following instructions may have already been fetched under the old, privileged rules[cite: 81]. \texttt{isb} flushes the pipeline, throws those pre-fetched instructions away, and forces the CPU to fetch them again under the strictly enforced unprivileged rules[cite: 81].

\textbf{The Privilege Trap:} This transition is a \textbf{one-way street}[cite: 81]. Writing to the CONTROL register is itself a privileged operation: if unprivileged code attempts to execute \texttt{msr control, r0} to clear nPRIV, the hardware simply \textbf{ignores} the write[cite: 81]. Code cannot maliciously promote itself back to privileged execution[cite: 81, 82]. There are only two ways back: a full hardware \textbf{reset}, or \textbf{an exception} (because exception handlers automatically run in Handler mode, which is unconditionally privileged)[cite: 82].

\subsection{What Unprivileged Code Cannot Do (The Sandbox Constraints)}
Once restricted, the CPU actively blocks critical operations to create a secure sandbox[cite: 83]:

\begin{table}[h!]
\centering
\begin{tabular}{|p{0.5\linewidth}|l|}
\hline
\textbf{Attempt} & \textbf{Result} \\ \hline
Read or write the \textbf{System Control Space} (\texttt{0xE000E000}...): SysTick, NVIC, SCB & \textbf{BusFault} \\ \hline
\texttt{msr control, r0} (raise privilege back) & Ignored \\ \hline
\texttt{cpsid i} / \texttt{cpsie i} (mask or unmask interrupts) & Ignored \\ \hline
Semihosting \texttt{bkpt 0xab} & QEMU refuses it, so it faults \\ \hline
\end{tabular}
\end{table}

\textit{(Note: The NVIC is the hardware block that manages device interrupts; it lives in the same restricted system area as the SCB)[cite: 83].}

Ordinary RAM, flash memory, and standard code execution still work normally[cite: 83]. The restricted code simply cannot \textbf{reconfigure the machine}, and it cannot silence it by masking interrupts[cite: 83].

\subsubsection{Try It: The HardFault Escalation}
The semihosting restriction has a direct, observable consequence[cite: 83]. Right after the privilege-drop block in \texttt{main}, add a call to \texttt{semihost\_write0("main: unprivileged hello\textbackslash{}n");} and run \texttt{make run}[cite: 83]:

\begin{lstlisting}[language=bash]
main: privileged hello
main: this text lives in .data
HardFault_Handler: a hard fault happened
\end{lstlisting}

Your line never prints[cite: 84]. QEMU strictly refuses semihosting requests from unprivileged code[cite: 84]. The \texttt{bkpt} instruction is treated as a security violation and triggers a fault[cite: 84]. Since no dedicated fault handler covers this specific trap in the current setup, it escalates to \textbf{HardFault}[cite: 84]. 

Notice that \texttt{HardFault\_Handler} \textit{can} print via semihosting, even though the code that caused the fault was unprivileged[cite: 84]. This is because handlers automatically run in Handler mode, regaining full privileges[cite: 84]. (Stop QEMU with \texttt{Ctrl-C} and remove the offending line).

\subsubsection{Debugging the CONTROL Register}
You can watch the \texttt{nPRIV} bit flip in the debugger[cite: 80]. With \texttt{make debug} in terminal 1, run the following in GDB:

\begin{lstlisting}[language=bash]
(gdb) target remote :1234
(gdb) break main
(gdb) continue
(gdb) p/x $control        # 0x0: privileged
\end{lstlisting}

Then let the program run past the privilege drop (for example, by setting a breakpoint on \texttt{SVC\_Handler}---introduced in the next section---and continuing)[cite: 80]. Print \texttt{\$control} again: it is now \texttt{0x1}[cite: 80]. The \texttt{nPRIV} bit is set, and it securely stays set[cite: 80].

\subsection{SVC: The Door That Stays Open}
Unprivileged code is strictly blocked from touching the hardware, but it can still \textbf{ask} for tasks to be done on its behalf. The \texttt{svc \#n} ("supervisor call") instruction is deliberately allowed to execute within unprivileged code.

When executed, it raises the \textbf{SVCall} exception (Exception 11), whose designated handler resides in slot 11 of the vector table: \texttt{SVC\_Handler}. As with any exception, the CPU immediately transitions into Handler mode, meaning the handler itself runs fully \textbf{privileged}. When the handler function returns, the CPU drops back into Thread mode to execute the instruction right after the \texttt{svc}, \textbf{still entirely unprivileged}.

\begin{lstlisting}[language=make]
 Thread mode, UNPRIVILEGED              Handler mode, PRIVILEGED
 -------------------------              ------------------------
 main:
   ...
   svc #0  ----- SVCall exception ----> SVC_Handler:
                                          semihost_write0("...")
                                          (can print, can touch
                                           SysTick, NVIC, SCB)
   next instruction <--- exception return --- return
   ... (still unprivileged)
\end{lstlisting}

Hardware privilege is \textbf{borrowed} only for the strict duration of the handler, and only the specific code \textit{you} compiled into the handler runs with it. The unprivileged code does not get to choose what the handler runs; it can only knock on the door.

The number \texttt{\#n} inside \texttt{svc \#n} is encoded directly into the machine instruction. Real OS kernels utilize this number (combined with arguments passed in registers) to determine \textit{which} specific system service is being requested. For our baseline proof of concept, there is only one service, so the program simply executes \texttt{svc \#0}.

\subsection{This Is a System Call}
Compare this bare-metal sequence directly with what happens on a standard desktop environment:

\begin{table}[h!]
\centering
\begin{tabular}{|l|l|l|}
\hline
 & \textbf{Linux on your laptop} & \textbf{Our Cortex-M3} \\ \hline
\textbf{Restricted code} & your program, in user mode & \texttt{main} after \texttt{nPRIV} = 1 \\ \hline
\textbf{Trap instruction} & \texttt{syscall} (x86-64), \texttt{svc} (ARM) & \texttt{svc \#0} \\ \hline
\textbf{Privileged side} & the kernel & \texttt{SVC\_Handler} \\ \hline
\textbf{Service} & \texttt{write()} puts bytes on the terminal & print via semihosting \\ \hline
\end{tabular}
\end{table}

The architectural mechanism remains identical at every scale: the restricted side cannot safely perform the job itself, so it intentionally traps into code that can, and that privileged code securely decides what to do. The \texttt{write()} system call located at the bottom of the libc \texttt{printf} stack on your laptop works exactly this way.

\subsection{Adding the System Call}
The final steps to turn this into working code happen in \texttt{src/main.c}.

First, you must write the \texttt{SVC\_Handler}. It prints a message using \texttt{semihost\_write0} and then simply returns:

\begin{lstlisting}[language=c]
void SVC_Handler(void)
{
    semihost_write0("SVC_Handler: privileged code printing on behalf of unprivileged code\n");
}
\end{lstlisting}

Unlike the hardware fault handlers you wrote earlier, it does \textit{not} loop forever: an \texttt{svc} trap is a deliberate request for service, not a bug. Falling off the end of the C function triggers a clean return from the exception, dropping privileges and jumping back to the instruction after \texttt{svc \#0}. Its name strongly overrides the weak default defined in \texttt{boot/startup.s}, just like the fault handlers did. 

\textit{(Note: A standard C function can serve flawlessly as an exception handler because the Cortex-M hardware automatically saves and restores the registers a C function might modify upon exception entry and return).}

Then, after the privilege drop in \texttt{main}, you insert the trap instruction using inline assembly:

\begin{lstlisting}[language=c]
__asm__ volatile ("svc #0" : : : "memory");
\end{lstlisting}

Executing \texttt{make run} now correctly prints the third line:
\begin{lstlisting}[language=bash]
SVC_Handler: privileged code printing on behalf of unprivileged code
\end{lstlisting}

\textit{Troubleshooting note:} If you forget to explicitly write the \texttt{SVC\_Handler} in C, the \texttt{svc} instruction seamlessly lands in the weak \texttt{Default\_Handler} defined in \texttt{boot/startup.s}, and the program hangs silently in its infinite loop (meaning the weak default successfully did its job).

\subsection{Touching the Hardware Without Privilege}
Finally, you must definitively verify that the unprivileged hardware protection is actively enforced. 

After the \texttt{svc \#0} line, while \texttt{main} is still unprivileged, attempt to write \texttt{0} into the SysTick timer's control register (located at address \texttt{0xE000E010} in the restricted System Control Space):

\begin{lstlisting}[language=c]
volatile uint32_t *systick_ctrl = (volatile uint32_t *) 0xE000E010;
*systick_ctrl = 0;
\end{lstlisting}

Running \texttt{make run} yields:
\begin{lstlisting}[language=bash]
SVC_Handler: privileged code printing on behalf of unprivileged code
BusFault_Handler: a bus fault happened
\end{lstlisting}

The output proves that the \texttt{svc} successfully returned to unprivileged code. Then, the System Control Space hardware actively rejected the unprivileged store instruction, forcing the CPU to raise a \textbf{BusFault}. Because \texttt{Reset\_Handler} enabled bus faults earlier in the SHCSR, the fault routes directly to its own specific handler, and you immediately know exactly what kind of error occurred.

\subsubsection{Conclusion: Privilege and CPU Modes}
One final observation completes the picture. In gdb, put a breakpoint on \texttt{SVC\_Handler}, \texttt{continue} execution, and print \texttt{\$control} inside the handler: it is still \texttt{0x1}. 

The handler is privileged \textit{not} because the \texttt{nPRIV} bit magically cleared itself, but because the CPU is currently running in \textbf{Handler mode}. Handler mode is architecturally designed to always be privileged, regardless of what the \texttt{CONTROL} register says.


\section{Conclusion: The Final Result}
With all the steps in place, the solution's \texttt{make run} prints the four lines you saw at the beginning of this chapter:

\begin{lstlisting}[language=bash]
main: privileged hello
main: this text lives in .data
SVC_Handler: privileged code printing on behalf of unprivileged code
BusFault_Handler: a bus fault happened
\end{lstlisting}

Read them as a definitive summary of the week's architectural work:
\begin{itemize}
    \item The \textbf{first line} shows that \texttt{Reset\_Handler} successfully reached \texttt{main}, operating securely in privileged Thread mode.
    \item The \textbf{second line} shows that the \texttt{.data} copy loop works: the linker's LMA/VMA memory split and your assembly boot code perfectly agree.
    \item The \textbf{third line} shows that after intentionally dropping privilege, unprivileged code can still securely get privileged work done through \texttt{svc} and \texttt{SVC\_Handler}: establishing a true system call.
    \item The \textbf{fourth line} shows that unprivileged code attempting to reconfigure the CPU is immediately stopped by a \texttt{BusFault}, which is then cleanly reported by its own dedicated handler thanks to the SHCSR configuration. 
\end{itemize}

\textit{Note: With \texttt{DEMO\_DIVIDE\_BY\_ZERO} in \texttt{src/main.c} set to 1, the same image instead prints \texttt{UsageFault\_Handler: a usage fault happened}, proving the CCR divide-by-zero trap actively works.}

Your program now runs completely \textbf{freestanding}: there is no libc, no crt0, and no underlying OS (and the \texttt{Makefile} flags state this explicitly). It prints through semihosting, trapping into a more powerful host. Crucially, it implements---in just a few dozen lines of assembly and C---the core idea of every operating system's protection model: \textbf{restricted code cannot touch the machine directly, and must ask privileged code through a single, controlled door.}
